# COLLABORATION.md — Little Sprout 完整協作規約

本檔是 `CLAUDE.md` 的完整版參考：gates 細節、Linear 狀態機、命名與訊息範本、agent model 政策、前饋↔反饋對照表。產品與技術規劃見 `docs/PLAN.md`。

## 0. 最高原則：前饋必有反饋

所有寫給 agent 的指示（CLAUDE.md、agent 定義、派工 prompt）都**假設可能不被遵守**。每一條重要規則都必須有對應的**機械式反饋 gate**（hook、CI、腳本）攔截違規；做不到機械攔截的，由 orchestrator／merge-reviewer 人工兜底，並在 §7 對照表誠實標示。**新增重要規則時必須同時新增它的 gate，否則視為未完成。**

## 1. 角色與分工

- **Orchestrator（主 session）**：拆解任務、在 Linear 開票與推動狀態、指派 subagent、把關每一個 gate。原則上不直接寫功能程式碼（harness 與小型修補除外）。
- **ui-designer subagent**：**所有 UI 畫面設計必須由這個專門的 subagent 透過 Pencil MCP（.pen 設計檔）完成**。禁止在沒有 .pen 設計稿的情況下直接手寫新畫面的 SwiftUI 版面。設計檔：`design/littlesprout.pen`。
- **ios-dev subagent**：功能實作。一張 ticket＝一個 worktree＝一條 branch。**UI 票（Swift diff 含 `Features/`或 `DesignSystem/`）push 前必跑 `scripts/gates/tap-target-check.sh <UDID> <scheme>`**（≥44pt 點擊目標機械 gate，已掛進 push-gate.sh／CI 自動觸發，不需要手動另外跑；LS-95）。**新增 Features 畫面必須同步更新 `LittleSprout/TapTargetGateScreenName.swift`（註冊）或 `scripts/gates/tap-target-exemptions.txt`（具名排除＋理由）**——`tap-target-registry-check.sh` 對帳，兩邊都沒有即擋（LS-95 M1）。
- **merge-reviewer subagent**：merge gate 的 code review（四維度，見 §4）。**裁決除 Linear comment 外必貼 GitHub commit status `merge-review`** 到 orchestrator 派工給的 PR head SHA（`bash scripts/ops/post-status.sh <審的 sha> merge-review success|failure "<verdict> R<n> · linear:<comment id>" --url <comment url> --expect <當下 head>`：APPROVE→success、REQUEST_CHANGES→failure；`gh pr view … headRefOid` 只當 `--expect` 比對，與審的 SHA 不同即 exit 2 不貼、回報 head 已前進需重審；分支保護列它為 required check，沒貼＝併不進去；status 綁 SHA 不隨分支走——head 再 push 即重審重貼；貼失敗不得靜默，handoff 明說由 orchestrator 補貼；LS-87）。
- **qa subagent**：在 `test` branch 上依驗收條件驗收，UI 票必做視覺驗收（模擬器實際渲染，優先用 mobile-mcp，備援 `xcrun simctl` 截圖）。裁決先 `save_comment` 寫回票、再**必貼 commit status `qa`** 到驗收的 `test` tip SHA（`git rev-parse HEAD`＝`origin/test`；PASS→success、FAIL→failure、BLOCKED→failure 且 description 以 `BLOCKED: <缺什麼>` 開頭；description 帶 comment id）——`promote.sh test main` 只認這個 SHA 的 `qa` success；test 前進即重驗重貼（LS-87）。
- **dead-code-sweeper subagent**：feature 收尾時巡檢該 feature 引入的死碼與殘留物（只報告不刪改）。
- **visual-reviewer subagent**：對抗性視覺審查。**任何設計稿在送 orchestrator／使用者核可之前必須先過它**——以極嚴視覺標準獵殺 AI slop 與模板感，預設 ITERATE（退修；verdict 詞彙唯一：ITERATE／APPROVE），設計須自證三個記憶點才能通過。只審查不動檔。
- **ui-designer 與 visual-reviewer 開工必先用 Skill 工具載入專案 skill `little-sprout-brand`**（`.claude/skills/little-sprout-brand/`：LS-46 定案的 tokens 與實測對比、字標與品牌、沖印品母題、長輩硬約束、專案版 slop 禁例、實作進場條件 12 項；載入失敗不得靜默、handoff／verdict 明說），skill 本體與兩份定義的接線由 `scripts/gates/brand-skill-check.sh` 在 CI 驗（LS-30，§7）。

**Agent model 政策**（agent 定義檔的 `model:` 為預設；orchestrator 派工時得以 Agent 工具的 `model` 參數覆寫升級）：

| Agent | 預設 | 升級到 opus 的時機（orchestrator 手動判斷） |
|---|---|---|
| ui-designer | sonnet | 建立全新設計語言／資訊架構大改版時 |
| ios-dev | sonnet | 併發或架構性的票（背景上傳佇列、導航骨架、RLS 設計）、同一票 sonnet 兩次未過 gate、hotfix |
| merge-reviewer | opus | 預設即最高——review 是安全網；純文件 diff 可降 sonnet |
| qa | sonnet | 驗收含併發時序或安全（RLS）判斷時 |
| dead-code-sweeper | sonnet | 大型 feature 批次或跨模組重構後的巡檢 |
| visual-reviewer | opus | 預設即最高——視覺判斷是對抗審查的核心能力 |

降級同理：機械性小任務（批次改名、跑腳本回報）可用 haiku。升降級都要在派工訊息中註明理由。

**審查類 agent 的 Linear 權限**（LS-60）：merge-reviewer 與 dead-code-sweeper 具 Linear 讀票（`get_issue`／`list_comments`）權，merge-reviewer 另具 `save_comment` 寫回權；兩者皆**無** `save_issue`（不得改狀態或票文）。審查依據以票文為準，不得只憑 commit／PR body 推斷。

## 2. 分支模型

| Branch | 用途 | 規則 |
|---|---|---|
| `main` | 正式站（App Store / TestFlight 發佈來源） | 禁止直接 commit；只由 `test` 以 `promote.sh` fast-forward 晉升，或接受 `hotfix/*`／harness 分支與 `revert-*` 的 PR |
| `test` | 測試站；qa subagent 在此驗收 | 禁止直接 commit；只由 `development` 以 `promote.sh` fast-forward 晉升（不開 PR、不留 merge commit、不收 back-merge） |
| `development` | 開發整合 | 禁止直接 commit；只接受來自工作分支的 PR（或 hotfix 併入 `main` 後的 back-merge PR） |
| `feature/*` `fix/*` `hotfix/*` | 工作分支 | 一律在 worktree 中作業；`hotfix/*` 從 `main` 切出 |

流向：`feature|fix/* → development ⇒(FF) test ⇒(FF) main`。**晉升＝`bash scripts/ops/promote.sh <from> <to>`**（development→test、test→main；LS-85）：`git fetch` → 方向白名單 → FF 檢查（`origin/<to>` 須為 `origin/<from>` 的祖先，否則拒絕並指示先 back-merge）→ `origin/<from>` 的 SHA 四個 check（`ci`／`db`／`lint`／`rules`，只認 GitHub Actions app 15368）各取最新一筆皆 success → 同一 SHA 的 commit status `merge-review` 為 success（test→main 另需 `qa` 為 success；`gh api …/commits/<sha>/status`，缺／failure／pending 皆拒並印出誰該貼——見下方「裁決 status 貼在哪個 SHA」；LS-87）→ `PROMOTE_VIA_SCRIPT=1 git push origin <驗過的 sha>:refs/heads/<to>`（推 SHA、不推 ref——巡檢 cron 的 `git fetch` 會移動 remote-tracking ref）→ 印摘要。不開 PR、不留 merge commit、不派 merge-reviewer（它只審 feature／fix／hotfix PR）、不再 back-merge。**禁止手動 `git push origin development:test`／任何直推 `test`／`main`**——push-gate 第 0 步 `push-ref-check` 擋無 `PROMOTE_VIA_SCRIPT=1` 或非 FF 的 test／main 推送。三條分支永遠是祖先鏈（`test ⊂ development`、`main ⊂ development`），漂移由巡檢偵測（§4-b）。development→test 由 orchestrator 批次晉升（QA 票 test 未含時）；test→main 即 release（打 tag `vX.Y.Z`）。帳：LS-57 一張票 4 個 PR（#114 dev→test、#118 test→main、#121／#123 back-merge）、4 輪 CI、零人審，全為了讓分支保護放行；back-merge 純粹是 `--merge` 在 main 留 merge commit 造成。

**裁決 status 貼在哪個 SHA（LS-87）**——status 綁 SHA、不隨分支走，所以每個要併／要推的 SHA 都得有人對它負責（工具一律 `bash scripts/ops/post-status.sh <sha> <merge-review|qa> <success|failure> "<description>" [--url]`）：

| 動作 | SHA | 誰貼 | context／description／前提 |
|---|---|---|---|
| feature／fix／hotfix PR | orchestrator 派工給的 PR head（`git rev-parse <head>`；`gh pr view <n> --json headRefOid -q .headRefOid` 只當 `--expect` 比對——不同＝head 已前進，不貼、重審） | merge-reviewer | `merge-review` success／failure，`<verdict> R<n> · linear:<comment id>`；再 push＝新 head＝重審重貼 |
| promote development→test | `origin/development` tip（GitHub 產生的 PR merge commit——沒人審過這個 SHA 本身） | orchestrator | `merge-review` success，`promote: no content diff（PR #<n> head <sha7>）`。**先核對**：`git log --first-parent --merges origin/test..origin/development` 每個 merge commit 的第二親（`<merge>^2`）都有 `merge-review` success（`gh api …/commits/<merge>^2/status`），且 merge commit 沒有手解衝突夾帶的內容（先 `tree=$(git merge-tree --write-tree <merge>^1 <merge>^2) || { echo 衝突→不貼; exit 1; }` 再 `git diff <merge> "$tree"` 為空——merge-tree 有衝突時 exit 1 且把衝突報告印到 stdout，直接塞進命令替換會餵給 `git diff` 一坨文字、看到的是 git 錯誤而不是「有手解內容」）；任一不成立不貼、退回重審 |
| promote test→main | `origin/test` tip（＝上一列貼過的同一 SHA，`merge-review` 已在） | qa agent | `qa` success，`PASS R<n> · linear:<comment id>`（FAIL／BLOCKED→failure）；**orchestrator 不得代貼** |
| back-merge PR `main`→`development` | PR head＝`main` tip（hotfix PR 的 merge commit；若 main 是 FF 晉升來的，SHA 同 test tip、status 已在） | orchestrator | `merge-review` success，`back-merge: no content diff（hotfix PR #<n> head <sha7>）`；核對方式同 promote 列 |

**GitHub 端強制**：`development` 必須走 PR；`test`／`main` 不要求 PR（FF push 推得進去）但 required status checks `ci`＋`lint`＋`rules`＋`db`（四個皆限 GitHub Actions app 15368）＋`merge-review`（commit status context，`app_id: -1`＝任何來源——由 post-status.sh 以 gh 使用者 token 貼，不是 Actions；`development` 亦列，只 PATCH `required_status_checks` 且只加 `merge-review`——其餘 check 照現況（lint／rules 目前 any，不收緊）、require PR 不動；LS-87）對**推上去的 SHA** 生效——沒有四個綠 check＋`merge-review` success 的 SHA 推不上去、沒有 `merge-review` success 的 head `gh pr merge` 被拒（GH006，server-side 硬 gate；CI 對 development／test／main 的 push 也跑四 job，每個 SHA 都有 check）；三條分支皆 enforce_admins（admin 也不能繞）、禁 force-push 與刪除。**同一 SHA 推到 test／main 會再跑一輪 CI**：flaky 紅時**重跑該 job**（`gh run rerun <run-id> --failed`）即解封，不得 `--no-verify`／手動 push 繞過（PR #141 R1 F4）。套用／核對：`bash scripts/ops/protection-apply.sh <development|test|main> [--dry-run] [--out <dir>]`（冪等；前後 protection JSON 存 `<dir>/protection-<b>-{before,after}.json` 附 PR body；development 只動 checks 段）。**套用時機**：`merge-review` 列為 required 的那一刻起所有 open PR 的 head 都需要 status——先把在飛的 PR 併完或逐一補貼，再套（LS-87 的實際套用由 orchestrator 在其 back-merge 併入後執行）。「限制推送者」GitHub 只對 organization repo 開放，本 repo user-owned → 由 collaborators 清單承載（僅使用者本人有 push 權）。盲區：GitHub 沒有「拒絕非 FF 推送」的規則（require linear history 會連 development 自己的 PR merge commit 一起拒）——FF 只能由 promote.sh／push-gate 在客戶端驗，漂移由巡檢偵測（§7）。

**Worktree 規約（平行分工）**：
- 位置 `.claude/worktrees/LS-<n>`（已 gitignore）。一張 ticket 一個 worktree 一條 branch（gate：`branch-ticket-check`，工作分支自 merge-base 以來的 commit 票號必須等於分支票號；刻意夾帶他票以 commit body＋PR body 各一行 `Bundles: LS-<m>` 宣告——LS-50，§7）。
- 多張 ticket 平行時各自 worktree，**禁止跨 worktree 編輯檔案**；合併完成後移除 worktree——機械面用 `bash scripts/ops/cleanup-merged.sh [--dry-run|--apply] [--force] [LS-<n>]`（LS-86）：掃描已完全併入 `origin/main`／`origin/development` 的 worktree／本機分支／遠端分支，預設 dry-run 只列、`--apply` 才實際 `git worktree remove`／`branch -D`／`push origin --delete`；dirty worktree（tracked 修改／未追蹤非 ignored 檔；gitignore 掉的產物不算，移除前印審計清單——LS-141）、保護分支、呼叫端目前所在目錄一律略過並列出——只有殘留全命中白名單（`__pycache__/`、`.DS_Store`）且加 `--force` 才視為可清，絕不刪未併入的東西；票 Canceled／Done 但從未開工的 worktree 指名時可清（Linear 狀態自動查或 `--force-unstarted`，LS-141）。**agent 不得自行刪分支／worktree，只有 orchestrator 執行此腳本**（此前完全靠自律：2026-08-25 一次盤點抓到遠端 39 條分支 29 條已併、本機 19 條分支 9 條已併、5 個已併未移除的 worktree＋1 個 `mktemp` 殘留）。GitHub repo 設定 **`delete_branch_on_merge=true`**（已開）使 PR 併入即自動刪 head 分支；CLI 直接 push（未經 PR）併入的分支不受它涵蓋，靠 `cleanup-merged.sh` (c) 段掃（§7）。`mktemp -d` 建的暫存 worktree 由建立者的腳本自行 `git worktree remove`，不得留——`cleanup-merged.sh` (d) 段對路徑落在系統暫存目錄樣式（basename `tmp.*`）的殘留兜底清。票 Canceled 或分支被取代（無 PR、票已 Done）建議打 `archive/<branch>` tag 後刪分支（歷史可取回，不留分支）——**此項僅規約、無機械 gate**（判斷「該不該歸檔」需要 Linear 票狀態，非本票範圍，記入待辦池 LS-96）。巡檢 `patrol.sh` 的「分支已併入 base、worktree 未移除」偵測會直接印出 `cleanup-merged.sh` 指令供執行（§4-b／§7）。
- 首次 clone 後執行 `git config core.hooksPath .githooks` 啟用 gate hooks（worktree 共用同一份 config，不必重設）。
- **Pen 是單一全域文件（LS-91）**：涉及 `.pen` 的票派工前，orchestrator 先切檔——**ui-designer（會實際編輯）**跑 `bash scripts/ops/pen-open.sh <該票 worktree>` 把 Pen 切到該 worktree 的 `design/littlesprout.pen` 並對帳（exit 0 才算切成功；agent 開工仍要自己 `get_app_state` 再核對一次，見各 agent 定義）；**visual-reviewer／qa（唯讀讀稿）改跑 `bash scripts/ops/pen-read.sh <該票 worktree>`**（＝`pen-open.sh <root> --force-reload`）——`get_app_state` 回報「已一致」不保證那份 renderer 沒有停在磁碟被 git 更新前的舊快照，`pen-read.sh` 無條件強制清場重開才算數，見 §7「Pencil MCP filePath」列（LS-118）。移除任一設計相關 worktree 前，先跑 `bash scripts/ops/pen-open.sh <repo 根目錄>` 切回主 checkout 並確認 exit 0，避免移除後 Pen 仍指著一份已經消失的檔案。**設計票收工條件加一句**：handoff 前 `bash scripts/ops/pen-open.sh <repo 根目錄>` 須 exit 0（Pen 只開主 checkout）——這是 ui-designer 收工程序的最後一步，也是任何動過 `.pen` 的 agent 結束前的檢查點。`open -a Pen` 只在目標路徑**尚未在其他背景視窗開著**時可靠切換——多張設計票輪替下背景視窗會累積；R2 起 `pen-open.sh` 對此**自動清場**：偵測到殘留視窗時，先對它跑 `pen-land.sh --dry-run` 確認沒有未落地的變更（有變更就不動、印出先落地的指示），安全才 quit（優雅退出失敗則 fall back `kill -TERM`）＋重開＋重試一輪；`--no-quit` 關掉自動清場、只做原本的對帳，機制細節見 `scripts/ops/pen-open.sh` 檔頭與 §7。

**Harness 變更例外**：協作規約與 harness 檔（`CLAUDE.md`、`docs/COLLABORATION.md`、`.claude/agents/`、`.claude/settings.json`、`scripts/gates/`、`scripts/ops/`、`.githooks/`、`.github/`、`.mcp.json`）不走 feature→QA 全流程，比照 hotfix：從 `main` 切 `hotfix/LS-<n>-*` branch、PR 回 `main`（CI 照跑），合併後**只補一支 back-merge `main`→`development`**（`gh pr create --head main --base development`；LS-85 起唯一保留的 back-merge；head＝`main` tip 需 `merge-review` status——orchestrator 依上表「back-merge」列貼），`test` 不補——下次 `promote.sh development test` FF 帶到。**back-merge PR 一律「Create a merge commit」併入**：squash／rebase 會產生不在 `main` 上的新 commit，`main ⊂ development` 從此不成立、之後每一次 promote 的 FF 檢查永久失敗（PR #141 R1 F3；repo 設定關閉 squash／rebase merge 屬使用者手動設定項，§7）。這些檔案在 development 即時一致即可：所有工作分支都從 development（hotfix 從 main）切出，test／main 只會是 development 的祖先。

**harness PR 併入 `main` 後，先 pull 主 checkout 再派 agent（LS-71）**：agent 定義（`.claude/agents/`）、`CLAUDE.md`、專案層 `.claude/settings.json` 與 gate 腳本都是從**主 checkout**（repo 根目錄，不是 worktree）讀的——harness PR 併了但主 checkout 沒 `git pull --ff-only origin main`，接下來派出的每個 agent 都在用舊規約。SessionStart hook 會在 session 開頭偵測主 checkout 落後 `origin/main` 並提示（§4-b）；session 中途併入的靠 orchestrator 在 merge 後立刻 pull（§7）。**並行 harness PR 的合併順序**：兩張 harness 票同時在飛時幾乎必撞 `docs/COLLABORATION.md` §7 對照表尾與 `.github/workflows/ci.yml` 的自測 step——先併者不動，**後併者負責 `git merge origin/main` 解衝突再 push**（PR 頁 CONFLICTING 不會跑 CI，`merge-conflict-check` 只驗 push 當下，§7）。

**本地合併版 back-merge 的分支命名（LS-56 補記；LS-85 起只剩 `main`→`development` 這一支）**：GitHub 偶爾把 back-merge PR 誤判 CONFLICTING（本地 `git merge-tree` 零衝突——LS-54 PR #71 實測）。此時改在本地把 `main` merge 進 `development` 的臨時分支再開 PR，該分支**必須命名 `hotfix/LS-<n>-backmerge-development`**（例：`hotfix/LS-54-backmerge-development`）；同一形狀也用來修「test 有 commit 不在 development」的漂移（把 `origin/test` merge 進該分支，§4-b）。`test` 不再收任何 back-merge PR（方向矩陣 `base=test` 仍只收 `development|main|revert-*`，但正常路徑是 promote.sh 的 FF push）。命名成 `back-merge/*` 會被擋：CI 由 `rules` job 方向矩陣擋（PR #73 被擋、#74 改名後通過）、本機由 `commit-gate.sh` 的 branch 命名 regex 擋，不必另開規則。

**harness back-merge 後，open PR 要手動 update-branch（LS-10 補記）**：GitHub 的 `pull_request` workflow 定義是跟著該 PR 的 **head** 分支當下內容跑，base 分支被 back-merge 進新的 gate／CI 定義後不會自動反映到既有 open PR 上——那些 PR 的 head 沒有拿到新 commit，仍在用 merge 前的 workflow 版本檢查自己。這不是理論風險：LS-5 的 PR 在 harness back-merge 前後兩次 CI run（`32560313234` → `32560481798`）就是實測到同一份 head 內容因為 base 端 workflow 版本不同而跑出不同結果。做法：**orchestrator 每次執行 harness back-merge 到 `development` 後，必須對 `development` 上所有還開著的 PR 執行 `gh pr update-branch`**（LS-85 起 `test`／`main` 不再有 PR），把 back-merge 後的最新 commit 併進各 PR 的 head，讓它們吃到新 gate 再繼續走 review／CI。無機械 gate（GitHub 不會替你做這件事）；由 orchestrator 人工執行並在對應 ticket 記錄。

## 3. 命名與訊息規約

**Branch**：`feature/LS-123-short-slug`、`fix/LS-124-short-slug`、`hotfix/LS-125-short-slug`（slug 英文小寫連字號；pre-commit hook 會驗格式）。

**Commit message**（Conventional Commits + Linear ID；commit-msg hook 會驗第一行）：
```
<type>(<scope>): LS-<n> <一句話摘要>

<why：為什麼這樣改，而不只是改了什麼>

Fixes LS-<n>        ← 此 commit 完結該票時才加（Linear 自動連動）
```
type ∈ `feat|fix|chore|docs|refactor|test|perf|design`；scope 可省略。禁止 `--no-verify` 繞過 hooks（本機繞過者仍會被 CI required check 擋在 merge 前）。

**PR message**：依 `.github/pull_request_template.md`（ticket、變更摘要、驗證方式、風險、UI 截圖）。**檔頭段必須含本票 `LS-<n>`**（檔頭段＝從檔頭到第一個內容段落結束；開頭空白行與 `#` 標題行一併納入——模板的「## Ticket／空行／LS-<n>」與「Ticket: LS-<n> …」皆可）；`gh pr create/edit --body-file <f>` 之前先 `bash scripts/gates/pr-body-check.sh <f>` 斷言（票號取自當前分支），CI `rules` job 以 head 分支票號再驗（LS-63）。**紅了之後修 body 不會讓 CI 自動重跑**（`pull_request` 觸發不含 `edited`，`gh run rerun` 也重放舊 body）——close/reopen PR 或再 push 一個 commit（同 §6 DESTRUCTIVE-APPROVED 標記的坑，LS-37 實測）。含新畫面的 PR 必須在 body 寫 `Design: <.pen frame 名>`（CI 會驗）。

**暫存檔（scratchpad）**：agent 的暫存檔（PR body、handoff 草稿、取證輸出…）檔名一律 `LS-<n>-<用途>.<ext>`，或放進 `mktemp -d` 子目錄；禁止 `pr-body.md` 這類無票號通名——平行 agent 共用同一個 scratchpad 目錄會互相覆寫（2026-08-24 LS-53／LS-56 撞檔，LS-56 的 body 被 `gh pr edit` 貼上 PR #78，LS-63）。檔名本身無機械 gate，靠上列 PR body 檢查攔它要防的結果。

**派工 prompt 固定五條（LS-71）**——orchestrator 派任何會寫檔／開 PR 的 agent 都貼進 prompt（general-purpose agent 不讀本檔，只有 prompt 到得了）：
1. 暫存檔一律 `LS-<n>-<用途>.<ext>` 或 `mktemp -d`（上段；LS-63 事故）。
2. `gh pr create/edit --body-file <f>` 前先 `bash scripts/gates/pr-body-check.sh <f>`（CI 亦驗檔頭段含分支票號）。
3. `.test.sh` 失敗分支用 `${name}`，不寫 `"$name（"`（bash 3.2 會炸，LS-59）。
4. 分段落地：長工作每完成一項就落地＋commit＋push（.pen 存檔、程式 commit-gate 過就 commit，隨即 push 到工作分支），不准累積到最後一次交——**`.pen` 是不透明檔案，事後無法把一次編輯拆成多筆 commit**，只有邊做邊落地＋commit＋push 才保得住進度（LS-46 R8 第一次派工 4.5 小時無存檔；LS-68）。
5. handoff「未完成／剩餘」欄必列 reviewer 每一條 informational 的處置（已修／記入待辦池 LS-96／另票 LS-<m>（限 §5-b 優先序 High 以上）／不修＋理由），一條不能省（CLAUDE.md「每個 agent 都要遵守」）。**「記入待辦池 LS-96」必附 comment id（≥8 位 hex，先 `save_comment` 取 id 再寫）、「已修」必附 commit SHA（7–40 位 hex）＋檔案:行號，寫在同一行**——來源 LS-96 池項 `9f348e36`／`fd2fe81e`（LS-125 R2 申報四條「記入」一則沒寫、R3 申報「已修」commit 裡沒有該變更）；PR body 由 `scripts/gates/pr-body-check.sh` 全 body 逐行驗格式、CI `--verify` 反查（LS-140，§7）。

**Handoff 訊息**（subagent 完成或交接時，一律用此格式）：
```
Ticket：LS-<n>
已完成：（逐項）
已驗證：（怎麼驗的：測試名稱／指令輸出／截圖）
未完成／剩餘：（reviewer 全部 informational 的處置逐條列：已修 <commit SHA> <檔案:行號>／記入待辦池 LS-96 <comment id>／另票 LS-<m>（限 §5-b 優先序 High 以上）／不修＋理由；SHA／id 與申報同一行，PR body 由 pr-body-check 驗，LS-140）
風險與已知問題：
產出位置：branch／PR／.pen frame 名稱
```

**三種停滯型態**（腳本判定規則；stale＝參數分鐘數，預設 45）：
1. **PR 停滯**：CONFLICTING／UNSTABLE／BEHIND／CHANGES_REQUESTED 立即標；CLEAN 且 reviewDecision＝APPROVED 立即標「可併」；其餘 CLEAN／BLOCKED 超過 stale 沒更新標 ⏳（草稿不標）。
2. **分支停滯**：有 commit 但分支從未 push；領先 remote 且最後 commit 超過 stale（push gate 卡）；落後 remote（別處 push 過）；已 push、無 open PR、最後 commit 超過 stale。
3. **工作區停滯**：有未提交變更（不含 untracked）且最後改動超過 stale；worktree 建好超過 stale 仍 0 commit 無變更（尚未開工）；分支已併入 base（自 merge-base 0 commit、但分支 reflog 有過 commit）而 worktree 未移除（§2：合併完成後移除 worktree）。「最後 commit 幾分鐘前」只在分支自 merge-base 後有 commit 時才看——新 worktree 的 HEAD 就是 base commit，拿它的時間會把剛建好的 worktree 誤判成停滯（scratchpad 原型的 bug）；0 commit 時看 dirty 檔 mtime 與 worktree 的 `.git` 檔 mtime。

- **Backlog→Ready 機械規則**——觸發時點：巡檢每輪（§4-b cron），以及任一票進 In Review／Done 時。對每個 lane：若 In Progress＋In Review ＜ 上限 → 取該 lane Backlog 中 **priority 最高、blockedBy 全 Done、且不需使用者決策（非 `lane:product`）** 的票 → 改 Ready → **立即派工（Ready 不停留）**；同 priority 取 createdAt 最早。補位跳過 Spec／Design 兩格但不免除其離開條件：候補票文須已有可驗證驗收條件與 scope（Spec 出口），缺者不算候補、在 lane 狀態表標「待 Spec」；**同理缺 `project`、或（Phase 專案票）缺 `milestone` 者也不算候補、標「待結構」**（§3「開票結構」出口，與「待 Spec」並列，LS-77）；`lane:ui` 的 Design 出口由上限定義承載（沒核可稿就沒空位）。
- **例外**：`lane:design` 與 `lane:ui` 共用 Pen 時，ui 票的「設計稿讀取階段」期間 design lane 視為滿。**LS-103 起由 `patrol-linear.sh` 的 `lane_wip()`／`design_forced_full()` 機械判定**：ui 票 In Progress 時，若 `pen-open.sh --status` 回傳路徑命中該票 worktree 的 `design/littlesprout.pen`、或其 Pen autosave backup mtime 在 30 分鐘內，design lane wip 視為等於上限（不會誤印補派 design 票的動作）；任一步查不到都判定為「未滿」——**這是寬鬆（fail-open）方向，不是保守**（查不到不代表 Pen 真的空閒，只是機械信號還沒追上；R2 m2 更正此處先前的用字錯誤），不是機械保證（§7 Pen 列）。已知窄窗：ui 票剛派工到第一次 `pen-open.sh <worktree>` 之間那幾分鐘，兩條信號都還沒有東西可查，機械判定會是「未滿」——這幾分鐘內若巡檢剛好跑到，仍可能誤印補派 design 票的動作；**人工兜底**：orchestrator 逐行執行動作清單前，若有 `lane:ui` 票剛派工／狀態剛轉 In Progress 且尚未確認已開始讀稿，即使動作清單印出補派 design 的 `save_issue` 動作也先別執行，等 ui 票的 agent 確認已切檔（或至少過了幾分鐘）再補（§4-b 模板同步）。**LS-118 補記**：`qa`／`visual-reviewer` 現在唯讀讀稿前也會跑 `pen-read.sh`（`--force-reload`，會清場殺 Pen 重開），但觸發時票在 **QA** 狀態、且用的是 `test` checkout，`design_forced_full()` 的判定（命中 `pen-open.sh --status` 或該票 worktree 的 autosave backup mtime）不會命中——design lane 可能同時被判定「未滿」而補派，造成 ui-designer 正在編輯時被這次清場一併收掉（§7 Pen 列 LS-81 同型事故）。目前無機械攔截，**人工兜底**：orchestrator 派工／巡檢補位前，若知道有 QA／visual-reviewer 正在跑視覺驗收，暫緩補派 `lane:design`／`lane:ui`；機械化納入 `design_forced_full()` 記入 LS-96 待辦池。
- **巡檢輸出**多一段「**lane 狀態表**」（每 lane：上限／在飛／候補票）＋「**無 lane 標籤的 open 票**」清單（盲區提醒：沒標 lane 的票不會被補位）。
- **lane 空＝停擺，不是等待**（使用者 2026-09-03 裁決，LS-144；事故：三條 lane 同時空 50 分鐘、巡檢三輪回報「無異常、補位 hold」）：任一 lane 在飛 0 且無可派候補（無候補或候補全被擋）時，`patrol-linear.sh` 動作清單印 `→ 開票：lane:<x> 空 n 輪（…）——來源候選：…`（§4-b「工具」段），orchestrator 當輪開票或在 notes 寫明不開的理由（§4-b 模板第 4 步）；連續空 ≥2 輪升 `⚠`。票文標「**需 Design gate**」的 Backlog 票**永不列為候補**（lane 狀態表歸「待Design」——實作票是核可後另開的子票，Story 本身不派；這條同時補上「`lane:ui` 的 Design 出口由上限定義承載」的機械缺口，LS-96 池項 `b2993155`），只作為 design／ui lane 的開票來源。

**harness 優先序（2026-08-25 使用者核可；LS-79 規約段）**——起因：harness 票增長快於 product（open 32 張中 harness 18 張）。WIP=1 擋得住並行，擋不住 orchestrator 注意力、佇列擋 product、每張 gate 加重所有 PR、規則越多越常踩線的正回饋。規則：

- **排序 key**：Linear `priority` → 同級 `size:S`（<1h）→ `size:M`（半天）→ `size:L`（1 天+）→ createdAt。每張 `lane:harness` 票**必帶一個 `size:*` 標籤**。
- **分級**：**Urgent**＝blockedBy 鏈上擋住 product／design 票；**High**＝後果不可逆（正式站資料、併錯分支、誤刪）、或同類事故已發生 ≥2 次、或使用者點名；**Medium**＝發生 1 次且可逆、或直接降低每張 PR 固定成本；**Low**＝純效率、盲區補強、無事故（巡檢／cron 已能列出者一律 Low）。
- **入口收斂**：merge-reviewer／visual-reviewer／qa 的 informational、盲區補強、純效率建議，**預設處置＝在常駐票「Harness 待辦池」（LS-96）`save_comment` 一則**（格式：`來源 PR #n／LS-m Ix · 一句描述 · 觸發事故（有／無）· 估 size`），handoff 寫「記入待辦池 LS-96」；只有滿足 High 以上條件才開獨立票。待辦池 priority 為空、永不 Done、永不進 cycle、永不派工。
- **每 cycle 規劃時重排一次**（Cycle 規劃 Document，使用者核可）；Cycle 1 只收 Urgent／High 三張（LS-91／83／88）；LS-78（High，時限型）blockedBy M6，到期由 cycle 對帳補入。
- **反饋**：巡檢結構檢查（§4-b 模板第 5 步 (e)）列出 `lane:harness` 缺 `size:*` 的票；補位（第 4 步）只取 priority 最高、同級 size 最小，且跳過 LS-96；§7 對照列。盲區：分級仍是人判（orchestrator 開票時填），但每張票的「觸發事故」欄讓判斷可稽核。
- **機械面**：`scripts/ops/patrol.sh` 本身無 Linear token；lane 補位候補的計算自 LS-103 起由 `scripts/ops/patrol-linear.sh` 用 `.env` 的 `LINEAR_API_KEY` 直接打 GraphQL 算出（不經 MCP），印出 `→ save_issue …` 動作清單，orchestrator 只需執行（步驟寫在 §4-b cron 模板）；缺 token 時退回 orchestrator 用 MCP（`list_issue_labels`＋`list_issues`＋`get_issue`＋`save_issue`）手動執行同一套規則。CI／pre-push 不驗（自測見 §7 對應列）。`lane:design` 的 wip 計算另納入上方「例外」的 Pen 訊號判定（F2，LS-103）。

## 5-c. Cycle（LS-79）

使用者 2026-08-25 詢問「Linear 能不能加 Sprint」→ 已在 Team Settings 開啟 Cycles（1 週、無 cooldown，自動把 active 票加進當前 cycle）。**Cycle 回答「這週要達成什麼」（方向盤，使用者每週唯一固定決策點）；§5-b 的 lane 規則回答「下一張做什麼」（引擎）**。Cycle 為主軸：lane 補位只從當前 cycle 取票——規則本文見上方 §5-b「Backlog→Ready 機械規則」，機械面見 `lane_candidates()`（`scripts/ops/patrol_linear.py:363-378`），不在本節重複第二份副本。

- **F1 週期**：Cycle＝1 週、無 cooldown（Linear Team Settings 已開）。「規劃 cycle」＝當前 active cycle；無 active cycle（交接空檔）時＝最早的 upcoming cycle（`pick_current_cycle()`，`scripts/ops/patrol_linear.py:468-478`）。
- **F2 規劃**（使用者每週唯一固定決策點）：cycle 開始當天首次巡檢，orchestrator 依 milestone 順序＋各 lane 上限×可用天數估算（含上一 cycle 滾入票）產出提案，以 `save_document`（**須同時掛 `cycle`＝當前 cycle**，不只掛 project「Phase 1」；標題「Cycle N 規劃」）貼出並在晨報同步；使用者回「同意」或調整一次即核可。**核可前**orchestrator 只可把「滾入票＋在飛票」放進 cycle，不得預先塞入尚未核可的新範圍——scope 若要在核可前擴大，只能走下面 F3／§5-b 的「cycle 外補位＋scope+」路徑，會在動作清單留痕。**為何必須掛 cycle**（R1 merge-review 實測發現）：下面 G3 (c) 的存在性檢查走 `DOCUMENTS_QUERY` ＝ `documents(filter: { cycle: { id: { eq: $cycleId } } })`（`scripts/ops/patrol_linear.py:89-91`），只看得到掛在 cycle 上的 Document——只掛 project 的文件 (c) 永遠查不到，會誤判「未規劃」而重複建立（Cycle 1 已實際發生：2026-08-25 建的規劃文件只掛 project，含使用者核可記錄；(c) 數天後仍誤報，8/31 又補建一份只掛 cycle、不含核可記錄的重複文件）。**F5「同一份 Document」現在明確指「掛 cycle 的那一份」**；Cycle 1 這兩份重複文件的資料合併（把核可記錄搬到掛 cycle 的那份、封存另一份）留給 orchestrator 手動執行，不在程式碼 PR 內動 Linear 資料。
- **F3 派工來源只取當前 cycle**：見上方 §5-b「Backlog→Ready 機械規則」——該 lane 在 cycle 內無票時取 cycle 外最高優先並**加入當前 cycle**（scope+，在 cycle 圖可見）＋巡檢紀錄一行。
- **F4 臨時票即時入列**：事故 harness、review 衍生小票等不必等規劃——**開票（`save_issue`）當下即帶 `cycle`＝當前 cycle**；仍是 Backlog 狀態的臨時票不受下面 G1 限制（Backlog 不要求 cycle），但建議一併帶上，規劃時才看得到。
- **F5 結束與回顧**：cycle 結束時未完成的票由 Linear 自動滾入下一個 cycle（Linear 原生行為，不需機械介入）；結束後首次巡檢，orchestrator 在同一份「Cycle N 規劃」Document 貼「Cycle N 回顧」段（完成／滾入／scope 變化／本週各票 retro 改善項彙整）；晨報自此改為 cycle 週報格式（規劃段＋回顧段同一份文件，避免文件四散）。

**反饋（機械）**：
- **G1**：PreToolUse hook `scripts/gates/linear-issue-check.sh` 規則 E（與 LS-77 規則 A-D 同一支腳本）——**R1 merge-review 混合案**（PR #216 comment `7377158a`，orchestrator 拍板；票文原字面是「`Ready`／`In Progress` 且未帶 cycle、建票與更新票皆驗」，此處記錄有實證依據的偏離）：
  - `state` 設為 `Ready` 且未帶 `cycle`（含空字串／JSON 數字 `0`／純空白字串）→ deny，**建票與更新票皆套用**——`Ready` 是 unstarted，下方 G2（Linear「active 票自動加入當前 cycle」）不涵蓋這個狀態，這裡是唯一防線。
  - `state` 設為 `In Progress` 且未帶 `cycle` → deny，**只在建票時套用**；更新既有票改成 `In Progress` 不驗。理由：R1 merge-review 把 594 筆歷史 `save_issue` 呼叫逐筆餵進規則回放，`state ∈ {Ready, In Progress}` 且未帶 cycle 有 82 筆會被誤攔，其中 61 筆是「更新票改 `In Progress`」這個 orchestrator 日常派工形狀（`{"id":"LS-n","state":"In Progress"}`）；這個形狀沒有違反實質不變量——決定性反例 LS-112：建票 `state=Backlog` 無 cycle，之後全部 `save_issue` 只有 `{id, state}` 兩個鍵（從未傳過 cycle），但 `cycleId` 始終正確，證明 G2（Linear Team Settings 自動把 active 票加進當前 cycle）對 `started` 狀態確實生效，加上下面 G3 (a) 每 26 分鐘兜底已守住不變量——這條分支的邊際效益趨近於零，代價是每次派工被擋一次 round-trip。
  - `Backlog`／`Done`／其他狀態不要求 cycle（F4 的臨時票允許先落 Backlog、規劃時再排入）。
  - deny reason 教可執行修法（用 `list_cycles` 或巡檢輸出的「current cycle：N」查**當前** cycle 編號），不暗示照抄字面數字——歷史流量 60 筆都是字面 `cycle:"1"`，換 cycle 後沿用這個字面值會把在飛票寫進已結束的 cycle，這正是本規則要防的事，不能自己先犯。
  - 規則排在「更新票一律放行」（LS-77）之前判斷；`cycle` 正規化（`0`／純空白視同未帶）與 `id` 型別防呆（見上一列 LS-77 那列）皆已收在同一支腳本。自測見 §7 對應列。
- **G3**（既有，LS-103）：巡檢 `cycle_reconciliation()`（`scripts/ops/patrol_linear.py:481-508`）每輪對帳四類：(a) active 票（Ready／In Progress／In Review／QA／Design／Spec）不在當前 cycle → 列出並印 `save_issue cycle=` 補加動作（**Linear UI 手動建票／改狀態繞過 G1 hook 的盲區由此兜底，也是「更新票改 In Progress 不驗 cycle」這個刻意接受的缺口的最終防線**）；(b) cycle 內 **Backlog／Spec** 票 blockedBy 未解 → 列「規劃錯誤」；(c) cycle 進入第 2 天仍無「Cycle N 規劃」Document → 列「未規劃」並印建立動作；(d) cycle 剩餘 <24 小時 → 提醒準備回顧／規劃下一輪。任一非空即列出，不得回「無異常」。

**盲區**：MCP 無建立／調整 cycle 的工具（`list_cycles`／`list_documents` 唯讀；cycle 起訖日期只能在 Linear UI 手動調整，或依賴 Team Settings 的自動週期，本專案目前用後者）；Cycle 規劃／回顧 Document 的核可真實性完全靠使用者本人回覆，機械只能提醒「未規劃」「剩 <24h」，驗不到規劃內容品質（milestone 順序／lane 上限估算是否合理）或核可是否真的發生——§7 對應列。

## 6. 補充規定

- **Hotfix**：`hotfix/*` 從 `main` 切出、PR 回 `main`（CI＋review 照跑、QA 走快速通道），合併後**只補一支 back-merge `main`→`development`**（`gh pr create --head main --base development`；LS-85 起唯一保留的 back-merge），**一律「Create a merge commit」併入**（squash／rebase 會讓 `main ⊂ development` 永久不成立、promote 的 FF 檢查從此失敗），`test` 不補——下次 `promote.sh development test` 帶到。
- **Release**：`bash scripts/ops/promote.sh test main`（FF push；前提＝test tip 的 `qa` status success，LS-87）後打 tag `vX.Y.Z`（semver），TestFlight 上傳由 orchestrator 執行並在對應 ticket 記錄 build 號。
- **DB migration gate**：`supabase/migrations` 的變更必附 RLS 測試（CI 強制）；**破壞性 migration（DROP、縮欄、改型）需使用者本人核可**——核可方式：使用者本人在 PR 對話串（Conversation）留一則 comment、內容獨佔一行 `DESTRUCTIVE-APPROVED`（**建議**，LS-123；gate 只讀 issue comments——review 行內留言與 review body 不在來源內）；寫在 PR body 仍接受（向後相容）。**標記須獨佔一行**（允許前後空白／CRLF；同行不得有其他字，粗體／反引號包起也不算。反過來，gate 只看 raw 文字的行：藏在多行 HTML 註解 `<!-- … -->` 或 fenced code block 內的獨佔行仍會放行，rendered 看不見——標記不保證肉眼可見，審查請看 raw——LS-45）。comment 來源只認 `user.login`＝repo owner（`github.repository_owner`）的 issue comment（`scripts/gates/approval-comment-check.sh` 抓、逐則送同一支整行錨定 gate，`gh` 失敗 fail closed），agent 不得代寫、不得刪／改使用者留言；`gh pr edit --body-file` 整份覆寫 body 不再洗掉核可（來源：LS-121 PR #218——使用者 02:41Z 在 body 蓋章、ios-dev R2 覆寫 body 洗掉、使用者 03:08Z 改留 comment 但當時 CI 只讀 body；使用者裁決「放 comment，建議未來也這樣做，這樣就不會被誤刪」）。body 標記加了 CI 不會自動重跑（`pull_request` 觸發不含 `edited`），需 close/reopen 或再 push（LS-37 實測；§3 的 PR body 票號檢查 LS-63 同坑）；comment 是 gate 執行時經 API 即時抓的，留了 comment 後 `gh run rerun <run-id> --failed` 重跑 `rules` 即可（rerun 重放的是事件 payload 裡的 body 快照，comment 不受影響）。**分級自 LS-53 起由 `scripts/gates/migration-breaking-check.sh` 做 statement 級判定**（單一 pass 剝 `--`／`/* */` 註解後以 `;` 切句，多行敘述、單一字面值的 `execute '…'` 動態 SQL 也認得；`||` 串接拆開多字關鍵字認不得——已知限制，靠 merge-reviewer；規則表在檔頭）：**DESTRUCTIVE**（任何 DROP／TRUNCATE／DISABLE RLS／ALTER COLUMN TYPE，不留物件型別白名單讓人換寫法）→ 上述本人核可；**BREAKING**（ALTER POLICY 不分收緊放寬、CREATE POLICY … AS RESTRICTIVE、REVOKE 收回 public／anon 以外角色、CREATE [OR REPLACE] FUNCTION／DROP FUNCTION 既有名稱、RENAME、SET SCHEMA）→ PR body 須有 **`BREAKING:` 段落**：`BREAKING:` 在行首、同一行寫受影響呼叫端／app 版本／遷移路徑摘要（`scripts/gates/breaking-section-check.sh` 行錨定；粗體／列點／引用前綴、只有標頭下一行才寫內容皆不算；細節可在下方列點），**且 `docs/API.md` 須在同 PR 有變更**（契約文件跟著改；既有 RPC 只改本體也算——在該條目補一行行為差異）。兩級以檔內所有命中取聯集，同一句也可同時命中兩級（LS-37 invites：DROP POLICY＋REVOKE authenticated ＝ 兩者都要；DROP FUNCTION 既有 RPC ＝ 兩者都要）。只從 public／anon 收回的 REVOKE 是新函式上鎖慣例、ALTER DEFAULT PRIVILEGES 只影響未來物件，皆不算。
- **Secrets**：金鑰一律不進 repo。Client 端用 gitignored 的 `Secrets.xcconfig`；CI 用 GitHub Secrets；`service_role` key 永不出現在 client 或 repo。
- **`design/` 素材尺寸政策（LS-74）**：LS-46 PR #104 review 一度誤判「`.pen` 逐輪快照」是體積負債，LS-72 PR #119 review 實測推翻——`.pen` 是純 JSON，git delta-pack 後每版增量極小（5 版 raw 6.98 MB → pack 0.15 MB）；真正吃掉 repo 體積、且刪除後仍永留封包歷史的是 `design/*.png` 這類不可 delta 的二進位大檔（單張 1–2.6 MB）。**政策**：設計稿內置入的照片 placeholder 用 ≤1024px（最長邊）JPEG（畫布顯示不需要 1536px 以上解析度）；字標／icon 素材保留 PNG 但同樣限制在合理尺寸（`.claude/agents/ui-designer.md`）。**機械面**：`design/` 下新增或修改的二進位檔 >500 KB 由 `scripts/gates/design-asset-size-check.sh` 擋（掛進 `commit-gate.sh` 的 pre-commit 鏈；CI `rules` job 以 `--base` 模式對 PR diff 兜底，同 LS-69 evidence-path-check 的 `--no-verify` 繞過防線）——判定二進位用 git 自己的 `--numstat` 二進位標記（NUL byte sniff／`.gitattributes` 覆寫）——這是便宜的代理指標，不等於 pack 端的 delta-pack 決策（merge-review R1 F2 實測；細節與已知盲區見 §7 對應列），不靠副檔名白名單，`.pen`／`design/evidence/*.json` 等文字檔天然不受限。**不重寫歷史、不轉換既有檔**——gate 只看這次 diff 新增／修改的路徑，既有未觸碰的 `design/*.png` 一律接受。**git-lfs（票文方案 1）緩議**：涉配額／clone／CI 摩擦，單人專案現階段收益不足；若日後素材量級改變再議，不在本票落地。
- **回滾**：正式站問題以 revert PR 處理——`revert-*` head 開向 `main`（GitHub Revert 按鈕產生；CI 方向矩陣對三條保護分支皆合法），併入後同 hotfix 只補一支 back-merge `main`→`development`，`test` 由下次 `promote.sh development test` 帶到（要讓 test 立刻同步回滾就馬上 promote）；保護分支禁止 force-push，`test`／`main` 不接受非 FF 推送（promote.sh／push-gate 客戶端擋、巡檢偵測漂移），所以回滾永遠是「往前加 revert commit」，不是把分支倒回去（LS-85）。
- **本機 Supabase 容器序列化（LS-70）**：本機 `supabase db reset`／`bash supabase/tests/run.sh`（及任何會動同一容器的指令）一律經 `bash scripts/ops/supabase-lock.sh -- <命令>`——所有 worktree 共用同一個容器（同 `project_id`／port），裸跑互踩（LS-57／LS-66：rc=137、"container is not running"、migration 忽有忽無）。lock＝`/tmp/supabase-lock-<project_id>` 目錄（`mkdir` 原子性，macOS 無 flock），holder 檔記 pid／worktree／branch／cmd／時間；等待逾時 15 分鐘 fail loud（exit 124）；持有者 pid 不存在自動回收（誤搬到別人剛建、holder 未落地的活鎖會搬回）；`run.sh` 未在 lock 內（以 `supabase-lock.sh --held` 的祖先判定為準，不信 `SUPABASE_LOCK_HELD` 環境變數）會自己經 lock 重跑；巡檢 `patrol.sh` 印持有者。等待逾時先看持有者是否還在跑，**不得 `rm -rf` 別人的 lock**。**migration 版本號**取 `date -u +%Y%m%d%H%M%S` 當下時間、不手填整點；push-gate 4b／CI Migration rules 以 `migration-version-check` 擋**本分支引入的** migration 在 tree 內重複、或與目標分支同版本不同檔名的撞號（目標分支自帶的撞號不擋——另開票在目標分支修，不要動本分支去補）。隔離方案（每 worktree 各自 `project_id`／port 的容器）另票評估。
- **雲端資料庫只透過 migration 變更**：schema／policy 變更一律走 `supabase/migrations`＋PR，**禁止用 Supabase MCP 或 dashboard 直接改正式專案**。機械面：`.mcp.json` 的 supabase MCP 以 `--read-only --project-ref` 鎖唯讀與專案（LS-43 起走 PAT/stdio，PAT 存 .env），需要寫入時由使用者本人臨時解鎖。**注意：PAT 是帳號層級、具完整寫入權的 Management API 憑證，唯讀鎖只在本機 client 端生效，且 Management API 路徑繞過 RLS——`.env` 的保管等級＝正式站的保管等級**。`project_ref` 視為公開資訊（本來就會出現在 app 的 API URL）。**已併入 target（development／main）的 migration 檔不可再 modified／renamed／deleted**——migration 是 append-only 帳本，已 apply 的內容被改會造成本機與正式站 drift；push-gate＋CI `rules` job 以 `scripts/gates/migration-immutable-check.sh --base <ref>` 擋（LS-80，§7），逃生口為 commit body 獨佔一行 `MIGRATION-REWRITE-APPROVED: LS-<n>`＋PR 上同樣獨佔一行的宣告——使用者本人的 PR comment（建議）或 PR body（LS-123，來源同上列 `DESTRUCTIVE-APPROVED` 的 comment 機制）（僅限尚未部署到正式站的檔，需人判斷）。
- **正式站 `supabase db push` 每次需使用者當次授權（LS-71）**：對正式專案執行 `supabase db push`（及任何會改雲端 schema／資料的 CLI 指令）每一次都要使用者本人**當次**口頭授權——不得沿用上一次的授權、不得寫進 permissions allow 清單、不得由 agent 代跑。auto-mode 的分類器會擋這類指令：被擋就停下回報使用者，**不改寫指令繞過**（拆 pipe、包進腳本、換工具都算繞）。schema 內容本身仍走上列「雲端資料庫只透過 migration 變更」（migration＋PR＋CI）；這條管的是「按下部署」那一步。
- **本機 Auth OTP 信件模板（LS-93）**：`supabase/config.toml` 的 `[auth.email.template.magic_link]` 指向 `supabase/templates/otp.html`，只讓本機 Inbucket 直接顯示明文 6 碼、QA 免走 Admin API；只影響本機 dev stack，正式站模板另由 Supabase dashboard 設定（LS-99 已做），彼此互不影響。
- **API 變更紀律（LS-41）**：契約的真身＝migrations＋錯誤碼＋RLS 行為，`docs/API.md` 是 iOS 端唯一可消費的契約文件——變更 RPC 簽章／表／錯誤碼／回傳形狀必須與 migration **同一 PR** 更新 API.md（gate：`api-contract-check`——本機 push-gate 文字解析 best-effort、CI `--catalog` 查活 DB 為權威；錯誤碼表 ↔ Swift `LSErrorCode` 的集合一致自 LS-54 起由 `error-codes-check` 對帳，但 migration 內 raise 的碼 ↔ 錯誤碼表、與 `RETURNS TABLE` 欄位仍無機械涵蓋，靠 merge-reviewer）。**UI 上線前可自由改**：某 RPC 尚無出貨的 iOS 呼叫端時，改簽章或語意不需相容層，doc＋tests 同 PR 動即可。**UI 首次上線後傾向 additive-only**：該 RPC 已有出貨 client 之後，變更以「新增」為原則（新參數帶 default、新語意開 `_v2`），不破壞既有簽章；確有必要的破壞性變更須在 PR body 以 `BREAKING:` 段落寫明受影響的 app 版本與遷移路徑，並在 API.md 該條目加相容性註記。「已上線」的判定依據＝API.md **§4 逐支 RPC 條目**標記 `shipped: <app 版本>`（**不得寫進 §9 機械對帳區塊**，那裡是逐行精確比對）；標記自 LS-25 TestFlight 起維護（補齊全部 RPC 的 `shipped:` 是 LS-25 的驗收條件之一），**fail-safe（逐條保守）**：LS-25 完成後，§4 條目**未標** `shipped:` 者一律視為已上線，確定未出貨者須顯式寫 `shipped: none`（漏標倒向「多做相容層」而非無聲放行；此形狀可機械化：檢查每個 §4 條目底下皆有 `shipped:` 行）；LS-25 之前全部 RPC 視為上線前。**此三條的機械涵蓋（LS-53 起）**：migration 被 `migration-breaking-check` 判 BREAKING 時，CI 驗 `BREAKING:` 行錨定段落＋`docs/API.md` 同 PR 變更（見上方 DB migration gate 條）；additive-only 本身、`shipped:` 標記、以及不經 migration 的破壞性變更（只改 API.md 語意、Swift 端）仍靠 merge-reviewer 與 orchestrator 人工把關；§7 對照表分列。
- **Checkpoint**：每張 ticket 完成，orchestrator 把 handoff 訊息留在 Linear ticket comment，讓狀態可還原、可交接。
- **Feature 收尾儀式**：「feature」的粒度由 orchestrator 判斷並記錄——單張 feature 票，或同批 promote 的票群共用一次。① dead-code-sweeper 巡檢（範圍＝該 feature 的累積 diff）；② orchestrator retro（lesson learning review）——固定檢視：各 gate 的攔截／漏接記錄、review 輪數與返工原因、agent 派工與 model 選擇是否恰當、需要補的工具或 MCP、規約與 gate script 的改善項。改善項一律開票（harness 票走 hotfix 流程），不留口頭。③ **清理**（LS-86；LS-141 修訂）：`bash scripts/ops/cleanup-merged.sh --dry-run LS-<n>` 看清單、確認後 `--apply`——移除該票已併入的 worktree 與本機分支（遠端 head 分支已由 `delete_branch_on_merge` 自動處理，見§2／§7）。dirty 只看 tracked 修改與未追蹤非 ignored 檔；gitignore 掉的產物（`Config/Secrets.xcconfig`、`supabase/.temp/`、`supabase/tests/evidence/`、`.claude/evidence/<票>/`）視為可丟，dry-run 會先印「將一併丟棄的 ignored 產物」清單——**看到 `.claude/evidence/` 在清單裡，先確認截圖已貼進 Linear／PR 再 `--apply`**，移掉就沒了。票 Canceled／Done 但 worktree 從未開工（tip＝base）：指名 `--apply LS-<n>` 時有 `LINEAR_API_KEY`（`source .env`）會自動查票狀態、completed／canceled 才清；沒 key 加 `--force-unstarted`。移除前腳本查 `pen-open.sh --status`：Pen 開著該 worktree 的 `.pen` 會拒刪並印處置（先 `bash scripts/ops/pen-open.sh <主 checkout>` 切回，有未落地變更先 `pen-land.sh`）；Pen 在跑但 `--status` 讀不到也拒（登入 pen CLI 或關掉 Pen 再跑），Pen 沒在跑或本機沒 pen CLI 才放行；不得改用手動 `git worktree remove --force` 繞過（LS-119 事故）。純 harness 票可免 dead-code 巡檢，retro／清理仍照做（retro 輕量版）。
- **模擬器驗不了的項目**（推播、Sign in with Apple 完整流程）：QA 標註「需實機驗證」，不得記為 PASS。
- **模擬器用完必關（LS-100）**：ios-dev／qa 任務結束（handoff 前）、push-gate 跑完 unit tests（成功或失敗皆算）後，都要 `xcrun simctl shutdown <UDID>` 關掉自己這次 boot 的每一台模擬器——機器空跑浪費資源，也會讓下一個 agent／patrol 誤判「已有人在用」。`demo-*` 名稱的模擬器（demo 環境的持久機）豁免，不要關。`scripts/ops/patrol.sh` 巡檢「Booted 模擬器」段（>1 台非 `demo-*` 同時 Booted 即標）只能事後發現，不是攔截；真正攔得住的只有 push-gate 自己這條路徑。
- **CI 成本**：public repo 的 Actions 免費，但仍只在 PR 與保護分支 push 觸發，勿加無謂矩陣。

## 7. 前饋↔反饋對照表（§0 的落地清單）

hook 隨分支內容走（舊分支可能沒有新 hook）、且可被 `--no-verify` 繞過，所以**本機 hook 只是快速回饋，CI `rules` job 才是強制層**——凡標「hook＋CI」者兩層皆有。

| 前饋規則 | 機械反饋 gate | 狀態 |
|---|---|---|
| 保護分支禁直接 commit；`test`／`main` 禁非 FF 推送、禁繞過 promote.sh（§2） | pre-commit hook（`commit-gate` 擋在 main／test／development 上 commit）＋GitHub branch protection（development 必須走 PR；test／main required checks 對推上去的 SHA 生效＋enforce_admins＋禁 force-push／刪除）；非 FF／繞過 promote.sh 由下列「晉升 FF」列的 push-gate 擋 | ✅ |
| 測試／lint 過了才能合併 | pre-push hook＋CI required checks（`ci`＋`lint`） | ✅ |
| commit message 格式 | commit-msg hook＋CI 逐筆驗工作分支 PR 的 commit（merge/revert/fixup 豁免；`git log base..HEAD --not origin/main origin/development origin/test` 排除已存在於任一保護分支的歷史 commit，避免未來保護分支上出現的不合規歷史 commit，經由 back-merge／跨分支 merge 帶進 feature 分支後被永久誤擋——LS-10） | ✅ hook＋CI |
