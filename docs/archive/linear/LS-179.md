## MAJOR-1 —— `suspended_at`／`suspended_reason` 四欄 client **讀得到**，與 migration 註解／API.md 兩處／§11 營運手冊的明文保證相反

**檔案:行號**
- `supabase/migrations/20260904212530_suspension_and_registrations.sql:87-92`：「client 讀不到這四欄（不在下面重新開放的欄位級 grant 清單裡）……**原本 `authenticated` 對 profiles／families 就已經是逐欄 grant**……新增欄位不主動出現在任何既有 grant 清單裡，天生就是不可讀不可寫，不需要額外一句 REVOKE。」
- `docs/API.md:178-180`（profiles）：「**client 完全讀不到、改不動**——這兩欄不在 `authenticated` 的任何 grant 清單裡」
- `docs/API.md:65`、`docs/API.md:200`（families）：同樣的「client 完全讀不到」
- `docs/API.md:2635`（§11 營運手冊）：`suspended_reason = '寫下原因（稽核用，client 讀不到）'`

**事實**：那句前提是錯的。`information_schema.role_table_grants` 實查——`authenticated` 對 `public.profiles` 是**表級** `INSERT, SELECT`、對 `public.families` 是**表級** `SELECT`（逐欄 grant 只用在 UPDATE 上）。表級 SELECT 自動涵蓋任何後來 `add column` 的新欄位。

**具體失敗情境（實測，非推論）**
```
-- 停權者以自己的 JWT 讀自己的 profile
select id, suspended_at, suspended_reason from public.profiles;
→ a0000000-…-0002 | t | 內部稽核：涉嫌違規，已通報
-- 家庭停權後，家庭建立者（本人未被個別停權）讀自己的家庭
select id, name, suspended_at, suspended_reason, storage_quota_bytes from public.families;
→ fa000000-…-0001 | A 家 | t | 內部稽核：家庭違規 | 5368709120
```
營運照 §11 把稽核原因（可能含檢舉／通報細節、第三方個資）寫進 `suspended_reason`，被停權者一支 `GET /rest/v1/profiles?select=suspended_reason` 就讀得到。

**不是權限升級**：自行解除已實測擋住（`update profiles set suspended_at=null` → `42501 permission denied for table profiles`，UPDATE 是逐欄 grant，沒給這兩欄）。

**建議修法**（擇一，但文件三處必須跟著訂正）
- (a) 把 `profiles`／`families` 的表級 SELECT 換成逐欄 grant：**注意 PostgreSQL 的欄位級 REVOKE 對已存在的表級 grant 無效**，必須 `revoke select on table … from authenticated` 之後逐欄 `grant select (…)`——這會動到既有讀取面，需要測試護航。
- (b) 接受旗標可讀，但把「稽核原因」搬到 client 讀不到的地方（例如 `private` schema 的稽核表），`suspended_reason` 只留給不敏感的分類值；同時改掉 migration:87-92、API.md:65／178／200／2635 的措辭。

**複驗方式**：`docker exec -i supabase_db_little-sprout psql -U postgres -d postgres -c "select table_name, privilege_type from information_schema.role_table_grants where table_schema='public' and table_name in ('profiles','families') and grantee='authenticated';"` → 修好後不應再看到表級 `SELECT`；行為面重跑上面兩句探針應回 0 列／NULL。
