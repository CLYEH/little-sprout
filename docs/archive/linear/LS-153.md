## Findings

### F1（major）帳號刪除（LS-143 情況 2）的 Storage 物件永遠不會被清除
`supabase/migrations/20260903110908_purge_expired.sql:279-305`（入列只發生在 `purge_expired()` 的 media DELETE 那句 CTE 裡）／對照 `20260903084231_delete_account.sql:198`（`delete from public.families … cascade`）

**失敗情境（本機實測，非推論）**：建一個家庭＋1 張 media（含 thumb）→ 以唯一成員身分呼叫 `delete_my_account()`（＝LS-143 情況 2）→
```
NOTICE: delete_my_account 後 media 列數=0（已 cascade 硬刪），purge_storage_queue 新增=0
NOTICE: 60 天後再跑 purge_expired，佇列新增仍為 0（media 列早已不存在，路徑無從回收）
```
`media` 列被 `families` cascade 直接硬刪，**繞過本票唯一的入列點**；列一消失，`storage_path`／`thumb_path` 就再也沒有任何地方記得，bucket 裡的原圖與縮圖成為永久孤兒，之後任何一次 `purge_expired()` 都救不回來。

這正是票文 §1「家庭整體刪除（LS-143 情況 2）同規則」要的東西，也是 LS-143 檔頭明文 handoff 出來的債（「實際清除批次是另一張票」＝本票）。PR body 規格分歧 1 只論證了「DB 列已經立即刪掉、比 30 天更嚴格」——**那句話對 DB 列成立，對 Storage 物件不成立**，而 LS-132 要公告的承諾涵蓋照片本身。單人家庭使用者刪帳號是這個 app 最常見的刪帳號情境，等於承諾主路徑整條落空。

**建議修法（可行性我實測過）**：把入列從 CTE 移到 `public.media` 的 statement-level `AFTER DELETE` trigger（`referencing old table as old_rows`，SECURITY DEFINER），`purge_expired()` 只留 `delete … where deleted_at < v_cutoff` 與計數。我在本機建了同形狀的探針 trigger 後刪除 families：
```
NOTICE: PROBE6：families cascade 刪除後，statement trigger 入列 2 條路徑
```
→ transition table 在 FK cascade 觸發的內部 DELETE 下可用，修法成立，而且順帶涵蓋未來任何新增的刪除路徑（既有 `media_storage_delete` 額度 trigger 本來就靠同一個機制）。

### F2（major）`profiles` 硬刪後帳號可被復活，且刪除請求標記一併消失
`20260903110908_purge_expired.sql:331-339`（`delete from public.profiles`）；支撐取捨的論述在檔頭 `:41-51`、`docs/API.md` §6 同段

migration 與 API.md 都把「刪 profiles 是安全的」建立在這句話上：*「既有帳號重新登入不會自動補回 profiles……這個孤兒帳號實務上會馬上撞到一連串失敗，等同被鎖住」*。這句話對 `profiles_auto_create_trigger`（只掛 `auth.users` INSERT）成立，但**對 app 實際的程式路徑不成立**：`LittleSprout/Services/Family/SupabaseFamilyAPIClient.swift:51-58` 的 `ensureProfileExists()` 在 `createFamily` 之前以 authenticated 身分 upsert `profiles`，而 `profiles_insert` policy（`20260822120200_rls_policies.sql:122`）就是 `id = auth.uid()`。

**失敗情境（實測）**：
```
NOTICE: P3：purge 後 profiles 列數=0（已清），auth.users 列數=1（仍在，email 等 PII 保留）
NOTICE: P3：authenticated 以同一個 uid 重新 INSERT profiles —— 成功（帳號復活）
NOTICE: P3：現在 profiles 列數=1，deletion_requested_at=NULL（刪除請求標記消失）
```
後果三層：
- (a) 已請求刪除的使用者用同一組 Apple／Google 身分再登入，第一次建立家庭就重生 profiles，帳號實質復活——App Store 5.1.1(v) 的「刪除帳號」語意不成立。
- (b) `deletion_requested_at` 是本票與 LS-151 之間**唯一的交接契約欄位**（LS-143 檔頭原話）。硬刪 profiles 等於把它抹掉：LS-151 落地後想用它做 RLS 拒寫、或想反查「哪些 `auth.users` 還沒被補刪」，被 purge 過的帳號會從清單裡永遠消失。風險欄自己提議的那條巡檢（`auth.users` 有、`profiles` 沒有、建立超過 31 天）也因此只能靠 `created_at` 猜，分不出「purge 過的刪帳號」與「單純還沒建 profile 的新帳號」。
- (c) `auth.users` 的 email／provider id（PII）留著沒人管。

### F4（minor）`profiles` 清除可能永久失敗，而且只留在 `purge_runs` 沒人看

### F1（major）Edge Function 毒丸隊頭阻塞：≥200 筆無法確認的佇列列 ⇒ Storage 清除**永久停擺**

`supabase/functions/purge-storage/index.ts:141-147`（未出現在 `data[]` 就記 failure、不 dequeue）＋ `:178`（`doneIds.length < queue.length` → `break`）＋ `:98-103`（`order by enqueued_at` `limit 200`）；可達來源在 `:157-171`

**失敗情境（本機 e2e 實跑，非推論）**——佇列放 200 筆「物件已不存在」的舊列（`enqueued_at` = 10 天前）＋ 2 筆真實上傳物件的新列：

```
佇列筆數：202
真實物件上傳後存在性：real1.jpg -> 200   real2.jpg -> 200
-- 呼叫 EF（第 1 次）--  processed= 0  failed= 200  HTTP= 207
  呼叫後佇列筆數：202
  真實物件是否仍在：real1.jpg -> 200   real2.jpg -> 200
-- 呼叫 EF（第 2 次，模擬隔天再跑）--  processed= 0  failed= 200  HTTP= 207
  真實物件是否仍在：real1.jpg -> 200   real2.jpg -> 200
```

對照組（把那 200 筆毒丸列刪掉，其餘完全不動，同一支函式同一次 serve）：

```
  佇列剩：2
  processed= 2  failed= 0  HTTP= 200
    real1.jpg -> 400   real2.jpg -> 400      ← 立刻被清掉
```

**機制**：無法確認的列永遠不會被 dequeue，`enqueued_at` 又不會改變 ⇒ 它們單調累積在佇列**最前面**；`order by enqueued_at limit 200` 每次只讀得到它們，`:178` 的中止條件讓迴圈在第一批就 break。毒丸滿 200 筆之後，後面**任何**列都再也讀不到——排在後面的照片實體永遠不會被刪除，而且每天回 `207 processed:0`，沒有任何東西會讀這個回應（`purge_runs` 只記 DB 端，完全不記 EF 結果）。

**怎麼會累積到 200 筆**：`:157-171` 自己就是最短路徑——`remove()` 已經成功刪掉整批 200 個物件之後，那句 `.delete().in("id", doneIds)` 若失敗（PostgREST／DB 暫時性錯誤、statement timeout、連線中斷），這 200 列全部原地留下；而它們指向的物件**已經不存在了**，之後每一次 `remove()` 都拿不到它們的 `name`，全部變成永久毒丸。**一次暫時性錯誤就剛好湊滿門檻。** 檔頭 `:19-26` 把這個情況評為「可接受的殘留成本——純粹浪費一次 API 呼叫、不造成任何資料錯誤」，這個評估是錯的：它不是浪費一次呼叫，是整條佇列從此不再前進。

**另外，不需要滿 200 筆就已經有傷**：`:178` 的條件是「整批全部確認完成」才續跑，所以**只要有 1 筆未確認**，每次 invocation 就只跑得完一批（≤200 筆），而不是 `MAX_BATCHES × BATCH_SIZE = 4000`——R1 F6 那個「一天只清得動 200 個物件」的容量問題在有毒丸時原封不動地回來了，而 R2 是把它當成已修在報。

**建議修法**（擇一）：
- (i) 給 `purge_storage_queue` 加重試計數／死信欄位（`attempts`／`last_error`／`next_attempt_at`），SELECT 時跳過已停放的列——毒丸不再佔住隊頭；或
- (ii) 把「確認」的粒度改對：R1 F5 真正要擋的是**整個 bucket 打不到**，那就每個 bucket 每次 invocation 用 `getBucket()`／`listBuckets()` 確認一次；bucket 存在時，「路徑沒出現在 `data[]`」語意上就是「物件已經不存在」＝這筆佇列的目的已達成，可以安全 dequeue。這樣既保留 R1 F5 的保護，也沒有毒丸。

attempts 11 -> 1024 分鐘

### F2（minor）`parked` 觀測查詢自己吞掉 error，失敗時報 `parked: 0`＝假的「一切正常」

`supabase/functions/purge-storage/index.ts:284-289`

```ts
const { count: parked } = await supabase
  .from("purge_storage_queue")
  .select("id", { count: "exact", head: true })
  .gte("attempts", MAX_ATTEMPTS);
console.log(`purge-storage: parked=${parked ?? 0}`);
```

`error` 沒有被解構、沒有進 `warnings`；PostgREST 回錯時 `count` 是 `null`，`parked ?? 0` 把它**變成 0**——回應與 log 都會說「沒有任何列停放」，HTTP 狀態也不受影響（`status` 只看 `failures`／`warnings`）。這正是 R3 minor 2 要消滅的那一類假陰性，只是換了個地方：**唯一的觀測出口失敗時，訊號會塌陷成「健康」而不是「不知道」**。

**誠實標註**：這是**確定的程式性質**（讀碼即可斷定，不是推測），但**觸發機率低**——要在同一次 invocation 裡「前面的 SELECT／DELETE 都成功、只有這一次 count 失敗」。我沒有注入 PostgREST 失敗去重現。

**修法**（一行）：`const { count: parked, error: parkedError } = …`，`parkedError` 時 `warnings.push(...)`，並讓 `parked` 帶 `null` 而不是 0（或直接沿用既有的 warning→207 機制）。
