### M1（major）`supabase/tests/109_reactions_block_filter.sql:233-272` — EXPLAIN 證據段量的是手抄的函式本體副本，對函式漂移完全免疫；且它自己的 FAIL 訊息宣稱抓得到的 mutation，實測抓不到

第 245-260 行把 `get_reaction_counts` 的函式本體 SQL 抄一份成 `v_stmt`，第 261 行 EXPLAIN 的是這份**副本**，不是 RPC 本身。第 266 行的 FAIL 訊息寫著「mutation：拿掉 WHERE 的 family_id/target_type/target_id 篩選會導致這裡紅」——**這句話是錯的**：我把 migration 的函式本體真的拿掉 `and r.target_id = any (p_target_ids)`（上面的 mutation C），109 連同 50_／60_／87_ 四個檔全綠，沒有任何一條測試會紅，而真實 RPC 已經退化成掃整個家庭的 reactions（rows 20→251、buffers 1075→5289；家庭愈大放大愈多）。

具體失敗情境：日後有人為了加欄位／改條件動 `get_reaction_counts` 本體（例如把 `target_id = any(...)` 改寫成別的形狀、或把 `blocked_pairs` 述詞挪走），只要沒同步改測試檔裡那份副本，`bash supabase/tests/run.sh` 與 CI `db` job 全綠通過，時間軸每頁 3 次 RPC 每次都掃全家庭反應——這正是這段效能證據存在的理由（`50_rls_plan_no_percall_subquery.sql` 的 get_reaction_counts 段自 LS-58 起就是為了防這件事）。
