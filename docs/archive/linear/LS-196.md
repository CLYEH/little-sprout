## Findings

### F1（**major**）鑑權測試殺不掉「prefix 比對」與「空 key 放行」兩種退化

`supabase/functions/_shared/keys.test.ts:102-108`、`:127-134`（負向案）；連帶 `supabase/functions/push-dispatch/handler.test.ts:767-778`

現行 19＋3 個測試的負向輸入全部是「跟正解完全無關的字串」（`"wrong-key"`／`"wrong-token"`／`"some-anon-key"`／`"short"`）。這類輸入無法區分「精確比對」和「前綴比對」，也沒有任何一案的 `SUPABASE_SECRET_KEYS` 帶空字串值——所以上表 M1／M3／M4 三支突變在 114 個測試全綠的情況下存活。

**具體失敗情境**：本票把 `purge-storage`／`push-dispatch` 的 `verify_jwt` 關成 `false`，這支 helper 從此是**唯一**守門、且兩支端點對公網直接可達。

- *prefix 退化*：日後有人把 `timingSafeEqual()` 換成自製比對、或誤用 `startsWith`／`includes`（這是很常見的「簡化」改法），CI 114 綠照過。攻擊者送 `apikey: s` 即取得 service-role 權限 → `purge-storage` 會依佇列刪 Storage 物件、`push-dispatch` 會 claim 並送出通知（`claim_notification_events()` 先標 `sent_at` 再處理，被 claim 掉的事件不會回滾，等於可被外人清空推播佇列）。
- *空 key 退化*：`keys.ts:74` 的 `v.length > 0` 與 `:112` 的 `if (apikey)` 是兩道互相冗餘的防線，任一被拿掉、而 `SUPABASE_SECRET_KEYS` 又含空值（輪替期很實際，例如 `{"default":"sb_secret_…","previous":""}`），則**完全不帶 `apikey` header** 的請求會被放行（`headers.get("apikey") ?? ""` 與空字串候選比對成功）。

現行程式碼本身是正確的，**沒有 live 漏洞**——這是「測試釘不住意圖」的問題（CLAUDE.md Rule 8）。之所以列 major 而非 minor：本票的驗收條件把這三支 mutation 列為必殺，且這是關掉平台守門後唯一的閘門，而修法只要 3 條 assertion：

1. `apikey` ＝ `NEW_DEFAULT.slice(0, 8)`（正解前綴）→ 期望 `false`
2. `Authorization: Bearer ${LEGACY.slice(0, 6)}`（正解前綴）→ 期望 `false`
3. `SUPABASE_SECRET_KEYS = '{"default":"sb_secret_x","previous":""}'`、**不帶** `apikey` header → 期望 `false`

（M2「JSON 壞掉 fail-open」已被 `keys.test.ts:167` 確實殺掉，這支不用補。）

### F2（minor）`docs/API.md:1902-1905` vault secret 名稱敘述與 LS-153 實況矛盾，會把部署步驟導向重演同一個 401

### N1（minor）`docs/API.md:1913-1922`、`:2652-2661` 兩段 `net.http_post` 範本漏了 `timeout_milliseconds`，比正式站現行 job 更差

R1 我看到範本沒設 `timeout_milliseconds` 時，假設「LS-153 既有 cron job 就是這個形狀」而沒有列 finding。**這個假設是錯的**——本輪為了查 vault 實況翻到 LS-153 comment `cac7d8c4`（2026-09-04 正式站部署紀錄），實際掛上去的 job 是：

```
timeout_milliseconds := 60000
```

而 `timeout_milliseconds` 在整份 `docs/API.md` 一次都沒出現（我 grep 過）。

**具體失敗情境**：orchestrator 執行票文第 7 點時，會 `cron.unschedule` 舊 job、照 §6 範本重建成 `apikey` 標頭版本。照抄範本就會把 `timeout_milliseconds := 60000` 一併丟掉、退回 `pg_net` 預設的 **5000 ms**。`purge-storage` 單次最多跑 20 批 × 200 筆＝4000 個 Storage 物件，正常量體下就可能超過 5 秒 → pg_net 在 5 秒後放棄、`net._http_response` 記 timeout，**EF 其實跑完了、清除也生效了，但呼叫端拿不到那個 `{"processed":…}` JSON**。而 LS-153 的解 hold 驗收條件正是「200 `processed`／`parked` JSON」——等於煙測又會「失敗」，而且失敗現象（拿不到成功回應）跟本票要修的 401 很容易被混為一談，排查成本高。`push-dispatch` 那段範本同理（每分鐘一次、要送 APNs，更容易超過 5 秒）。
