## 範圍

1. `scripts/gates/pr-body-check.sh`（本機＋CI 皆呼叫）加兩條規則，只掃 PR body：
   * (a) 任何含 `LS-96` 字樣的行（「記入 [LS-96](https://linear.app/little-sprout-app/issue/LS-96/harness-待辦池常駐-reviewer-informational盲區補強純效率項先記在這裡滿足-high-以上條件才升獨立票)」「入池」「待辦池」同義）必須帶 ≥8 位 hex 的 comment id 片段；缺 → exit 1 並印「記入 [LS-96](https://linear.app/little-sprout-app/issue/LS-96/harness-待辦池常駐-reviewer-informational盲區補強純效率項先記在這裡滿足-high-以上條件才升獨立票) 必附 comment id（先 save_comment 取 id 再寫）」。
   * (b) 任何以「已修」開頭或含「已修」的處置行必須帶 7–40 位 hex 的 commit SHA；缺 → exit 1。
   * 兩條都只對「處置／未完成／informational」語境行生效的話會太脆——直接全 body 掃，誤判時 agent 改寫措辭即可（handoff 說明取捨）。
2. CI（`rules` job 既有 pr-body-check 步驟）加反查：對 (a) 抓到的每個 id，用 `LINEAR_API_KEY`（secrets 已在 CI，查 `patrol-linear.sh` 用法）呼叫 Linear GraphQL `comment(id)` 確認存在且 `issue.identifier == LS-96`；對 (b) 的 SHA 確認 `git cat-file -e <sha>` 且在 PR commits 內（`git merge-base --is-ancestor <sha> HEAD`）。本機無 key 時跳過反查、只做格式（印「反查略過」）。
3. 自測 `pr-body-check.test.sh`（既有）補正負樣本：含 id／缺 id、含 SHA／缺 SHA、SHA 不在 PR 內（CI 模式）、同義詞「入池」。
4. `docs/COLLABORATION.md`：Handoff 格式段落補一句規則來源與 gate；§7 對照表加一列。派工 prompt 規則（memory）已有，本票只做 gate。

**minor 1 — 逐行都 fork 一次 grep，長 body 成本 3.5 秒**（`scripts/gates/pr-body-check.sh:112`）
`is_pool` 的 LS-96 整字比對對**每一行**都跑 `printf | grep -qE`（2 個子程序／行），即使該行根本沒有 `LS-96` 子字串；:111 的 `入池`／`待辦池` 判定則已經用零成本的 `case`。

**minor 2 — 純數字 token 可冒充 comment id，而 (a) 在 CI 目前只有格式這一關**（`scripts/gates/pr-body-check.sh:104`）
`hex_tokens` 只要求 `^[0-9a-f]{8,}$`，純十進位長數字（CI run id、時間戳）符合。
失敗情境（實跑確認）：body 寫 `- i1：記入 LS-96（見 CI run 33735096239）` → **exit 0 綠**，但這行沒有任何 comment id。因為 repo 尚無 `LINEAR_API_KEY`，(a) 在 CI 就只有格式這一關，這條就此漏過。（(b) 不受影響：`已修（build 20260903）` 雖過格式，CI 的 `--verify` git 反查照樣判紅——我也實跑過。）

**i1（informational）— 錯誤訊息沒說「小寫」**（`pr-body-check.sh:116`／`:127`）：規則只收小寫 hex（自測 ⑤a 有釘），但訊息寫「≥8 位 hex」「7–40 位 hex」。實跑 `已修 7C2FF80 Foo.swift:12` → 紅，訊息是「沒有 commit SHA」，貼大寫 SHA 的 agent 會鬼打牆。兩處各加「小寫」二字即可。
