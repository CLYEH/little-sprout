### F1（**major**）自測宣稱的負控不存在——「副檔名判定」這條 mutant 17 組全綠存活
`scripts/gates/design-asset-size-check.test.sh:3`

檔頭白紙黑字寫：

> 若判定退化成用副檔名猜二進位（**誤放行沒有 .png 副檔名的二進位**、或誤擋大型文字檔）…這裡會紅。

**實測不成立。** 我把 `design-asset-size-check.sh:95` 的內容判定換成純副檔名白名單：

```bash
case "$path" in *.png) ;; *) continue ;; esac
```

→ 自測 **17 組全綠 + 「✓ design-asset-size-check 自測通過」**。第二條同源 mutant（把 `-- design` pathspec 收窄成 `-- "design/*.png"`）同樣 17 組全綠存活。

**根因**：套件裡每一個二進位樣本的檔名都是 `*.png`（`small.png`／`big.png`／`existing-big.png`／`boundary.png`／`boundary2.png`／`multi-a.png`／`multi-b.png`／`violate.png`），每一個文字樣本都是 `.pen`／`.json`／`.txt`——**副檔名與內容在 17 組裡從未分歧**，所以「靠內容」與「靠副檔名」兩種實作對這份自測完全不可分辨。

**具體失敗情境**：這個 gate 的整套設計理由就是「不靠副檔名白名單」（`design-asset-size-check.sh:14-15`、§7 對照表）。今天行為是對的——我實測 `design/a4-disguised.json`（PNG bytes 存成 .json，600,008 bytes）→ 紅、`design/blob`（無副檔名，600,000 bytes）→ 紅。但這條性質**沒有被任何測試釘住**：日後有人為了效能加一條副檔名快篩、或「簡化」成白名單，CI 照樣全綠，`design/logo`（無副檔名）、`design/hero.webp`、偽裝成 `.json` 的圖檔就一路放行——正是這支 gate 存在的理由被靜默拆掉。這與 COLLABORATION 已記錄的 LS-95 R1 B1（harness 靜默失效卻全綠）同一 class。

**建議修法**（約 6 行）：補兩組——(a) `design/` 下 600 KB、副檔名非 `.png` 的二進位（`design/blob` 無副檔名，或 `design/asset.json` 內容為 PNG bytes）→ 期望紅；(b) 現有 ③ 已覆蓋另一半（大型文字放行）。這一組同時把 F1 的兩條 mutant 都殺掉（pathspec 收窄也會漏掉它）。

順帶：handoff／PR body／§7 宣稱的兩條 mutation（門檻反轉、二進位判定恆真）都屬「gate 整個失效」型 mutant，任何自測都抓得到；真正瞄準本 gate 設計性質的那條反而存活。§7 的「✅ hook＋CI（自測含 mutation 負控）」目前是高估。

### F2（minor）文字檔完全無上限，且腳本／§7 記錄的判準理由實測可證偽
`design-asset-size-check.sh:13`、`docs/COLLABORATION.md:250`

腳本第 13 行與 §7 對照表都寫：`--numstat` 的二進位標記「正是 git 決定『這個 blob 能不能 delta-pack』的同一套判準」。**兩個獨立實驗都推翻它**：

1. `--numstat` 的標記來自 `buffer_is_binary()`（**只看前 8000 bytes 有沒有 NUL**）與 `.gitattributes` 的 `diff`／`-diff` 屬性；pack 端的 delta 決策走的是 `delta` 屬性與 pack-objects 啟發式，兩者不是同一套。實證：我在 scratch repo 加一行 `.gitattributes`：`design/*.png diff`，一個 800 KB 隨機內容的 PNG numstat 變成 `3183 0`（文字）→ **gate 放行**；而那一行對 delta-pack 毫無影響。
2. 「文字＝可 delta＝不是負債」也不成立。三個 repo 各 5 版 600 KB、`gc --aggressive` 後：
   - 每版整批換內容的 base64 文字：raw 3000 KB → **pack 2344 KB（78%）**
   - 同尺寸二進位隨機（對照）：→ 3052 KB
   - 真的每版小改的大型文字：→ **124 KB（4%）**

   可不可 delta 取決於「版間內容是否相似」，不取決於 diff 的 binary 標記。

**實測放行的假陰性形狀**（皆 exit 0）：
- `design/a3-asset.svg` 666,752 bytes（SVG 內嵌 base64 PNG）
- `design/a2-embedded.json` 600,034 bytes（base64 內嵌）
- `design/b6.pdf` 621,027 bytes（第一個 NUL 在 offset 21,072 > 8000）——**且這是真實形狀**：我抽樣本機 12 個 >400 KB 的 PDF，其中 `Simulator.app/Contents/Resources/HomeTemplate.pdf`／`PlayPauseTemplate.pdf`（正是向量設計素材）第一個 NUL 在 45 KB 之後，git 一律當文字。
- `design/a1-sneaky.png` 608,000 bytes（前 8000 bytes 純文字、之後全 NUL）——構造樣本，真 PNG/JPEG 標頭在前 16 bytes 內就有 NUL，不會誤放。

**但我要同時說清楚：這個「文字豁免」的決策本身，我獨立量測後認為是對的。** 對現行 repo 全歷史做 `--no-local --bare` clone 後量 `objectsize:disk`：

| | 版本／blob 數 | raw | pack | 比例 |
|---|---|---|---|---|
| `design/littlesprout.pen` | 86 | 138.13 MB | **0.83 MB** | 0.6%（~10 KB/版） |
| `design/*.png` | 9 | 14.41 MB | **14.11 MB** | 98.0% |

整包 `size-pack` 19.45 MiB，PNG 佔 72%。LS-72 的結論在 86 版之後依然成立，gate 的靶打對了。

所以 F2 是 minor 而非 major：**行為對、理由錯**。但 §7 是永久制度紀錄，LS-46 當初就是因為錯誤的體積歸因才生出這張票——記一條實測可證偽的技術結論進 §7 是同一個坑。**建議**：(a) 把腳本 13 行與 §7 那句「與 delta-pack 同一套判準」改成實話（「借用 git diff 的二進位啟發式：前 8000 bytes 有無 NUL／`.gitattributes` 覆寫」）；(b) §7 該列的「**盲區**」欄現在只列了 copy 偵測，把「文字檔完全無尺寸上限——base64 內嵌 SVG／JSON、前段長 ASCII 的向量 PDF 一律放行」補進去。要不要另加一條文字上限（例如 >2 MB 提醒）我認為可以留給 LS-96，不是本 PR 必做。

### F3（minor）`--base` 兜底對「PR 內先加後刪」的大檔無效
`design-asset-size-check.sh:72`

`base...HEAD` 是**樹比對**，不是逐 commit 掃描。實測：branch 上 commit A 加 `design/transient.png`（900,000 bytes）、commit B 刪掉 → `--base` **exit 0 綠**，而 `git rev-list --objects` 確認該 blob 仍永留分支歷史 1 筆。這打到票文自己指名的根因（「刪除後仍永留封包歷史」），而 CI 這層的存在理由正是本機 pre-commit 被 `--no-verify` 繞過時的兜底——一旦繞過，加了又刪的大檔就完全無人攔。

觸發需要先繞過 pre-commit（LS-88 的 PreToolUse hook 另有攔阻），且 LS-69 `evidence-path-check --base` 是同一形狀、屬既有一致設計，故不列 major。**建議**：§7 盲區欄補一句，或改用 `git log --diff-filter=A base..HEAD` 逐 commit 掃（後者成本較高，可留 LS-96）。

## 四維度逐項

**1. Race condition**：無 finding。純 bash、無共享狀態；`mktemp` 清單檔各行程獨立、`trap ... EXIT` 正確；`while read < "$list"`（不是 pipe）讓迴圈內的 `exit 2` 真的中止本行程，沒有踩 subshell 吞 exit 的坑。`commit-gate.sh:5` 是 `set -euo pipefail`，gate 的 exit 1／2 會確實中止整個 pre-commit 鏈。

**2. 運算效能**：無 finding。實測對真實 2 MB `.pen` 的變更：`git diff --numstat` 16 ms、整支 gate `--base` 模式 58 ms。逐檔 `git cat-file -s` 只對 binary-marked 檔跑（一般 0–2 個），不值得改 `--batch-check`。
