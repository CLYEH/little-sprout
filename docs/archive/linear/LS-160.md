**N1 · minor · `LittleSproutTests/AppSectionTests.swift:113-127`（`findNameAvailabilityPlist()`）——用掃描＋字典序猜 runtime，但測試行程手上就有正解**

測試跑在模擬器裡，`SIMULATOR_ROOT`／`IPHONE_SIMULATOR_ROOT` 環境變數直接就是**當下這個 runtime 的 RuntimeRoot**。我在模擬器內實測：
```
PROBE SIMULATOR_ROOT=/Library/Developer/CoreSimulator/Volumes/iOS_23A8464/Library/Developer/CoreSimulator/Profiles/Runtimes/iOS 26.0.simruntime/Contents/Resources/RuntimeRoot
PROBE viaSIMULATOR_ROOT exists=true   ← $SIMULATOR_ROOT + /System/Library/PrivateFrameworks/SFSymbols.framework/CoreGlyphs.bundle/name_availability.plist
```
具體失敗情境：
1. **驗的表 ≠ 跑的 runtime（今天就在發生）**：這台專屬機跑的是 iOS **26.0**（`iOS_23A8464`），但 `found.sorted { $0.path > $1.path }.first` 選中的是 **26.5** 的表（字典序 `iOS_23F77` > `iOS_23A8464`）。今天無害（版本表是累積性的），但斷言的依據跟實際 runtime 不是同一份。
2. **字典序不是版本序**：build 字串（`23A8464`／`23F77`）的字典序只是碰巧與版本同向。哪天選中較舊的表、而某個符號是更新的 year 才引入 → 查不到 → `XCTFail` 假紅。
3. **環境佈局改變 → 全 PR 一起紅**：Apple／GitHub 改 cryptex 掛載路徑時，這條 required check 會紅在與程式碼無關的變動上。

建議：先讀 `ProcessInfo.processInfo.environment["SIMULATOR_ROOT"]`（找不到再退回現行掃描）——順便消滅 1 與 2。**列 minor 不擋**：所有失敗模式都是 loud（不會靜默放行），且 CI 今天實證綠。

**N2 · minor · `AppSectionTests.swift:88-92` 註解的事實有誤，且擋掉了可機械化的單一來源**

註解寫「`IPHONEOS_DEPLOYMENT_TARGET` 只落在編譯產物 Mach-O 的 LC_BUILD_VERSION load command，不會出現在 Info.plist 或任何執行期可讀的 Bundle 屬性裡」——**不成立**。build 出來的 `LittleSprout.app/Info.plist` 有 `MinimumOSVersion = 17.0`（PlistBuddy 讀出），我也在測試行程內實測：
```
PROBE bundleID=com.leoyeh.littlesprout
PROBE MinimumOSVersion=17.0
```
（unit test 由 app host，`Bundle.main` 就是 app bundle。）

具體失敗情境：deployment target **往下**調（例如為多支援一版舊 iPad 從 17.0 降到 16.0）而這個常數留在 17.0 → 測試變得比實際寬鬆，`stroller.fill`（16.1）照樣綠，iOS 16.0 裝置卻是空白圖示——**唯一的靜默方向**。往上調（17→18）則是假紅、會被發現。往下調罕見，故 minor。

建議：常數改讀 `Bundle.main.infoDictionary["MinimumOSVersion"]`（讀不到就 `XCTFail`，維持 fail loud），或至少把註解裡的錯誤事實刪掉——照現在的寫法，下一個想修的人會被這段註解說服「沒得讀」而放棄正解。
