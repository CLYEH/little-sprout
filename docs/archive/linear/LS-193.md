### M1（major）三分流在 `members` 尚未載回／載入失敗時靜默落到 04a——唯一成員看不到 04d「整個家庭一併刪除」警告
`LittleSprout/Features/Settings/DeleteAccountFlowView.swift:71-81`、`LittleSprout/Features/Settings/DeleteAccountStep.swift:52-70`、`LittleSprout/Services/Family/FamilyStore+Members.swift:145-147`

`classification` 直接讀 `familyStore.leaveFlowCase`，而 `leaveFlowCase` 對「`members` 為空」的處置是 `guard let myself = members.first(...) else { return .leave }` → `.leave` → `classifyDeleteAccountFlow` → `.generalMember`（04a）。`DeleteAccountFlowView` 完全沒有消費 `familyStore.membersState`，沒有 loading 態、沒有 failure 態——「還不知道」與「確定是一般成員」在畫面上是同一個結果。

**具體失敗情境**：使用者其實是家庭唯一成員。`SettingsView` 的 `.task` 打 `listMembers` 遇到一次暫時性失敗（或網路慢、使用者在回應到達前就點了「刪除帳號」）→ `members` 仍為 `[]` → 落 04a，畫面明白寫著「你會離開「陳家」，**其他家人跟他們的照片、日記完全不受影響**」（事實相反：整個家庭會被 cascade 硬刪）。使用者按「繼續刪除帳號」→ `step = .finalConfirm`，此後 `content` 只看 `step`、再也不看 `classification`（`DeleteAccountFlowView.swift:59`），**04d 警告從此不可能出現**。04e 打完確認詞送出，`delete_my_account()` 情況 2 成功執行、整個家庭連同所有照片／影片／日記永久刪除。04b（唯一 owner）誤判有伺服器 `LS050` 兜底會被導回 04b；**04d 這條沒有任何伺服器兜底**。

**實跑證據**（暫時加測試、跑完還原，工作樹已回乾淨）：
```
PROBE-RESULT: before=generalMember step=Optional(LittleSprout.DeleteAccountStep.finalConfirm(origin: …generalMember)) after=soleMember
```
（`makeModel(members: [])`：`myFamily` 有值、`ownerUserID` 有值、`members` 空 → 分流 `generalMember`；按下「繼續刪除帳號」順利進 04e；`members` 這時才載回來 → 分流才變 `soleMember`，但已經來不及。）

### M2（major）票文範圍 3「停權者亦可走完」未達成
實作 handoff 自報「停權使用者無法從 UI 走到刪除帳號」，並歸類為「不修（超出本票範圍）」。覆核屬實且成因確認：`docs/API.md` §5 `LS052` 列明訂停權者經 `private.family_ids()` 等四支集合函式收斂後 `families_select` 靜默回 0 列 → `FamilyStore.refreshMyFamily()`（`FamilyStore.swift:216-226`）把 `myFamily` 設成 `nil` 且 `lookupState = .success` → `AuthenticatedGate`（`RootView+AuthenticatedGate.swift:106-115`）導向 `ForkView`；`ForkView.swift` 只有「我有邀請碼」「我要自己建立家庭」兩顆鈕，**沒有設定、沒有登出、沒有刪除帳號入口**，兩顆鈕又都會被 `LS052`／`LS054` 擋。

這不是可以順手放掉的 informational：範圍 3 是本票明列的驗收項，且 LS-179 R2 特地為 `delete_my_account()` 做了 `private.enforce_deletion_bypass()` 豁免（API.md §4 原文「這正是被停權的人最可能需要的出路」），後端已付的代價在 client 端被整條封死，App Store 5.1.1(v) 的合規保證因此不成立。修法可能落在 `RootView`／`ForkView`（不在本票檔案清單內）——請 orchestrator 二擇一，不接受「靜默不做」：(a) 本票補一條「停權／無家庭但已登入」也能到達刪除帳號的路徑；(b) 另開票並**明文修訂 LS-193 範圍 3**，把該驗收項移轉過去、LS-193 才可進 QA。

### M3（major，PLAUSIBLE——由程式碼＋API.md 契約推導，未做端到端重現）RPC 成功但 EF 失敗後若流程中斷，帳號進入無法恢復的死路
`LittleSprout/Features/Settings/DeleteAccountFlowModel.swift:34`（`deletionRequested` 只活在這個 model 實例裡）、`LittleSprout/Features/Settings/DeleteAccountFlowView+Status.swift:117-122`（重試只在 04h 這張畫面上）。

**具體失敗情境**：04e 送出 → `delete_my_account()` 成功（`profiles.deletion_requested_at` 已寫入、家庭已刪或已退出）→ `finalizeAccountDeletion()` 失敗（EF `500`／`503`，或 handoff 自己實測到的「本機無 edge runtime」同型的服務不可達）→ 04h。此時 app 被系統回收／使用者強制關閉。重啟後：`ownerUserID` 不跨啟動保存 → `syncOwner` → `refreshMyFamily()` 回 `nil` → `ForkView`。而 `docs/API.md` §「Edge Functions／`delete-account`」明訂「沒有呼叫本端點，帳號不會被刪除（也不會有排程自動補做）」，`LS051` 又把 `families`／`join_requests` 的 INSERT 全擋——使用者卡在三岔路，兩顆鈕都失敗、沒有登出、也沒有任何路徑回到刪除流程重打 EF。帳號永久停在半刪除狀態。

### n1（minor，PLAUSIBLE）`finalizeAccountDeletion()` 仍有**兩個**呼叫端，一般流程沒有被納入 resumer 的去重

### n1（minor→已修，`3c115d0`）✅ 這次「唯一擁有者」是真的

`grep -rn "finalizeAccountDeletion()" LittleSprout`（排除協定宣告／註解／Preview 實作）在 head 只剩**一個**呼叫端：`PendingAccountDeletionResumer.swift:91`。`DeleteAccountFlowModel.swift:201-220` 改成 `await resumer.finalize(userID:)` 後把 `resumer.state` 投影成 `manualStep`；`PendingAccountDeletion.clear` 的呼叫端也只剩 resumer 一處（`:92`）。

**task coalescing 正確性（逐點推導）**：
- `task(for:)`（`:84-101`）是 `@MainActor` 同步函式：`Task { }` 在 MainActor 上是**排程**不是就地執行，函式在 `inFlightTasks[userID] = task` 之前沒有任何 suspension point，因此不可能出現「Task body 先跑完、`defer` 先清掉字典、之後才把已完成的 task 塞回字典」這種殘留（那會讓後續呼叫 coalesce 到一個已結束的 Task、`await` 立刻返回而 EF 永遠不再打——這是這個寫法最容易踩的坑，這裡構造上避開了）。
- **字典清理**：`defer { inFlightTasks[userID] = nil }` 在 Task body 內、同樣 MainActor 隔離，成功與失敗兩條路都會執行。
- **失敗可重試**：catch 只設 `state = .failed`，字典項已由 defer 清掉 → 下一次 `retry`／`finalize` 會建立新 Task，不會被永久卡在 in-flight。
- **fire-and-forget 與 await 兩種呼叫端共用同一個 Task**：`resumeIfPending` 丟棄回傳值、`finalize` `await .value`，語意一致。
