## Findings

### F1（major）`LittleSprout/Services/Albums/AlbumDetailStore.swift:117`——`reflectUploadedMedia` 的 `generation += 1` 會整批丟棄飛行中的首載 `refresh()`

**失敗情境**（正是本票 1(b) 要修的那個情境）：使用者對相簿 A 一次上傳 3 張（`maxConcurrentUploads = 3`）、飛行中離開詳情頁再進來。`loadDetailStoreIfNeeded()`（`AlbumDetailView+Actions.swift:216-230`）建新 store → `subscribeDetailStore` → `await store.refresh()`。`refresh()` 要跑三次網路 await（`fetchAlbumMediaLinks`／`fetchMedia`／`signedURLs`）；只要任一張上傳在這個窗口內完成，`AlbumsStore.attachUploadedMedia`（`AlbumsStore.swift:217`）就會呼叫 `reflectUploadedMedia` → `generation += 1` → 首載 `refresh()` 的 `guard myGeneration == generation` 落空、**整份清單被丟棄**：`photos` 只剩剛插入的那 1 張，相簿既有的 N 張從照片牆消失，meta 列「N 張相片」跟著錯；`loadState` 停在 `.submitting`（`refresh()` 的守門 early-return 不收尾狀態，`photos` 非空時被 `photoGridOrEmptyState` 的 `default` 分支遮掉、使用者看不出來）。`AlbumDetailView` 沒有 `.refreshable`，另一個 `refresh()` 入口 `loadFailureState` 的「重新載入」只在 `photos.isEmpty && loadState == .failure` 才畫得出來——**畫面內沒有復原路徑**，只能退出再進一次。

**重放**（head，`AlbumDetailStoreTests` 內暫時加一支、gated stub，跑完已還原）：伺服器有 2 張既有照片，reflect 落在 refresh 窗口內 →
- head：`("[360BE9C3…]") is not equal to ("[F4BBFBBB…, 360BE9C3…, AD0F2F30…]")`、`("submitting") is not equal to ("success")`；
- 拿掉 `generation += 1`（＝併入前行為）：同一支測試得到 `photos == [既有 A, 既有 B]`、`loadState == .success`。

也就是說這個修法把「只丟失剛上傳的那 1 張、下次進來就看得到」換成「丟失相簿既有全部照片＋載入狀態卡住」——**同一條時序下失敗模式嚴格變壞**，而且發生的窗口正是 1(b) 的主場景。

現有測試 `LittleSproutTests/AlbumDetailStoreTests.swift:191` `test_reflectUploadedMedia_notClobberedByStaleInFlightRefresh` 起手 store 是空的、只斷言 `photos == [newMediaID]`，所以看不到這個損失（Rule 8：它把「整批丟棄 refresh」寫成了正確行為）。

**建議修法**：改用票文 1(c) 的另一個選項「以 id 去重合併」——不要動 `generation`，改成記下「本世代 refresh 飛行期間 reflect 插入過的 id」，`refresh()` 收尾時把不在 `newPhotos` 裡的那幾筆合併回最前面（union by id）；或保留守門但在世代不符時改成合併而非 `return false`，並且不論哪條路徑都讓 `loadState` 落在終態。測試補上「既有照片仍在」與 `loadState` 的斷言。

### F2（minor）`LittleSprout/Services/Albums/AlbumsStore.swift:230-258`——single-flight 查詢失敗會一次打掉整批

`.pending` 的 `Task` 失敗時，**所有共用它的等待者一起 throw**；`attachUploadedMedia` 的 `catch { return }` 是靜默 best-effort，於是一次暫時性網路失敗會讓同批最多 3 張照片都跳過 `attachMedia`——`media` 列已建好卻沒有 `album_media` 連結（使用者看不到、且會落進 LS-222／LS-223 的 orphan 清理範圍）。改動前每張各自查一次，同一個失敗只會弄丟 1 張。`catch` 已經清掉 `.pending`（256-258 行），所以等待者原地重試一次就能修掉放大效應（或以本地基底退化處理）。

### F3（minor）`LittleSprout/Services/Albums/AlbumsStore.swift:232`——`.ready` cursor 整個 session 不失效

cursor 只在 `reset()`（登出）清除。情境：10:00 本機加一張（cursor → next=5）；其間別的裝置加了 2 張（sort_order 5、6）；14:00 同一個 app session 再加一張 → 拿到 5，跟別台的 5 撞號；舊版現查 `links.count` 會得到 7、不會撞。handoff 記的限制是「多裝置**同時**加照片仍可能撞號」，但這裡是**時間上分開**的兩次上傳也會撞，屬本次改動新引入的一段。影響只到排序（`refresh()` 的 mediaId tie-break 讓結果仍是確定性的，但新照片可能不排最前），故列 minor。建議：cursor 綁「一批上傳」而非整個 session（批次抽乾後丟掉），或 detail store refresh 觀察到更大的 max 時失效。
