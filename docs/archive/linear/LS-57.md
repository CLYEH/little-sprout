## 需使用者決策

1. owner 移除是否應為**不可被作者撤銷**？（建議：是——記錄 `deleted_by`；作者只能清除自己設下的 `deleted_at`；owner 設的只有 owner 能還原。）
2. 若是，實作面：三表加 `deleted_by uuid`，RPC 寫入，作者還原路徑檢查 `deleted_by = auth.uid()`；API.md §3 明寫。與 [LS-23](https://linear.app/little-sprout-app/issue/LS-23/story檢舉封鎖額度-uieula)（檢舉/封鎖/移除 UI）合併設計較省。
3. 附帶（F6）：`LS020/023/024` 在授權檢查前丟出 → 已登入者可跨家庭辨識 UUID 存在性（UUIDv4 不可枚舉，低風險）——是否統一改為先授權再查存在（全域慣例票）。

未決前 API.md §3 先明寫現況「owner 軟刪可被作者還原」（[LS-52](https://linear.app/little-sprout-app/issue/LS-52/db-安全albums-updatecomments-update-owner-分支不限欄位-owner-可改寫他人相簿標題與留言內文) 已要求）。

## 追加（PR #70 R2 N4）

* `albums`/`comments` 的 `family_id` 對作者可寫：同時屬於兩個家庭的人可把自建的相簿/留言整列搬到另一家（USING 比舊列、WITH CHECK 比新列兩邊都過）——這是 N1 跨家庭越權 race 的成立前提。建議：`family_id` 列為不可變欄（trigger 或 WITH CHECK `family_id = old`——RLS 看不到 OLD，需 trigger），與 deleted_by 同票處理。

### B1（blocker）刪帳號會被這支 trigger 打死
`supabase/migrations/20260825040000_deletion_attribution.sql:107-109`（`on delete set null`）與 `:157-158`（`else new.deleted_by := old.deleted_by`）互相打架。

profiles 被刪時，FK 的 RI 動作是 `update <table> set deleted_by = null where deleted_by = <id>`——這句 UPDATE **會觸發同一支 BEFORE UPDATE trigger**，走推導第三條（OLD/NEW 的 `deleted_at` 都非 NULL）把 RI 剛塞的 NULL 改回那個即將消失的 profile id，接著 FK 檢查炸 `23503`。

實測（同一個交易內，先有 trigger 再 drop trigger 對照）：

```
A) owner 移除後 deleted_by=...f1 (owner=...f1)
B) 作者被 LS027 擋下（正常）
C0) >>> 有 trigger：owner 帳號刪除失敗 sqlstate=23503
     msg=insert or update on table "diaries" violates foreign key constraint "diaries_deleted_by_fkey"
C1) 移除 trigger 後：owner 帳號刪除成功（證明肇因是 enforce_deletion_attribution）
```

**具體失敗情境**：任何使用者只要名下有「目前仍是軟刪狀態、且 `deleted_by` 是他」的 diary／album／comment，他的帳號就刪不掉（先轉移 owner 也沒用，C0 那一步就是轉移後才刪的）。PLAN §9-A2／路線圖第 8 項把「app 內帳號刪除」列為 **MVP 必要**（App Store Guideline 5.1.1(v)）。三張表都中。

**為什麼現有測試看不到**：`supabase/tests/run.sh` 收尾是先 `delete from public.families`（cascade 掉三張表的內容列）再 `delete from auth.users`——順序剛好閃過，換個順序就會紅。88_ 三段全是 `begin; … rollback;`，也碰不到 RI。

**建議修法**（擇一）：
- (a) `deleted_by` 不掛 FK，只留 `uuid`：同時解掉 B3、也省掉 `:112-114` 那三支幾乎全 NULL 的反向索引（65_ gate 不接受 partial，所以有 FK 就一定得建全表索引）；API.md 註明「可能指向已刪除的 profile，join 用 left join」。
- (b) 保留 FK，trigger 對「`old.deleted_by` 非 NULL、`new.deleted_by` 為 NULL、`deleted_at` 完全沒動」這個 RI set-null 特徵放行。
兩種都請在 `88_deletion_attribution.sql` 補一段「刪掉一個曾軟刪過內容的使用者帳號必須成功」的迴歸——這正是「新增重要規則＝同時新增它的 gate」。

### B2（應修，實質等同 blocker：本票的核心保證可被繞過）owner 後手移除拿不到歸屬
`…deletion_attribution.sql:155-158`。推導第三條「OLD／NEW 都非 NULL → 保留 OLD.deleted_by」是對稱的，檔頭 44-53 行只論證了「作者不能用重複軟刪把歸屬從 owner 洗成自己」，**反方向沒論證、也沒測**：owner 對「已被作者自刪」的內容再按一次移除，`deleted_by` 仍是作者，作者事後可自行還原。

實測：
```
STEP1 作者自刪後 deleted_by=...f2（author）
STEP2 owner 再次移除後 deleted_by=...f2（仍是 author，不是 owner）
STEP3 >>> 作者成功還原了 owner 移除過的日記（deleted_at=NULL）
```

**具體失敗情境**（兩條，第二條不需要 race）：
1. race：作者的自刪與 owner 的移除幾乎同時發出，作者那筆先 commit → owner 的移除在歸屬上是 no-op。
2. stale UI：owner 的列表還沒 refresh，作者剛把自己那篇自刪掉，owner 對它按「移除」——RPC 回 void、**沒有任何錯誤**，owner 合理相信已永久移除；作者稍後還原，內容重新出現在時間軸。

這正是票文「owner 移除必須是不可被作者撤銷」要堵的那件事。`88_` §1 只測了作者後手那個方向。

**建議修法**：推導第三條加一條 owner 升級分支——呼叫者是該家 owner 且 `old.deleted_by` 不是 owner 時，把 `deleted_by` 換成呼叫者（非 owner 呼叫者仍維持保留 OLD，B1 的偷歸屬防線不變）；或改記一個不會被還原／帳號刪除洗掉的 `removed_by_owner boolean`，一次解掉 B1/B2/B3。並在 88_ 補「作者先自刪 → owner 再移除 → 作者還原必須 LS027」。

### B3（應修）`on delete set null` 讓「deleted_by 保證非 NULL」這句話不成立
`…deletion_attribution.sql:77-78` 寫「新產生的每一筆刪除，從這支 migration 套用的那一刻起，deleted_by 保證非 NULL」——與 `:107-109` 的 `on delete set null` 直接矛盾。同一組實測（把 trigger 拿掉讓帳號刪得掉之後）：

```

D) >>> owner 帳號刪除後，作者成功還原了 owner 移除的日記
```

**失敗情境**：移除內容的 owner 轉移完 owner 身分、刪掉自己的帳號（MVP 支援的流程）→ 所有他移除過、仍在軟刪狀態的內容全部解鎖，原作者可自行還原。`docs/API.md` 三處「NULL＝本欄位新增之前就已軟刪除的既有資料」也因此不完整——migration 之後也會產生 NULL。採 B1(a) 的話這條自動消失；若堅持保留 FK，至少要把檔頭與 API.md 改成誠實描述，並讓使用者裁「刪除移除者帳號＝解鎖還原」可不可接受。

### B4（應修，**PLAUSIBLE**，未實跑）新併發場景的 mutation 證據我判斷不成立
`supabase/tests/concurrency/diary_delete_vs_restore_s2_author_restore.sql:16-20` 宣稱「拿掉 `set_diary_deleted` 的 `for update` → S2 不再被阻塞、也拿不到 LS027，兩條斷言與 verify 都會變紅」。我讀 Postgres 的行為判斷這不會發生：`ExecBRUpdateTriggers()` 內部的 `GetTupleForTrigger()` 會**先對目標列取 `LockTupleExclusive`、再觸發 BEFORE ROW trigger**，並在偵測到並發更新時走 EPQ 重取最新版本當 OLD。所以就算沒有 `for update`，S2 那句 `update … set deleted_at = null` 仍會在 trigger 取鎖階段被 S1 阻塞約 1.8 秒，trigger 仍會讀到 `old.deleted_by = owner` 而噴 LS027——`v_elapsed < 0.5` 與 `not v_ls027` 兩條斷言都不會變紅。

## N1（blocker，親跑）呼叫端可以指定 `deleted_by`——兩句 PATCH 就撤銷 owner 的移除

`supabase/migrations/20260825040000_deletion_attribution.sql:246-249`

```sql

    return new;          -- ← 直接放行，NEW.deleted_by 原封不動寫進資料庫
  end if;
```
這條短路排在還原鎖之前，而且**沒有把 `new.deleted_by` 覆寫回 `old.deleted_by`**。`albums` 對 `authenticated` 是 table-level UPDATE grant（涵蓋 `deleted_by`），`albums_update` 的 WITH CHECK 只比 `created_by`／`family_id`——所以「只改 `deleted_by`、不碰 `deleted_at`」這句 UPDATE 一路暢通。

**具體失敗情境**（PostgREST 兩個請求＝兩個交易，不需要 race、不需要時序）：
1. owner 呼叫 `set_album_deleted(X, true)` → `deleted_by = owner`
2. 建立者 `PATCH /albums?id=eq.X` body `{"deleted_by": "<自己的 uuid>"}`
3. 建立者 `PATCH /albums?id=eq.X` body `{"deleted_at": null}` → 還原鎖比對 `old.deleted_by`（現在是自己）→ 放行

實測：
```
X0 owner 移除相簿                    deleted_by=...f1  is_deleted=t
X1 作者直接還原（對照）              被擋 sqlstate=LS027      ← 這條是 88_ 唯一測到的
X2 作者把 deleted_by 改成自己        >>> 放行
X2 後                                 deleted_by=...f2
X3 作者還原 owner 移除的相簿         >>> 成功（deleted_at=NULL）
```
**這正是本票要堵的那件事**：「owner 移除不可被作者撤銷」在 albums 上完全不成立。`docs/API.md:569-570`「呼叫端無法指定，也無法透過直接 `.update()` 繞過」、`:525`／`:615`、migration 三段欄位註解的同一句話都是錯的。（`diaries`／`comments` 沒有 UPDATE grant，只有 albums 中——但 albums 的 hybrid 路徑正是票文與 orchestrator 實作要點指名要堵的那條。）
