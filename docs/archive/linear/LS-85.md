## 描述

## 來源

使用者 2026-08-25 問「三分支間 merge 有必要每次開 PR／派 merge-reviewer 嗎」→ 同意本方案，並要求前饋／反饋都要有。帳：[LS-57](https://linear.app/little-sprout-app/issue/LS-57/產品決策owner-軟刪的內容可被作者直接還原diariesalbumscomments-系統性-是否記錄-deleted-by) 一張票花了 4 個 PR（#114 dev→test、#118 test→main、#121／#123 back-merge）、4 輪 CI、零人審——全為了讓分支保護放行；back-merge 純粹是 `--merge` 在 main 留 merge commit 造成。

## 原則

* merge-reviewer 不動（本來就只審 feature／fix／hotfix PR）。
* 三條分支永遠是祖先鏈（從不直接 commit 到 test／main）→ 晉升＝fast-forward push，不留 merge commit，back-merge 消失。
* hotfix 照舊走 PR 進 main（有內容、要審）；併入後只補**一支** back-merge main→development（PR），test 不補——下次 FF 帶到。
* Gate 不減、換位置：每個進到 test／main 的 SHA 都必須有四個綠 check（server-side），FF 與 check 由腳本＋hook 驗（client-side），漂移由巡檢偵測。

## 前饋（規約）

* F1 COLLABORATION §2 改寫：晉升流程＝`bash scripts/ops/promote.sh <from> <to>`（development→test、test→main）；禁止手動 `git push origin development:test`；hotfix 流程＝PR 進 main → `promote.sh`？不——hotfix 併入後 orchestrator 開 back-merge PR main→development（唯一保留的 back-merge），命名 `hotfix/LS-<n>-backmerge-development` 或直接 `gh pr create --head main --base development`。
* F2 CLAUDE.md「分支流向」一行同步：`feature|fix/* → development ⇒(FF) test ⇒(FF) main`；`hotfix/*` → main → back-merge development。
* F3 §4-b 巡檢模板：「QA 但 test 未含 → 晉升」改為呼叫 `promote.sh`；加「分支漂移」一步（見 G4）。
* F4 COLLABORATION §6 回滾段：revert PR 流程不變（revert 進 main 後 back-merge development 同 hotfix）。

## 反饋（機械）

* **G1 GitHub 分支保護（test／main）**：關閉「require pull request」、保留「require status checks to pass」（ci／db／lint／rules 四個 job 名）＋「block force pushes」＋「restrict who can push」（僅使用者帳號）。development 維持現狀（feature 仍走 PR）。用 `gh api -X PUT repos/CLYEH/little-sprout/branches/<b>/protection` 執行，**執行前後的 protection JSON 存成證據附 PR body**，§7 記錄指令。使用者 2026-08-25 已同意此變更。
* **G2 CI push 觸發**：`.github/workflows/ci.yml` `on.push.branches: [development, test, main]`（四 job 全跑），讓每個 SHA 都有 check；PR 觸發不變。晉升時 development tip 的 SHA 已有綠 check → 狀態檢查即刻滿足；若 check 尚未完成或紅，GitHub 拒收 push（server-side 硬 gate）。
* **G3** `scripts/ops/promote.sh <from> <to>`：(a) `git fetch`；(b) 方向只允許 development→test、test→main；(c) FF 檢查：`git merge-base --is-ancestor origin/<to> origin/<from>` 否則拒絕並指示「先 back-merge」；(d) `gh api repos/…/commits/<sha>/check-runs` 四 job 全 success 否則拒絕（印出缺哪個）；(e) `git push origin origin/<from>:<to>`（帶 `PROMOTE_VIA_SCRIPT=1` 給 push-gate）；(f) 印出 from／to／sha／check 摘要。正負自測 `promote.test.sh`（合成 repo＋stub `gh`：非 FF 拒、check 紅拒、check 缺拒、方向錯拒、正常放行；bash 3.2 `${name}`）。
* **G4 push-gate**：目標分支為 test／main 時，無 `PROMOTE_VIA_SCRIPT=1` 或非 FF → 擋（保護分支禁直接 commit 的既有規則改寫為「禁非 FF 推送、禁繞過 [promote.sh](<http://promote.sh>)」）。`--no-verify` 仍禁（G1/G2 在 server-side 兜底：沒有綠 check 的 SHA 推不上去）。
* **G5 巡檢漂移偵測**（[patrol.sh](<http://patrol.sh>) 三分支段）：`test ⊂ development`、`main ⊂ test` 皆須成立（is-ancestor）；不成立即印「⚠ 分支漂移：<b> 有 <n> commit 不在 <parent>」——hotfix 併入後 main 領先 development 屬預期，超過 40 分鐘未 back-merge 才警示；`patrol.test.sh` 加案例。
* **G6 §7 對照表**：三列——晉升 FF（前饋 §2；反饋 G1＋G3＋G4）、每 SHA 必有 check（前饋 §2；反饋 G2＋G1）、分支漂移（前饋 §2；反饋 G5）。盲區明寫：server-side 無法拒絕非 FF 推送（GitHub 無此規則、require-linear-history 會拒絕 development 自己的 PR merge commit），靠 G3/G4 client gate＋G5 偵測。

### Findings

**F1（minor｜race condition｜PLAUSIBLE）`scripts/ops/promote.sh:94`**
推送的 refspec 來源是 **ref 名稱**而非驗過的 SHA：
```
PROMOTE_VIA_SCRIPT=1 git push origin "refs/remotes/origin/${from}:refs/heads/${to}"
```
`refs/remotes/origin/<from>` 由 git 在 **push 當下**解析，不是 `$from_sha`。
失敗時序：promote.sh 通常在主 checkout 執行；`git rev-parse`（L53）到 `git push`（L94）之間夾著 `gh api` 往返（約 0.5–3s）。同一個 object store 上任何併發 `git fetch origin` 都會改寫 `refs/remotes/origin/development`——而這種 fetch 不只一處：`scripts/ops/patrol.sh:82`（cron 每 26 分鐘＋SessionStart hook）、以及 5 個 linked worktree 裡任何 agent 的 fetch（worktree 共用 `refs/remotes/*`）。窗口內 development 前進 → 推出去的是**沒被 promote.sh 驗過 check 的新 tip**，而收據 `✓ 已晉升 test → ${from_sha}` 印的是另一顆 SHA。
影響有界：新 SHA 若沒綠 check，GitHub required checks 會 GH006 拒收（→ exit 1，訊息「遠端在 fetch 之後又前進？」剛好也對），所以不是 gate 繞過，最壞是**假收據／多推了一段**。
建議（一個 token）：`git push origin "${from_sha}:refs/heads/${to}"`，並把 `${from_sha}` 印進 L93 那行；可選再加 push 後 `git ls-remote origin refs/heads/${to}` 對帳。**這是我最建議先修的一條。**
（標 PLAUSIBLE：窗口窄，我沒實際重現。）

**F2（minor｜scope）`scripts/gates/push-ref-check.sh:26-31`＋`scripts/gates/push-gate.sh:14-26`**
刪除分支／tag 早退是 **LS-87 的 scope**，不是 LS-85 的。LS-85 G4 只要求「目標分支為 test／main 時，無 `PROMOTE_VIA_SCRIPT=1` 或非 FF → 擋」；「push-gate 對分支刪除早退」逐字出現在 LS-87 標題。
減輕因素：註解明寫「LS-87 G4」（是揭露而非夾帶）、與 FF 檢查共用同一個 stdin parser（拆開會讓 LS-87 重寫同一個迴圈並製造衝突）、有自測 ①②③。

**F3（minor｜前饋缺口）`docs/COLLABORATION.md` §2／§6**
新的祖先鏈不變量依賴 back-merge PR 以 **merge commit** 併入，但 repo 同時開著 `allow_squash_merge=true`／`allow_rebase_merge=true`，文件沒有任何一句指定合併方式。
失敗情境：hotfix 併入 main → back-merge PR main→development 被 **squash** 併入 → development 只拿到 main 的**內容**、沒拿到 main 的 **commit**。`promote.sh development test` 仍會 FF（test ⊆ development），但 `promote.sh test main` 的 FF 檢查**永久失敗**（main 上那顆 hotfix merge commit 不是 test 的祖先），patrol 也會永遠標「main 有 n commit 不在 development」。要復原得重做一次真 merge。
fail-closed 且巡檢看得到，故列 minor。建議：§2／§6 各補一句「back-merge PR 一律 Create a merge commit，禁 squash／rebase」，§7 該列同步。

**F4（minor｜運算效能＋新失敗模式）`.github/workflows/ci.yml:12-13`**
`on.push.branches` 含 test／main → 同一顆 SHA 的 40 分鐘 macOS `ci` job 與 `db` job 每次 release 會多跑兩輪。
比成本更值得記的是它開了一個新的卡點：promote.sh 取**最新一筆 check-run**，所以 test 上那輪重跑若 flaky 紅了，`promote.sh test main` 就會拒——即使同一顆 SHA 有更早的一整組綠，而 test 又不能倒回去（禁 force push）。解法是重跑該 job（產生 id 更大的 check-run）即解封。**建議把這條復原步驟寫進 §2／§4-b**：因為當下的直覺反應（「它明明綠過」）就是去找繞過的方法。
註：票文 G2 白紙黑字寫三條分支，所以這不是偏離規格，只是後續可評估的最佳化（縮成 `[development]` 仍能滿足 test／main push 的 required checks——GitHub 看的是該 SHA 上已有的 check）。另開票即可。

**F5（minor｜gate 一致性｜PLAUSIBLE）`scripts/ops/promote.sh:76-77`**
client 端查 check-runs **沒有依 app 過濾**，而 `protection-apply.sh` 刻意把四個 required check 都釘在 `app_id 15368`。自測 fixture 甚至已經帶了 `"app":{"id":15368}` 欄位，腳本卻沒讀。
失敗情境：未來任何一個會產生同名 `ci`／`db`／`lint`／`rules` check-run 的 app（bot、可重用 action、狀態鏡像整合），只要 id 較大就能滿足——或誤擋——promote.sh，而 GitHub 端的規則根本不認它。此 repo 目前無這類 app，故標 PLAUSIBLE。
建議：`.check_runs | map(select(.app.id == 15368)) | sort_by(.id) | …`。

**F6（minor｜盲區未記）`scripts/gates/push-ref-check.sh:31`**

server 端 `allow_deletions=false` 會擋（線上兩條分支我都確認過），所以實際是安全的——但 §7 新增的三列沒提這件事。建議補一句：「刪除 test／main 由 GitHub `allow_deletions=false` 擋，客戶端不判」。
