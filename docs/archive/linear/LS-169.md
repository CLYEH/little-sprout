## Major

### M1 非 owner 成員換照片永久失敗，而且錯誤訊息把「權限不足」說成「伺服器問題，請稍後再試」

- **實跑證實**（本機 stack，lock hold 內；owner A＋member B(can_upload=true) 同一家庭）：
  - A 先上傳 `{fam}/avatars/{child}.jpg` → 200；B 覆蓋同路徑 → **400 `{"statusCode":"403","message":"new row violates row-level security policy"}`**。
  - 反向更糟：B 先上傳 `{fam}/avatars/{child2}.jpg` → 200；A(owner) 覆蓋 → 200，之後 `storage.objects.owner` 變成 A → **B 連自己原本上傳的那張都改不了了**（B re-upload own → 400）。
- 為什麼這**不是**「既有 Storage RLS 通用限制」（PR body 這樣寫）：既有 media 流程每次上傳都是新的 `{media_id}` 路徑，兩個成員永遠不會寫到同一個物件，這條 policy 分支在既有流程裡**不可達**；本票改用「每個孩子固定一條路徑＋upsert」才第一次讓它可達。也就是這是本票的設計決定帶進來的新失敗面。
- 使用者看到什麼：`StorageError` 不在 `AppError.map` 的映射鏈裡（`AppError.swift:195-218` 只認 URLError／AuthError／PostgrestError／HTTPError）→ 落 `.server` → `EditChildView.swift:132` 顯示「伺服器發生問題，請稍後再試一次。」——但這是永久拒絕，重試一百次都一樣；而且因為 `ChildrenStore.updateChild` 是「上傳失敗就整段不呼叫 `update_child`」，這位成員連同一個表單裡改的姓名／生日也一起存不進去。雙親家庭（一個 owner、一個 member）換寶貝頭像正是最常見的用法。
- 建議修法（三選一，擇一即可，請 orchestrator 裁定範圍）：(a) `media_bucket_update` 對 avatars 這個路徑形狀改認 `uploadable_family_ids()`（家庭層授權，與頭像「家庭共同維護」的語義一致）；(b) 路徑改成每次上傳唯一 `{family}/avatars/{child}/{uuid}.jpg`（避開 UPDATE 分支，代價是孤兒物件要清，接 LS-96 `39a3e5df`）；(c) 若決定接受這個限制，最低門檻是把 `StorageError` 403 映射成 `.rejected` 並給具體文案（同 `MediaUploadService.mapUploadError` 對 413 的既有慣例，`MediaUploadService.swift:253-260`），且把限制寫進 `docs/API.md` §6 而不是只寫在 PR body。

### M3 `onChange` + 裸 `Task` 載圖：兩張連著選會由「後完成」決定結果，可能上傳的不是使用者最後選的那張

## Cache-busting 專項驗證（orchestrator 要求的第 2 點）

- **不會讓簽名 URL 失效**：實跑 `GET <signedURL>&lsv=1788508541.123` → **200 / image/jpeg / 位元組與上傳檔相符**；負控（token 尾巴加一個字元）→ 400。storage-api 只驗 `token`，忽略額外查詢參數。
- **不會每次 render 打新請求**：`avatarCacheBust[path]` 是**上傳成功當下寫一次的固定時間戳**（`ChildrenStore.swift:151`／`:190`），不是在 `avatarURL(for:)` 裡 `Date()` 現算——同一次 session 內 URL 穩定，`AsyncImage` 不會每次 body 重抓。
- **換圖後列表立即更新**：換圖後 token 與 `lsv` 兩者都變 → URL 必然不同 → `AsyncImage` 重抓。額外的好處是即使重簽失敗、沿用舊 token，`lsv` 仍讓 URL 改變而舊 token 對同一路徑仍有效，抓回來的就是新內容。已知範圍（handoff 自己也寫了）：只覆蓋「本機這次 session 自己上傳」的情境，其他裝置靠下一次 refresh 重簽——這是可接受的取捨，不必為此加 `children.updated_at`。

### n1 「頭像 UPDATE 不看 `can_upload`」在真實 upsert 路徑上不成立——docs 與那條 DB 測試在描述一個產品其實做不到的行為

- **實跑證據**（同一位 `role=member, can_upload=false` 的使用者 D，同一個既有頭像物件）：
  - 直接 SQL `update storage.objects …`（＝那條測試做的事）→ **影響 1 列，成功**
  - 走**真實** Storage API（`POST /object/media/<path>` + `x-upsert: true`，＝ app 唯一會走的路徑）→ **400 `new row violates row-level security policy`**
  - 把同一位 D 的 `can_upload` 改成 true，其他都不變 → **200**
- 原因：storage-api 的 upsert 是「INSERT（衝突時轉 UPDATE）」，**INSERT policy 也要過**，而 INSERT 分支這輪刻意沒動（仍是 `uploadable_family_ids()`＝看 `can_upload`）。所以放寬的 UPDATE 分支對 `can_upload=false` 的成員在 app 路徑上永遠碰不到。
- 為什麼是 minor 而不是 major：失敗方向是**關緊**（不是把權限開大），受影響的只有「member 但被收回上傳權」這個受限角色，而且 m3 修好之後他看得到明確的 `.rejected` 文案。但**文件與測試都在斷言相反的事**——那條測試會讓之後的人相信一個不存在的行為（測試綠 ≠ 產品會這樣），這是「假牙齒」，比沒有測試更糟。
- 建議修法（擇一，都不大）：(i) 若照 orchestrator 裁定文字「誰能改孩子資料就能換頭像」要真的成立，`media_bucket_insert` 的 WITH CHECK 也加同一個 avatar 分支（一行 OR，測試 5b 的斷言就變成真的）；或 (ii) 維持現狀但把 `docs/API.md`／PR body 那句改成「換照片走 upsert，實務上要同時通過 INSERT（`can_upload`）與 UPDATE（contributor）兩條」，並把 5b 那條探針改成**經由 API 語意**的斷言（或至少在該段註解寫明「這是 SQL 層行為，client 的 upsert 另受 INSERT 分支約束」）。順帶：`ChildAvatarUploadService` 的 403 文案「請確認你仍是這個家庭的成員」對這位使用者是誤導（他就是成員，缺的是上傳權）。

### n2 被取消的載入 task 的 `defer`／catch-all 會污染下一輪的載入狀態
- 位置：`CreateChildView+Avatar.swift`（`loadPickedAvatar()`）與 `EditChildView.swift` 同名函式。

- 位置：`docs/API.md` §6「寶貝大頭照」小節，R3 新增段落結尾：「**放寬後的 UPDATE／DELETE 判準目前只在不經過 upsert 的直接 SQL UPDATE／DELETE（例如維運操作）時才用得到。**」
- **為什麼是錯的**（兩條獨立證據）：
  1. 實跑對照（我 R1／R2 兩輪的資料）：同一位 `role=member, can_upload=true` 的 B，走**真實** Storage API `x-upsert: true` 覆蓋 owner A 上傳的頭像——放寬前 **400**，只改了這條 UPDATE／DELETE policy 之後 **200**。也就是 app 的 upsert 路徑確實會經過、而且需要這條放寬分支。
  2. 從 policy 文本推導：對「不是家庭 owner、也不是該物件 `owner`／`owner_id`」的 member，分支 1（`owned_family_ids`）與分支 2（上傳者本人）恆為 false，唯一能放行的就是 avatar 分支。R1 M1 的事故（owner 一碰就把 member 永久鎖死）正是這條分支不存在時的表現。
- 影響：純文件，但方向是「讓讀者以為 `20260904081435` 這支 migration 對 app 沒有作用」——而它正是 M1 的修法本體；同一份 PR 的 BREAKING 段第 2 條寫的是正確版本（「這個放寬只到 UPDATE／DELETE policy 這一層……所以 `can_upload=false` 的成員實際上仍換不了頭像」），兩處自相矛盾。
- 修法（一句話）：把該句改成——「放寬讓**同家庭 owner／member（且有上傳權）互相覆蓋彼此上傳的頭像**在 app 上成立（這正是 R1 M1 的修法）；沒有一起放寬的是 INSERT，所以 `can_upload=false` 的成員在 upsert 的第一關就被擋下。」若不想在本輪動 docs，記入 LS-96 亦可（純文字、無行為影響）。
