## 現象

`SupabaseAuthServiceTests.test_initialSession_offlineWithExpiredLocalSession_doesNotClearCache` 以固定 `sleep 2.5s` 等待 supabase-swift `RetryRequestInterceptor` 重試（v2.49.0：`defaultRetryLimit=2`、退避 `pow(2,1)*0.5=1s`）。若 SDK 升版把 retryLimit 調 3（退避 1s+2s=3s > 2.5s），旗標 `false` 的迴歸就抓不到——無聲假綠，且無訊號提醒重調。

## 修法

在 `TestSupabaseClient.make(storage:)` 的離線 stub 計數被呼叫次數，重試用盡（今日 2 次）時 fulfil `XCTestExpectation`，再短 settle 後斷言。自適應 SDK 變更，測試可縮到 ~1.2s。

**不可**改用 `authStateChanges` 計數 `.initialSession`：`EventEmitter.emit(..., to: token)` token-scoped、每個訂閱者各觸發一次 `emitInitialSession`，測試端拿到自己那份，無法保證 service 內部監聽已處理；`didChangeAuthStateNotification` 更早發出，同樣不成立。

## 驗收

* 旗標改 `false` 必紅、還原必綠（同 [LS-55](https://linear.app/little-sprout-app/issue/LS-55/ios-基礎層收尾-minorspr-63-r2-n1-n9initialsession-離線抹-nil快取非同步測試ls999-測試死碼) M1 證明法）。
* 測試不含任何 SDK 重試常數字面值。

## Findings

### F1 — minor：`try?` 把「未來 SDK 不再拋錯」吞成無聲假綠
`LittleSproutTests/SupabaseAuthServiceTests.swift:251` `_ = try? await offlineClient.auth.session`

**失敗情境**：某版 SDK 若改成「`session` 直接回傳本機那份過期 session（或 fail fast）而不打網路」，這行會瞬間返回、`try?` 吃掉差異，整條測試的等待塌縮成 150ms。此時若旗標退化成 `false`，內部 `emitInitialSession` 還在跑 1s 重試、`.initialSession(nil)` 尚未送達，斷言就通過 → **無聲假綠**，正是 LS-62 要消滅的那一類 bug。`offlineCallCount > 0` 擋不住（內部路徑那時已經打過第 1 次）。

**建議修法**（3 行、同檔、在 scope 內，不含任何 SDK 常數）：
```swift
do {
    _ = try await offlineClient.auth.session
    XCTFail("離線時 auth.session 應該 throw——沒 throw 代表 SDK 不再走網路 refresh，這條測試的等待已失效")
} catch {}
```
我已在複本實測此變體：旗標 `true` 下 3/3 綠，代表今日確實會 throw，加上去不會誤紅。採用後同樣的 SDK 變更會變成**大聲的紅**而非無聲的綠。

### F2 — minor：註解把保證講得比實際強一點（順序假設）
`LittleSproutTests/SupabaseAuthServiceTests.swift:243`（「await 到的就是…那個背景重試序列本身真的執行完畢」）

**失敗情境（PLAUSIBLE，未重現）**：只有當測試那次呼叫抵達 `LiveSessionManager` 時內部 in-flight task 仍存活（或尚未建立）才會合流。若 `SupabaseAuthService` 的 `authStateChanges` 訂閱 Task 被餓超過 ~1s（要跨 `authStateChanges` getter 內的 `Task{}` 與 observe Task 兩跳），測試會自建一條序列、跑完、斷言，而內部序列才剛開始 → RED 情境下假綠。窗口寬約 1s，17 次 RED（9 次原狀＋8 次 1ms settle 變體）在 load 64 的機器上都沒踩到，屬低機率。

**建議**：不必改邏輯（沒有更乾淨的同步點——I-B 已排除用 `authStateChanges`，而「快取保持不變」本質上沒有可 poll 的終態）。只建議把註解語氣改成「與內部那條 refresh 序列合流（合流不成時也是一條同時起跑的等價序列）」，避免下一位維護者誤以為這是硬保證。

### F3 — informational：settle 餘裕已量測，建議把數字寫進註解
`:256` 的 150ms 目前有 ~150 倍餘裕（1ms 仍 8/8 紅）。把這個量測結果註記一句，未來若真的 flake，維護者才知道「不是把 150 調大就好，而是排程順序假設出事了（F2）」。

### F4 — informational：時間預算 headroom 約 4%
RED 首次執行量到 1.442s（後續 1.16–1.20s），對 ≤1.5s 只剩 ~4%。下限由 SDK 的 1s 退避決定，無法再壓。若 SDK 調大退避，這條會先變「慢」而不是「錯」——是大聲的失敗，可接受，不需處置。

### F5 — informational（環境）：2/24 runner 崩潰**與本測試無關**，且找到具體 root cause 候選，建議開 harness 票
- **判定：環境**。我在**專屬**模擬器上跑了 6 次 `xcodebuild test`／約 95 個 test case 執行（含 8+8+8+3 次 `-test-iterations`），機器 load average ≈ 64，**零** runner crash、零 flake；失敗全部是預期中的 `XCTAssertEqual`。
- **root cause 候選**：`scripts/gates/detect-simulator.sh` 產出的 destination 是 `platform=iOS Simulator,name=<機型>,OS=<版本>`——**用機型名而非 UDID**。多個 agent 併行跑 push-gate 時全部解析到同一台（清單第一台）模擬器，等於併發 `xcodebuild test` 打同一顆 simulator，正是 `Early unexpected exit, operation never finished bootstrapping`／`Restarting after unexpected exit` 的典型成因。現場旁證：審查當下有 3 台模擬器同時 Booted，與 agent 觀察一致。
- **建議**：開 `lane:harness` 票，讓 push-gate 取得專屬模擬器（每個 worktree `simctl clone`／固定 UDID 池，或用 lock file 串行化 `xcodebuild test`），並把 destination 改成 `id=<UDID>`。這同時能消掉 LS-56 註解裡記的 SPM 瞬斷同源雜訊。
