## Major

### M1（major）`LittleSprout/Services/Timeline/TimelineStore.swift:118-121`／`178-181` — 新增的 await 之後不再檢查世代號，繞過本檔自己文件化的作廢契約

`refresh` 原本在世代號檢查（`guard myGeneration == generation`）與 `refreshState = .success` 之間**沒有任何 suspension point**；本輪在中間插入 `await loadReactionCounts(...)`（最多 3 次網路往返），回來後直接寫 `refreshState = .success`，沒有重新檢查世代號；`loadReactionCounts` 內部（`TimelineStore.swift:287-297`）寫 `reactionStates` 時也沒有。`loadMore` 同型（`:178-181`，回來後也不再驗 `myGeneration`／`baseTailID`）。

失敗情境：
- 登出競態（`reset()` 的文件註解就是為這件事寫的，`TimelineStore.swift:301-304`）：refresh 已通過世代檢查、`entries` 已寫入，正卡在愛心計數的 3 次 RPC；使用者此時登出 → `reset()` 把 `entries`／`reactionStates` 清空、`refreshState = .idle`、`generation += 1`；RPC 回來後把**上一個帳號**的 `reactionStates` 重新寫回被清空的 store，並把 `refreshState` 從 `.idle` 改成 `.success`。
- 連續切換 `ChildFilterBar`：refresh#1 在愛心窗口內、refresh#2 已把 `refreshState` 設為 `.submitting`（或已 `.failure`），refresh#1 回來後把它蓋成 `.success`，且 `refresh` 對呼叫端回 `true`（`refreshWithCurrentFilter` 的呼叫端會據此判斷成功）。

誠實標註可見度：`TimelineView.swift:183-184` 只在 `renderableEntries.isEmpty` 時才讀 `refreshState`，所以目前多數情境使用者看不到症狀（`entries` 非空時錯誤態本來就不顯示）；但契約被打破後，之後任何依賴 refreshState 的改動都會踩到，且登出後殘留跨帳號狀態這條是實打實的。修法：`await loadReactionCounts` 之後再 `guard myGeneration == generation else { return false }`（`loadMore` 另加 `entries.last?.id == baseTailID`），或把愛心批次載入移出關鍵路徑（配合 M2 一起改）。

### M2（major）`LittleSprout/Services/Timeline/TimelineStore.swift:287-298` — 三種 kind 的 `get_reaction_counts` 逐一 await 串行，而且卡在 refresh／loadMore 的關鍵路徑上

`for (kind, targetIDs) in idsByKind { … guard let rows = try? await apiClient.reactionCounts(…) }`：三次呼叫彼此完全獨立（不同 target_type、不共享狀態），卻被寫成迴圈內逐一 await，第 2 次要等第 1 次回來才發。呼叫端 `:120` 又是 `await` 在 `refreshState = .success`（`:121`）之前——`:118-119` 的註解寫「不擋在 refreshState = .success 之前」，但程式碼實際就是擋著（註解與程式碼不一致，這點請一併修正）。

失敗情境：一頁同時有日記／相簿／照片三種卡時，每次下拉重新整理都變成 3 次序列 RTT。3G／弱網 300ms RTT 下等於每次 refresh 多等約 0.9 秒才收轉圈（`.refreshable` 的系統轉圈綁在 `await timelineStore.refresh(...)` 回來為止，`TimelineView.swift:210-213`）；`loadMore` 同理，且期間 `loadMoreState` 一直是 `.submitting`，`loadMoreTrigger` 的 guard 會擋住下一次捲底載入。

修法（與 M1 同一區）：三次呼叫改併發（`withTaskGroup`／`async let`，最多 3 個 kind 不必再設並發上限），結果彙整後**一次**寫回並重新檢查世代號；或者更好：愛心計數不進 refresh 的 await 鏈（`refreshState = .success` 先落地，計數用獨立 Task 補），因為程式碼自述「愛心是次要資訊、失敗只降級」——次要資訊不該延後主要內容的完成狀態。

### M3（major，PLAUSIBLE）`LittleSprout/Services/Timeline/TimelineModels.swift:279-289`＋`SupabaseTimelineAPIClient.swift:141-152` — 按讚者已退出家庭時，整份按讚名單解碼失敗（不是少一列，是整張 sheet 掛掉）

`reactors` 用 PostgREST embed `select("user_id, profiles(display_name)")`；`ReactorRow.init(from:)` 用 `container.nestedContainer(keyedBy:forKey: .profile)` **硬解**巢狀物件。`reactions` 沒有隨 `family_members` 退出而清除（`supabase/migrations/20260822120000_init_schema.sql:248-256` 只有 `profiles`／`families` 的 on delete cascade），而 `profiles_select` RLS 是 `id in (select private.peer_profile_ids())`（`20260822120200_rls_policies.sql:120-121`）——人一退出家庭就不再是 peer。PostgREST 對 to-one embed 是 left join 語意，讀不到的內層會回 null，`nestedContainer` 對 null 會丟 `valueNotFound`，整個 `[ReactorRow]` 解碼失敗 → `LikersListSheet.swift:96-98` 落到 `loadError`，使用者看到錯誤訊息而不是名單。

失敗情境：A 按了某篇日記的愛心後退出家庭（已上線流程，`FamilyStore+Members.swift:123` `leaveFamily()`／`removeMember`，UITest `FamilyMembersLeaveFlowUITests`）。留在家庭的人：Count Zone 仍顯示 N（`get_reaction_counts` 走 `reactions_select` 家庭範圍，仍算得到 A 那一列），點下去 sheet 永遠只顯示錯誤，且**其他按讚者的名字也一起看不到**。

標 PLAUSIBLE 的理由：本輪依派工單硬規則沒有實跑本機 stack 驗證 PostgREST 對這個情境確切回 null（而不是省略該 key），但兩種形狀都會讓現在的 `init(from:)` 丟錯，結論不變。既有 `FamilyMember`（`FamilyModels.swift:201-205`）用同一寫法是安全的——`family_members` 的列本身保證那個人還在家庭裡，`reactions` 沒有這個保證，這是抄慣例時漏掉的前提差異。
修法：`decodeIfPresent` 巢狀物件，取不到就跳過該列或回退成佔位名稱（例如「已退出的成員」）；並補一支解碼單元測試（餵 profiles 為 null 的 JSON）。
