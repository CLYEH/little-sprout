## 描述

來源：[LS-17](https://linear.app/little-sprout-app/issue/LS-17/storysign-in-with-appleemail-otp-登入) R2 merge-reviewer N5（PR #117 comment `611b6d97`）。

`AuthService` 協定文件（`AuthService.swift:18-24`）要求 `@Observable` class 內部訂閱 auth 狀態變化再對外發佈，但 `AuthStore` 目前只在三個時機取快照：`init`、自己的 mutating 方法之後、`RootView` 的 `scenePhase == .active`。

具體風險：SDK 偵測到 refresh token 被撤銷／重用 → `authStateChanges` 發 signedOut → `SupabaseAuthService.cachedSession` 變 nil，但 `AuthStore.session` 還捏著舊值 → `RootView` 繼續顯示 `AuthenticatedRootView`，使用者停在一個已登出的 app 裡，每個 API 呼叫都會 401，要背景再回前景才會被踢回登入頁。

[LS-17](https://linear.app/little-sprout-app/issue/LS-17/storysign-in-with-appleemail-otp-登入) 當下影響有限（登入牆後面全是佔位畫面、沒有真的 API 呼叫），但 [LS-18](https://linear.app/little-sprout-app/issue/LS-18/story建立家庭與邀請加入) 接上真資料後會浮現。

建議修法：`AuthStore` 內起一個 `Task` 訂閱 auth 狀態變化寫回 `session`；或在 `AuthService` 上補一個 `sessionUpdates: AsyncStream<AuthSession?>`。

務必在 [LS-18](https://linear.app/little-sprout-app/issue/LS-18/story建立家庭與邀請加入) 開始實作真資料串接之前完成。

- **AsyncStream 語義實測**（獨立 Swift script，非推測）：

### Findings

**F1 — minor｜`sessionUpdates` 的「一次性訂閱」語義沒被文件涵蓋**
`SupabaseAuthService.swift:25`（`let sessionUpdates`）／`AuthStore.swift:49`（`deinit` cancel）／`AuthService.swift:27-36`（協定文件）。
協定文件有寫「單一消費者」，這點合格；缺的是更強的那半條：**consumer 一旦取消，這條 stream 就永久死亡**（上面實測 1）。今天生產路徑 `LittleSproutApp.swift:9` 把 `SupabaseAuthService` 與 `AuthStore` 綁在同一行成對建立、同生共死，所以沒有現行 bug——但這是個對 LS-18 很近的陷阱。
具體失敗情境：LS-18 若把 `SupabaseAuthService`（或它底下的 client／service）提升成共用實例給 `SupabaseFamilyAPIClient` 用，而 `AuthStore` 在某條路徑上被重建（環境注入、登出後重建 store、或任何導致舊 store 被釋放的寫法）→ 舊 store 的 `deinit` cancel 把 stream 收掉 → 新 store 的 `for await` 立刻結束 → **LS-82 修的東西整條靜默失效，而且現有測試抓不到**（每條測試都是一個 stub 配一個 store，永遠 1:1）。
建議：協定文件補一句「訂閱是一次性的：consumer 取消後 stream 永久終止，因此 `AuthService` 實例與其 `AuthStore` 必須成對建立、同生共死」；或（較貴）把 `sessionUpdates` 改成 computed property，每次取用註冊一條新 continuation 到 lock 保護的陣列裡廣播。我傾向前者。

**F2 — minor / PLAUSIBLE｜快照路徑與 stream 之間的暫態倒退**
`AuthStore.swift:40-45`，以及 `AuthStore.swift:17-18` 那句「兩邊寫的都是同一個 `AuthService` 的事實，不會互相矛盾」。
`makeStream` 預設 `.unbounded`，緩衝的是**歷史事件**而不是最新狀態；`SupabaseAuthService.swift:44-45` 是先寫 `cachedSession` 再 `yield`，所以 `currentSession` 永遠 ≥ stream 已送達的最新值——快照路徑會**跑在 stream 前面**。
具體失敗情境：App 在背景／MainActor 忙碌期間累積兩個事件 `tokenRefreshed(S1)`、`signedOut(nil)`（順序如此）→ 回前景，`RootView` 的 `scenePhase == .active` 先跑 `refreshSnapshot()` 讀到 `nil`（正確，踢回 Welcome）→ 接著訂閱 task 才開始排空緩衝：`session = S1`（`isAuthenticated()` 變 true，root routing 閃回 `AuthenticatedRootView`）→ 再 `session = nil` 收斂。反向同理（剛登入成功寫入 S，緩衝裡遲到的 `nil` 蓋掉，再被 `signedIn` 修正）。
會自我修正、而且排空是 MainActor 上連續的 job，很可能來不及觸發一次 render，所以標 PLAUSIBLE、不列 major——但那句「不會互相矛盾」的文件敘述在暫態上是不成立的。
建議（一行、且不會弄紅現有測試）：迴圈裡改寫成 `self.session = authService.currentSession`——把 stream 當「有事發生」的訊號、把快取當權威值（快取在每次 yield 前就寫好，構造上不可能更舊）。`bufferingNewest(1)` 只縮小視窗、不封閉。順手把上面那句文件敘述改成「暫態可能不同步，但一定收斂」。

**F3 — minor｜`nonisolated(unsafe)` 其實不需要，而且拿掉了未來的編譯期保護**
`AuthStore.swift:33`（＋`24-31` 那段註解）。
上面的 Swift 6 實測顯示：`@ObservationIgnored` 一個就夠了（巨集不再把它轉成 computed property，nonisolated deinit 就能碰這個 Sendable stored property）；`nonisolated(unsafe)` 是多的。它不只是贅字——它把這個屬性**永久**移出 isolation 檢查。
具體失敗情境：日後有人加一個 `resubscribe()`／從 nonisolated context 重指派這個 handle（例如 F1 的重訂閱需求），編譯器不會吭聲，就跟 `deinit` 的 `cancel()` 形成真的 data race。
建議：刪掉 `nonisolated(unsafe)`，保留 `@ObservationIgnored`，註解相應縮短（順帶讓那段 10 行註解變成 4 行）。

**F4 — minor｜wiring 測試斷線時是「掛住」不是「變紅」**
`LittleSproutTests/SupabaseAuthServiceTests.swift:233`（`async let forwarded = service.sessionUpdates.first { ... }`）。
我把 wiring 改壞（`SupabaseAuthService.swift:45` 改成只在 `authSession == nil` 時 yield，模擬「有人日後把轉發簡化成只轉登出」）→ 這條測試印出 `Test Case ... started` 後**再也沒有結束**，我在 240 秒把它砍掉（同 class 其他測試都 <1 秒）。`first(where:)` 在一條不會 yield 目標值也不會 finish 的 stream 上是永久等待；`service` 被測試函式的區域變數抓著，所以連 deinit 的 `finish()` 都不會來救。
影響：CI `ci` job 有 `timeout-minutes: 40`，所以最壞是燒掉 40 分鐘後拿到一個「job timeout」而不是一條有名字的紅測試——診斷成本高，且掩蓋真正的迴歸點。
建議：比照同 PR 兩條 `AuthStoreTests` 的做法給它一個有界等待（`XCTestExpectation` ＋ `await fulfillment(of:timeout: 2)`，或跟一個 `Task.sleep` 賽跑），讓斷線時 2 秒內就紅。
