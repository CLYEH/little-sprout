成立。`knownExactCount = hasEarlier ? nil : comments.count`（`CommentsStore.swift:94`），而 `hasEarlier` 的唯一來源是 `page.count == Self.pageSize`（`loadInitial`／`loadEarlier` 各一處）：回傳筆數 < limit ⇒ 伺服器已無更早資料 ⇒ 手上這份就是全部 ⇒ `comments.count` 即總數。之後 `send()` 成功 `append`、`removeLocally()` 移除，各讓值正好 ±1，維持「確定」性質（`test_knownExactCount_incrementsBySendSuccess_whenAlreadyKnown` 釘住 +1）。保守側也對：剛好 20 則的情況會被判成 `hasEarlier == true`（不確定），只會少寫、不會寫錯。Head 顯示走另一支純函式 `CommentsSheetView.headCommentCountText(...)`（`hasEarlier` 時「N+ 則留言」），三個分岔由 `CommentsSheetViewTests` 三支測試釘住。

**② 不精確狀態下的刪除／新增，互動列停在舊值可接受嗎？裁定：可接受。**
`hasEarlier == true` 時不回寫，互動列維持既有值（在 LS-216 目前沒有其他來源的情況下通常是 0）。對照三個選項：(a) 寫入已載入筆數＝**已知錯誤**的數字（R1 m1 點名的問題）；(b) 維持舊值＝可能過時但不是錯的斷言；(c) 真正修好＝需要後端 `total_count`，不在本票範圍（i1 已進 LS-96 `d17bed11`）。sheet 內部使用者看得到「N+ 則留言」與「載入更早的留言」鈕，不會被誤導；互動列在 sheet 外沒有佐證，選 (b) 比 (a) 誠實。這也正是我 R1 的建議寫法，採納。唯一代價（>20 則的討論串在翻完分頁前互動列停在 0）handoff 風險段已明寫。

**③ 單元測試有沒有釘住「有更早時不回寫」？部分。**

**④ m2 世代守門的取消／覆蓋路徑正確嗎？正確。**
`loadInitial()` 進入時 `generation += 1` 並捕捉 `myGeneration`，await 後成功／失敗兩條路徑都先 `guard myGeneration == generation`（`CommentsStore.swift:97,104,110`）；`loadEarlier()` 只捕捉不遞增，await 後成功／失敗都比對，不符就 `loadEarlierState = .idle` 後丟棄（`:127-133,146-149`）——`.idle` 這一步很關鍵，`loadInitial()` 不會碰 `loadEarlierState`，不收回就會卡在永久轉圈，測試也把它斷言進去了。檔頭註解另外交代了「為什麼不需要 `TimelineStore.loadMore()` 那種 `baseTailID` 身分核對」：反向順序（`loadInitial` 先起、`loadEarlier` 後起）在這支 View 不可達，因為「載入更早」列只在 `initialLoadState == .success` 時渲染，而 `loadInitial()` 一進入就同步把狀態切成 `.submitting`、畫面同幀換成骨架屏。我核對過這個推理：兩個呼叫端（`+Actions.swift` `memberBlocked()`、`+States.swift` 重試鈕）都是 `Task { await store.loadInitial() }`，MainActor 會在下一個觸控事件之前跑完 Task 起頭那幾行，推理成立。
