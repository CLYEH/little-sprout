### M1（major）`supabase/tests/107_album_summaries.sql:424,427` — 效能斷言是恆綠句，永遠不會紅

```
  if v_plan ~* 'seq scan on (public\.)?media\b' then
  if v_plan ~* 'seq scan on (public\.)?album_media\b' then
```

PostgreSQL 的 ARE 裡 `\b` 是**退格字元（ASCII 8）**，不是字界（字界是 `\y`／`\m`／`\M`）。EXPLAIN 輸出裡永遠不會有退格字元，所以這兩條 `if` 永遠不成立。

實測（本機 PG 17.6）：

```
select 'Seq Scan on public.media m' ~* 'seq scan on (public\.)?media\b'  -- f
select 'Seq Scan on public.media m' ~* 'seq scan on (public\.)?media\y'  -- t
select 'Seq Scan on public.media m' ~* 'seq scan on (public\.)?media'    -- t
select 'Seq Scan on media'          ~* 'seq scan on (public\.)?media\b'  -- f
```

**具體失敗情境**：我另外灌 2000 列 media＋20 本相簿，把 `enable_indexscan`／`enable_bitmapscan`／`enable_indexonlyscan` 關掉再跑同一條 view 查詢——plan 裡確實出現 `Seq Scan on public.media m`（rows=2000, loops=20）與 `Seq Scan on public.album_media am`（Rows Removed by Filter: 1903），而 107 那兩條 regex 判定**皆為 false**。也就是說：日後若有人改動 view／policy／索引讓它退化成全表掃描，這一段照樣印「ok 效能：…plan 無 Seq Scan on media／album_media」並通過。票文驗收「EXPLAIN 不出現 seq scan」與 `docs/PLAN.md` §5／L131「灌幾萬列後 EXPLAIN 證明沒有 per-row 子查詢」目前沒有任何機械保障。

**建議修法**：
1. `\b` → `\y`（或直接拿掉界定符）。
2. 比照 `supabase/tests/50_rls_plan_no_percall_subquery.sql:245-255` 的既有慣例補一段**偵測器自證**（強制 `set local enable_indexscan = off` 跑一次，確認判準真的會紅；那個檔案的檔頭就寫著「抓不到的話上面三個 ok 全部沒有意義」）。
