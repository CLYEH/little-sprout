## Blocker

### B1（blocker）`LittleSprout/Features/Content/DeleteConfirmationSheet.swift:75-88`：sheet 高度自我量測是循環相依，detent 實質釘死在種子值 420 —— Dynamic Type 放大後確認文案被截掉，IN-1 要求的「無法復原」整句消失

`GeometryReader` 掛在 `.background`，量到的是 **VStack 已經被 sheet 高度夾擠之後**的高度，不是內容的內在高度：

```
measured_n = min(intrinsic, detent_{n-1})
detent_n   = measured_n + 8
```

`intrinsic > detent` 時 `measured` 永遠等於當下 detent，detent 只能每次 +8 慢爬、爬不到內容真正需要的高度。註解宣稱「sheet 剛好貼合內容高度（含 Dynamic Type 放大後的高度）」在放大字級下不成立。

**實測（本機 `LS-190-iPhone17Pro` iOS 26.0，`DeleteDiaryConfirmation`／`DeleteCommentConfirmation` harness，`xcrun simctl ui <udid> content_size <size>`，simulator-lock 內）**：

| content_size | 實測 sheet 高 | 結果 |
|---|---|---|
| `large` | ≈417pt | ✅ 完整 |
| `extra-large` | ≈424pt | ✅ 完整 |
| `extra-extra-extra-large`（**標準設定滑桿最大值，非輔助使用**） | ≈444pt | ❌ 內文截成「…之後還能在相簿看到。這個動作目前**…**」 |
| `accessibility-extra-large`（AX3，票文範圍 3 點名） | ≈439pt | ❌ 標題截成「要刪除「今天在溜**…**」一行；內文只剩 2 行「…家人也看不到；**…**」 |
| `accessibility-extra-extra-extra-large`（AX5） | ≈432pt | ❌ 內文只剩 1 行「這篇日記會從**…**」，兩顆鈕擠在一起 |

10b 同型：AX5 下標題「要刪除這則留**…**」、內文「這則留言刪除**…**」。

**失敗情境**：長輩把系統字級調到最大（本產品主要客群，`docs/elder-constraints.md` 的預設假設）→ 按下「刪除日記」→ 確認卡上看不到「裡面附的照片不會被刪除」與 **「這個動作目前無法在 App 內復原。」**——後者正是 LS-152 Notes IN-1（`fSH5S`）逐字裁決要放的那一句、也是拿掉「30 天可還原」承諾之後**唯一**的後果告知。破壞性動作的確認卡把後果藏起來。票文範圍 3「AX3 不破版」不成立。

附帶：handoff 風險欄第 4 條把「sheet 貼合量到高度時最底部取消鈕熱區被裁掉幾個點」歸因為「WDA 量測路徑偏移」——那不是量測工具問題，是同一個 bug 的症狀（`measured == available` 時本來就一點餘裕都不剩）；`+8` 緩衝與 `minHeight: 52` 是繞過症狀、沒有修根因。

另一個同源後果（**PLAUSIBLE**，未重現）：`errorRow` 排在兩顆鈕之後，失敗時要多佔一行高度——detent 長不上去的話錯誤訊息會被擠掉，使用者按下「刪除這篇日記」後畫面「什麼都沒發生」。

**建議修法**：不要在被夾擠的容器裡量自己。二選一——
(a) 內容包 `ScrollView`，detent 改 `[.height(x), .large]`（放大字級可捲、可拉大），或
(b) 量測前對內容加 `.fixedSize(horizontal: false, vertical: true)` 取內在高度，並把結果 clamp 在螢幕高的某個比例內；仍需搭配 `ScrollView` 處理超出螢幕的情形。
兩種都請補一支對 AX3／AX5 的釘樁（UITest 斷言完整 `bodyText` 字串在放大字級下 `exists && isHittable`，或 `TapTargetGateTests` 增設放大字級變體），否則現有 gate 抓不到——`tap-target-check.sh`／`TapTargetMeasurement.launch` 一律用 `UICTContentSizeCategoryL`，這個缺陷對它是隱形的。

### B2（blocker）`LittleSprout/Navigation/RootView+AuthenticatedGate.swift:96-98` × `LittleSprout/Features/SettingsView.swift:318-341`：一般登出路徑沒有 `eulaStore.reset()`，同機換帳號時新帳號可繞過 EULA 閘門

`EULAStore` 隨 app 存活（`LittleSproutApp.swift:19` 的 `@State`）。`AuthenticatedGate.disagreeAndSignOut()` 有 `eulaStore.reset()`（該函式註解自己寫明「換帳號登入需要重新檢查，不能沿用上一位使用者的 `shouldPresent`」），但**設定頁的一般登出沒有**——`SettingsView.signOut()` 只歸零 `familyStore`／`childrenStore`／`timelineStore`／`albumsStore` 四個 store，本 PR 沒有動它。

`eulaGate` 的判斷順序是「`.failure` → `shouldPresent == nil` → `shouldPresent == true` → 放行」，`checkState == .submitting` **不**被視為「還不知道」。

**失敗情境（不是 race，是確定性的殘留狀態）**：
1. A 在裝置上登入、同意 EULA → `shouldPresent = false`。
2. A 走設定 →「登出」（app 沒被殺掉）。`eulaStore` 保持 `shouldPresent = false`。
3. B（從未同意過）在同一台裝置登入。
4. `AuthenticatedGate` 重建，第一次 render：`checkState == .idle`、`shouldPresent == false`（A 殘留）→ 直接落到 `familyGate`。`.task(id: B)` 的 `checkStatus` 還在飛。
5. 家庭查詢與 EULA 檢查是兩支獨立並行的 `.task`，家庭查詢先回來時 B 就會看到 ForkView／時間軸；EULA 檢查回來後畫面才被 EULA 頁取代。網路卡住時 `checkState` 停在 `.submitting`，而 `.submitting` 不會擋——B 可以無限期停在 app 內。

票文驗收「QA：新帳號首次登入必見 EULA」在這條路徑上不成立；這是 App Store 5.1.1／UGC 的合規要求（PLAN §6 第 7 項／§10-B），不只是體驗問題。

**建議修法**（兩件都要，(a) 補洞、(b) 才是機械保障）：
(a) `SettingsView.signOut()` 成功後補 `eulaStore.reset()`——與 LS-113（`ChildrenStore`）／LS-126 R1 M5（`TimelineStore`）／LS-165（`AlbumsStore`）對其他四個 store 的既有修法完全同型，那三次都是同一個缺陷模式被 review 抓到。
(b) `EULAStore` 記下「這個判定屬於哪個 `userID`」（同 `FamilyStore.ownerUserID`／`syncOwner(to:)` 的既有手法），`eulaGate` 只在結果屬於當前 `userID` 時才放行，否則一律視為未知（走 `ProgressView("正在確認條款狀態…")`）。只做 (a) 的話，任何未來新增的登出／換帳號路徑忘了呼叫 `reset()` 會再犯一次。
建議同時補單元測試釘住「`userID` 換人之後 `shouldPresent` 不得沿用」，讓它有 gate。

### M1（major）`LittleSprout/Features/Timeline/DiaryDetailView.swift:143-162`（＋`:76-85`、`TimelineView.swift:69-72`）：scope 逾越，且入口沒有作者／owner 判斷

票文與派工 comment 都明寫「入口由內容操作表票（LS-189）接」、「入口 API 留給 LS-189 接」——本票只需要提供可被呼叫的 View。實作在 `DiaryDetailView`（有稿 `vzYXz`，稿上沒有這一列）常駐插入一顆 `lsDanger` 色「刪除日記」列，位置在 header 與內文之間，compact／regular 兩個版面都加。

同時，這顆鈕**不判斷呼叫者是不是作者或 owner**（檔內註解自承）。`docs/API.md` §4 `set_diary_deleted` 的授權是「作者本人或該家 owner」，其他成員一律 `42501`；`AppError` 把 `42501` 映射成 `.rejected`，`DeleteConfirmationSheet` 顯示的是通用文案「無法完成這個操作。」。

**失敗情境**：媽媽（一般成員）點進爸爸寫的日記 → 看到紅色「刪除日記」→ 點下去 → 確認卡 → 按「刪除這篇日記」→ 只得到「無法完成這個操作。」，不知道自己本來就沒有這個權限。LS-152 Notes `VAij1` 對同型情境的既有裁決正是「操作入口本來就該依成員身分隱藏，不應該讓使用者走到這個錯誤」。

**建議修法**：把日記入口也收回 harness（同 `deleteCommentConfirmationHost`，UITest 照樣跑得到，票文要求的 UITest 場景本來就只有「刪除留言確認流程」），入口留給 LS-189；若要保留，至少加作者／owner 判斷再顯示，並在 LS-208 或 LS-189 登記這個過渡版位。
