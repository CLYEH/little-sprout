### 六個複驗點

**(1) race／效能**

**`TaskGroup` 並行 PUT 與「兩者成功後才 INSERT」的順序保證 → 正確。**
```swift
try await withThrowingTaskGroup(of: Void.self) { group in
    group.addTask { try await putOriginal() }
    if let pendingThumb { group.addTask { try await bucket.upload(...) } }
    for try await _ in group {}
}
```
關鍵性質成立：任一 child 拋錯時 `next()` 立刻重拋、跳出 for，但 `withThrowingTaskGroup` 在離開 scope 前**必定 cancel 並 await 全部 child**，所以錯誤傳到呼叫端的 `catch` 時，兩個網路呼叫都已經確定結束——`cleanupOrphans` 不會撲空也不會漏清。INSERT 在 `uploadOriginalAndThumb` 成功回傳之後才發，順序保證是結構性的（不是靠註解約束）。

**縮圖生成跑在哪個 executor → 不在 main actor，不會凍結發佈中的 UI。** 這條我特別追了呼叫鏈：`DiaryComposerStore` 是 `@MainActor`（`:12`），但 `MediaUploadService` 協定與 `SupabaseMediaUploadService` **都沒有任何 actor 標註**（`:19`／`:29`），所以 `uploadPhoto`／`uploadVideo` 是 nonisolated async——依 SE-0338，nonisolated async 函式**不繼承呼叫端的 actor**，會跳到 global concurrent executor 執行。`makePhotoPendingThumbnail`／`makeVideoPendingThumbnail` 是該函式 body 的第一件事，因此同步阻塞的是一條 cooperative pool 執行緒，不是主執行緒。handoff 風險欄寫「同步阻塞」是誠實的，但影響範圍比字面小，值得寫清楚。

**HEIC／大圖記憶體峰值 → 這是正確的省記憶體路徑。** `CGImageSourceCreateWithData` ＋ `CGImageSourceCreateThumbnailAtIndex(maxPixelSize: 512)` 由 ImageIO 直接降採樣解碼，**不會**先把全解析度點陣materialize 出來（對比 `UIImage(data:)` 那條路——正是 LS-125 M4 當初的成因）。峰值 ≈ 傳進來的壓縮 `Data`（呼叫端本來就持有）＋ 一張 ~512px 點陣（<1 MB）。之後 `UIImage(cgImage:).jpegData(...)` 操作的也是那張 512 圖，很便宜。20 張佇列在既有的序列上傳迴圈裡跑，同時只有一張縮圖在記憶體。

`kCGImageSourceCreateThumbnailWithTransform: true` 也設了——輸出已套用 EXIF 旋轉，`cgImage.width/height` 是顯示方向的實際輸出像素，正是 §6 要求的「縮圖實際輸出的像素寬高，不是理論值」。（衍生的跨票注意事項見 i3。）

**影片首幀 tolerance → 沒設，見 i4。**

**(2) 失敗路徑**

**清理不可能刪掉「重試時已成功」的物件 → 結構性保證，不是靠時序運氣。** 每次 `uploadPhoto`／`uploadVideo` 進來就 `let mediaID = UUID()`，路徑全部由這顆隨機 UUID 推導；而 `DiaryComposerStore.uploadedMediaByDraftID` 保證已成功的草稿**根本不會再呼叫**上傳。所以第 N 次嘗試的 `cleanupOrphans` 只會碰到第 N 次自己生成的兩條路徑，跟任何其他嘗試的物件無交集。與 LS-125 續傳語意完全對齊。✓

**清理本身失敗 → `_ = try? await ... .remove(paths:)`，吞掉、不覆蓋原始錯誤。** 符合協定檔既有的 best-effort 約定（呼叫端只在意「這次失敗了」）。批次一次 `remove(paths: [原檔, 縮圖])` 而不是打兩次，測試有釘（`removed.count == 1` 且 `removed.first?.count == 2`）。

**雙向都測到了**：縮圖 PUT 失敗（原檔已成功）→ 清兩個；原檔 PUT 失敗（縮圖已成功）→ **仍要清縮圖**，不能只清原檔。第二支正是 handoff 自陳「實作中抓到的 bug」的反面，有測試鎖住。

### Minor

**m1 `objectPathPrefix` 每次上傳讀了兩次 `Date()`，跨月瞬間原檔與縮圖會落在不同 `yyyy/mm` 分片——而文件註解宣稱已經避免這件事。**
`MediaUploadService.swift:175-190`：
```swift
private static func objectPathPrefix(...) -> String {
    let components = calendar.dateComponents([.year, .month], from: Date())   // ← 每次呼叫都讀
    ...
}
static func storagePath(...) { "\(objectPathPrefix(...)).\(ext)" }
static func thumbStoragePath(...) { "\(objectPathPrefix(...))_thumb.jpg" }
```
實際呼叫點：`uploadPhoto:43`／`uploadVideo:79` 各呼叫一次 `storagePath`，`makePhotoPendingThumbnail:249`／`makeVideoPendingThumbnail:270` 各呼叫一次 `thumbStoragePath` ⇒ **每次上傳兩次獨立的 `Date()`**。但該函式的文件註解寫的是：
