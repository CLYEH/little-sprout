## Findings

### M1（major）冷啟動與 session 內換帳號都不會重新註冊 device token

`LittleSprout/Navigation/RootView.swift:63-71`（`onChange(of: scenePhase)`）、`LittleSprout/Navigation/RootView.swift:143-146`（`.task(id:)`）、`LittleSprout/Services/Push/PushNotificationStore.swift:30-46`

`UIApplication.shared.registerForRemoteNotifications()` 全專案只有兩個呼叫點：`PushNotificationStore.swift:45`（`refreshOnForeground`，只被 `onChange(of: scenePhase)` 的 `.active` 分支呼叫）與 `PushNotificationStore.swift:63`（`requestAuthorizationAndRegister`，剛授權時）。`refreshForEnteringApp`（同檔 30-36）只讀狀態、不註冊。SwiftUI 的 `onChange` 不對初始值觸發，所以**冷啟動這條路完全不會註冊**。

**失敗情境 a（票文範圍 2「已授權且 token 變更時重送」不成立）**：使用者已授權；APNs token 在 app 沒執行期間輪替（還原備份／重裝系統／Apple 端輪替）。下次冷啟動只跑 `refreshForEnteringApp`，不呼叫 `registerForRemoteNotifications()`，`didRegisterForRemoteNotificationsWithDeviceToken` 就永遠不會被系統呼叫（iOS 只在 app 主動註冊後才回呼），`register_device_token` 不會重送。`device_tokens` 留著失效的舊 token，推播靜默不到，要等使用者「切出去再切回來」才修復。Apple 的合約也是「每次啟動都要 register，token 只能從 delegate 回呼拿」。

**失敗情境 b（跨帳號推播外洩，`docs/API.md:767-770` 明文警告的那條）**：A 登出（票文範圍 2「登出時不刪 token」，`device_tokens` 這一列仍是 token→A）→ B 在同一個 app 行程登入（scenePhase 不變動）→ `AuthenticatedRootView` 重建、`.task(id:)` 跑 `refreshForEnteringApp` 取得 `.authorized`，但不註冊 → 沒有 `didRegister` 回呼 → `register_device_token` 不重送 → 這支裝置在 B 使用期間持續收到 **A 家庭**的推播文案（`push-dispatch` 依 `device_tokens.user_id` 派送）。`LittleSprout/Services/Push/PushLocalRecords.swift:26-29` 的註解宣稱「換帳號後這裡讀到的一定是 nil，天然會重送」——去重那一層確實不擋，但**沒有任何呼叫端會觸發那條路徑**，註解與實際行為不符。外洩窗口到下一次背景→前景為止，但使用者若不切換 app 就是整個 session。

**建議修法**：`refreshForEnteringApp`（`PushNotificationStore.swift:30-36`）在寫完 `authorizationStatus` 之後補上與 `refreshOnForeground`（同檔 42-46）相同的 `guard authorizationStatus == .authorized … UIApplication.shared.registerForRemoteNotifications()` 兩行；`.task(id: authStore.session?.userID)` 冷啟動與換帳號都會跑，一處就同時關掉兩個情境。另請補一支釘住「authorized 進場會觸發註冊」的測試——目前這條分支零覆蓋（見 i5），建議把 `UIApplication.shared.registerForRemoteNotifications()` 抽成協定（同 `LittleSprout/Services/Push/PushAuthorizationService.swift` 的既有分層四件套），否則無法 stub。

### m1（minor）`submitTokenIfNeeded` 的 check-then-act 跨 await，併發會重複打 RPC

`LittleSprout/Services/Push/PushNotificationStore.swift:91-99`

line 92 的去重 guard 讀 `UserDefaults`，line 94 `await` 出去打 RPC，line 95 才 `markSubmitted`。`AppDelegate`（`LittleSprout/Config/AppDelegate.swift:20-26`）每收到一次 `didRegisterForRemoteNotificationsWithDeviceToken` 就開一個新 `Task`。使用者連續快速切出／切回（或「剛授權」與一次前景轉場撞在一起）時，兩個 Task 都會在 line 92 通過 guard（此時還沒有人 `markSubmitted`），送出兩次 RPC。`register_device_token` 是 `delete … ; insert …` 兩個 statement（`supabase/migrations/20260822120200_rls_policies.sql:342-358`），兩筆併發交易會有一筆撞 `token` 主鍵 `23505`（或互等 row lock）；失敗那筆走 `didFailToRegister` 記 log，不致命，但白打一次 RPC，最壞情況兩筆都失敗、這一輪不會註冊（要等下一次觸發）。

**建議**：加一個 in-flight 標記（`private var inFlightTokenHex: String?`；store 是 `@MainActor`，check-then-set 之間沒有 await，是原子的），或把送出收斂成單一序列化 `Task`。

### m2（minor，PLAUSIBLE）`refreshForEnteringApp` 在 await 之後無條件寫狀態，換帳號時可能用前一位使用者的旗標覆寫

`LittleSprout/Services/Push/PushNotificationStore.swift:30-36`、`LittleSprout/Navigation/RootView.swift:143-160`

`refreshForEnteringApp` 沒有 `Task.isCancelled` 檢查，也沒有比對「回來時的登入者還是不是當初那位」。A 登出、B 立刻登入時 `.task(id:)` 會取消舊 task，但 `UNUserNotificationCenter.notificationSettings()` 不因取消提前返回，舊 task 回來後仍會用 **A 的** `hasShownBefore`（`PushPrepromptDisplayRecord.hasShown(userID:)`）覆寫 `showsPreprompt`。兩個寫入都在 `@MainActor` 上，沒有資料競態，但先後順序不保證：B 可能被誤判成該顯示（A 沒看過）或不該顯示（A 看過）。接著 `fullScreenCover` 的 `set` 與 `onFinish`（`RootView.swift:147-160`）用「當下」的 `authStore.session?.userID` 去 `dismissPreprompt`，等於把旗標記到 B 頭上。

需要精準取消時序，未在模擬器重現，標 **PLAUSIBLE**。**建議**：await 回來後 `guard !Task.isCancelled else { return }`，或把呼叫當下的 `userID` 與 `authStore.session?.userID` 比對再寫入。

## Findings

### M2（major）同一支裝置 A→B→A 再登入時，去重層吞掉重送，`device_tokens` 永遠留在 B 身上

`LittleSprout/Services/Push/PushNotificationStore.swift:109`、`LittleSprout/Services/Push/PushLocalRecords.swift:26-39`

R2 的 M1 修法（`PushNotificationStore.swift:51-52`）確實讓 `refreshForEnteringApp` 在已授權時呼叫 `registerForRemoteNotifications()`，系統也確實會再送一次 `didRegister` 回呼——但回呼落到 `submitTokenIfNeeded` 的第一道 guard（line 109）：

```swift
guard PushDeviceTokenSubmissionRecord.lastSubmittedTokenHex(userID: userID) != tokenHex else { return }
```

這筆記錄以 **userID 分 key**（`PushLocalRecords.swift:31` `keyPrefix + userID.uuidString`），語意是「這位使用者上次送過哪個 token」，不是「這支裝置目前綁在誰身上」。APNs device token 是 per-app-install、不隨帳號變動，於是：

**失敗情境（已在本機重現，非推測）**：

1. A 在裝置 D 登入、授權 → RPC 送出 → `device_tokens: T→A`；`UserDefaults[A]=T`。
2. A 登出、B 登入（同一支裝置、同一個 T）→ `UserDefaults[B]` 是 nil → 送出 → `device_tokens: T→B`；`UserDefaults[B]=T`。
3. B 登出、**A 再次登入** → `.task(id:)` → `refreshForEnteringApp` → `registerForRemoteNotifications()` 有呼叫、`didRegister` 有回來（我量到 `registerForRemoteNotificationsCallCount == 3`），但 line 109 讀到 `UserDefaults[A] == T` → **直接 return，RPC 不送**。`device_tokens` 那一列仍是 `T→B`。

後果就是 `docs/API.md:767-770` 與 `supabase/migrations/20260822120200_rls_policies.sql:334-338` 用粗體寫的那條：A 手上的裝置持續收到 **B 家庭**的推播（`push-dispatch` 依 `device_tokens.user_id` 派送，`supabase/functions/push-dispatch/handler.ts` `notification_recipients` 展開），而 A 自己一則都收不到。沒有任何路徑能自行復原——`refreshOnForeground`／設定頁流程最後都會回到同一道 guard，只有 token 真的輪替或重裝 app（`UserDefaults` 被清）才會解除。

`PushLocalRecords.swift:26-29` 的註解正是這個洞的來源，它宣稱「以 `userID` 分 key……表示換帳號後這裡讀到的一定是 `nil`，天然會重送」——**只有每個帳號第一次用這支裝置時成立**；回鍋登入時讀到的不是 nil，是上一輪的舊值。R2 新增的 `testRefreshForEnteringApp_accountSwitch_sameToken_reregistersForSecondUser`（`LittleSproutTests/PushNotificationStoreRegistrationTests.swift:74-108`）只走了 A→B 兩個全新使用者，剛好避開這條。

**重現方式（本輪實跑）**：把下面這支測試加進 `PushNotificationStoreRegistrationTests`（我在 `git archive 9788ddd` 的快照上做，**沒有動實作者 worktree**，`git status` 全程為空）：

```
refreshForEnteringApp(A) → didRegister(T,A) → refreshForEnteringApp(B) → didRegister(T,B)
→ refreshForEnteringApp(A) → didRegister(T,A)
XCTAssertEqual(deviceTokenClient.registerCallCount, 3)
```

PushNotificationStoreRegistrationTests.swift:206: XCTAssertEqual failed: ("2") is not equal to ("3")
  - A 再次登入時 device_tokens 還綁在 B 身上，必須重送 register_device_token

（同一輪 `registerForRemoteNotificationsCallCount == 3` 是過的——證明紅的是去重層，不是 M1 的修法退回去了。）

**後端側已實測沒有問題**，洞純粹在 client：我在本機容器（連線方式：`docker exec supabase_db_little-sprout psql`，證據 `LS-217-devicetoken-check.log`）用真 RPC 跑了兩次查詢——A 呼叫後 `token=ls217-mr-r2-device | user_id=a0000000-…-0001 | rows_for_token=1`；B 呼叫後 `user_id=b0000000-…-0001 | rows_for_token=1 | stale_rows_for_a=0`；中間三條直接路徑如契約所述全死（`ok: direct INSERT hits PK 23505`／`ok: UPSERT blocked by old row RLS USING 42501`／`ok: direct DELETE affected 0 rows`）；同一人重複呼叫冪等（`rows_after_repeat=1`）。也就是說**只要 client 肯送，換手一定正確**；現在的問題是第 3 步不送。

**建議修法**：把 `PushDeviceTokenSubmissionRecord` 從「每個 userID 一把 key」改成**單一 key 存最後一次成功送出的 `(userID, tokenHex)` 組合**（這支裝置只可能有一個當前綁定），`submitTokenIfNeeded` 改成「組合不同就送」。既有三支測試（`testSubmitTokenIfNeeded_sameTokenTwice_onlyRegistersOnce`／`_sameTokenDifferentUser_registersAgain`／`_tokenChanged_registersAgain`）語意不變仍會過，另補一支 A→B→A 的回歸測試。

## Findings（本輪新增）

### R3-m1（minor）`os.Logger` 印 `error.localizedDescription`，對 `AppError` 等於印了一句空話——m3 想解的問題沒有真的解掉

`LittleSprout/Services/Push/PushNotificationStore.swift:110-112`

`AppError` 宣告是 `enum AppError: Error, Equatable`（`LittleSprout/Errors/AppError.swift:22`），**沒有** conform `LocalizedError`；Swift 對這種純 `Error` 取 `localizedDescription` 會走 Foundation bridging，產出固定字串。實作者自己附的綠測試 log 就是證據——`.claude/evidence/LS-217/r3/m2-mutation-green.log:498`：

```
[push] LS-217 push registerForRemoteNotifications 失敗：無法完成作業。（LittleSprout.AppError錯誤0 。）
```

**失敗情境**：TestFlight 使用者說「收不到推播」，工程師撈 `subsystem:com.leoyeh.littlesprout category:push` 的 log，看到的每一筆都是這句——`AppError.rejected(message:"未登入，無法註冊裝置 token", code:"42501")`、`.validationRetryable(code:"22P02")`、`.network(message: URLError 敘述)` 三種完全不同的根因印出來一模一樣，`message`／`code` 兩個欄位（`AppError.map`，`AppError.swift:246-305` 明確保留下來供 log／除錯用）全部被丟掉。m3 的原始理由是「這正是『使用者說收不到推播』最可能的成因」，現在 Release 有一行 log 但沒有任何可分流的資訊，只比 `#if DEBUG print` 好在「知道失敗過」。

**建議修法**：改印 `String(describing: error)`（`AppError` 是 enum，會印成 `rejected(message: "…", code: Optional("42501"))`），或針對 `AppError` 取 `message`／`code` 兩欄分別帶 `privacy:`。順帶一提，若改印 message，`privacy: .public` 建議只留給 `code`、message 用預設（`register_device_token` 的錯誤訊息不回傳 `p_token`，今天不會外洩 token，但後端訊息內容不在本 repo 控制之下）。不擋合併。

### R3-m2（minor）`Config/Base.xcconfig:37-39` 的註解與實測相反：這個寫法**是**順序相依，照註解去搬行會靜默失效

`Config/Base.xcconfig:32`（`PUSH_ENTITLEMENT = NO`）／`:40`（`PUSH_ENTITLEMENT[sdk=iphonesimulator*] = YES`）

註解寫「SDK 限定的設定不看檔案裡的先後順序、看的是『比對得上目前建置的 SDK 就用它』，所以放在這裡（`PUSH_ENTITLEMENT = NO` 之後）純粹是就近註解，不影響效果」。我在快照上實測兩個反例（均 `xcodebuild -showBuildSettings`，實作者 worktree 未動）：

### m1（minor）`LittleSproutUITests/QA/QADriver.swift:196` — 點掉前置頁後的「同步點」是空斷言，一旦 tap 沒生效，訊息會退回原本無法辨識的那一條

`dismissPushPrepromptIfPresent()` tap 完 `稍後再說` 之後用 `try require(timelineHeading, "推播前置頁關閉後的時間軸", timeout: 15)` 當關閉的確認，但**這個斷言在 cover 仍然蓋著時也會立刻通過**：SwiftUI `.fullScreenCover` 蓋上去之後，底下時間軸的元素仍留在 XCUITest 的 a11y 樹裡。機械證據（QA R1 失敗時的 hierarchy dump，`.claude/worktrees/qa-test/.claude/evidence/LS-217/qa-e2e/browse-20260912-151026/diagnostics/`「App UI hierarchy for com.leoyeh_0_*.txt」）：同一份 dump 第 18 行 `StaticText … label: '時間軸'`、第 19 行 `Button … label: '新增回憶'`，第 57 行 `Button … label: '稍後再說'`——時間軸與前置頁同時存在於樹上。QA R1 之所以會失敗在「15 秒內沒等到『日記編輯器』」而不是「沒等到『新增回憶』」，正是同一個現象（按鈕找得到、tap 打在 cover 上沒作用）。

具體失敗情境：`稍後再說` 的 tap 若沒生效（例如 cover 正在做 present 動畫時 hit point 落在舊位置、或日後版面調整讓按鈕在捲動容器裡移動），`require(timelineHeading)` 依然立刻通過 → driver 繼續往下 → 在 `openEditor()` 死於「步驟 N：15 秒內沒等到『日記編輯器』」——正是 QA R1 FAIL 那條、當初讓排障繞遠路的訊息；本輪特地取的可辨識落點名「推播前置頁關閉後的時間軸」幾乎永遠不會被觸發（要「cover 消失且時間軸同時消失」才會）。

建議修法：把同步點換成 sentinel 消失——例如輪詢 `!pushPrepromptSkipButton.exists` 直到逾時，失敗訊息寫「點了『稍後再說』但推播前置頁沒有關閉」（同 LS-230 對 `InteractionRowUITests` 的「tap 後要有決定性同步點」修法）；要保留時間軸 require 就放在 sentinel 消失之後。列 minor 不列 major：happy path 已由 R5 三情境＋我這輪 browse 重跑各自驗過，這是 harness 診斷力的問題、不影響產品行為。
