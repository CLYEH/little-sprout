## 範圍

1. `scripts/ops/supabase-lock.sh` 新增子命令（沿用既有 mkdir-lock／holder 檔／死鎖回收機制，不另建第二把鎖）：
   * `--hold <label> [--max-minutes N]`（預設 30，上限 60）：取得 lock 後**不執行命令**，fork 一個守門子程序在背景持有（holder 檔 `cmd=hold:<label>`、記 `expires_at`），主程序印 holder pid 後立即返回；守門程序每 5 秒更新心跳、到 `expires_at` 自動釋放並印一行。
   * `--release`：只允許 holder pid 的祖先鏈（同 `--held` 判定）或同一 worktree 呼叫；釋放並印持有時長。
   * `--status`：持有中且為 hold 時多印 `label`／`剩餘分鐘`；等待訊息（既有每 30 秒一行）在遇到 hold 時改印「QA 持有中（<label>，剩餘 n 分）」。
   * 既有 `-- <命令>` 路徑不變：hold 期間其他 worktree 的 `db reset`／`run.sh` 照常排隊、沿用 `SUPABASE_LOCK_TIMEOUT`（預設 15 分鐘）——**hold 上限 30 分鐘大於等待逾時 15 分鐘**，等待者逾時會 fail loud 印出持有者 label，這是刻意的（QA 該在 15 分鐘內完成互動段，否則要拆段）；文件寫明。
   * 守門程序被 SIGKILL：既有「pid 不存在→回收」邏輯自然涵蓋；補測。
2. **自測** `scripts/ops/supabase-lock.test.sh` 加案：hold 後另一程序 `-- true` 等待且訊息含 label／`--release` 後立即取得／`--max-minutes` 到期自動釋放（用 `SUPABASE_LOCK_HOLD_TICK` 之類環境變數把心跳與到期縮成秒級，自測用）／非持有者 `--release` 被拒 exit 2／守門 pid 被 kill 後等待者回收。掛既有 CI `rules` job「Ops 腳本自測」step（**不改 step 名稱清單**，該 step 已含 supabase-lock）。

### Findings

**N1（minor，PLAUSIBLE）`scripts/ops/supabase-lock.sh:243` — `--release` 的「檢查後刪除」與死鎖回收有 TOCTOU，可能刪到第三者剛取得的鎖**

```
if read_holder && [ "$h_pid" = "$gpid" ]; then rm -rf "$lock"; fi
```

失敗情境：守門被 SIGKILL／crash（holder 檔仍寫著 `pid=<死守門>`）→ 持有者 `--release`：`alive gpid` 為假、跳過 kill 段 → 第二次 `read_holder` 看到 `h_pid=gpid` → **在 `rm` 真正動手之前**，另一 worktree 的等待者剛好跑完「is_stale → mv 到 tomb → 核對 → rm tomb → mkdir → 寫 holder」→ `--release` 刪掉的是等待者剛取得的鎖 → 兩個 worktree 同時對共用容器動手（正是 LS-70 要擋的事故）。

實測（把 `rm` 用 PATH shim 拖慢 1s 放大窗口，手法同既有自測的 `ps`／`mv` shim）：B 的命令還在跑，`--status` 已回 `free`、lock 目錄消失，`--release` 仍回 exit 0「已釋放」。**標 PLAUSIBLE、不列 blocker**：無 shim 的真實窗口只有 `[` 測試到 `/bin/rm` fork+exec 的 ~1–3ms，等待者要把 ~25ms 的回收＋取得整段塞進去，等於要求 releaser 在這兩條敘述之間被排程走開 ≥25ms；且正常路徑（守門還活著）不受影響——守門自己刪、releaser 第二次讀到的是新 holder 或沒有 holder，兩種都不刪。

建議修法：最後那步改用既有 `reclaim()` 同一套原子手續（`mv` 到 tomb → 核對 tomb 的 `pid`＋`started` 仍是那個守門 → 才 `rm -rf tomb`；不符就 `restore`），不要對 `$lock` 直接 `rm -rf`。附帶：mutation 測試把這一行改成無條件 `rm -rf "$lock"`，175 案**全綠**——這條保護目前沒有測試釘住（見 i6）。

**N2（minor，PLAUSIBLE）`scripts/ops/supabase-lock.sh:188` — `hold_owner_ok` 的 owner 腿對「已死的 pid」做祖先比對，缺 alive 檢查**

```
if [ -n "$h_owner" ] && is_ancestor "$h_owner"; then return 0; fi
```

檔頭自己寫了「agent 的 Bash 工具每次呼叫都是新 shell、owner 早已退出」——也就是這條腿平常比對的就是一個**死 pid**。失敗情境：hold 存續期間（≤30 分）OS 把 owner 的 pid 回收再指派給另一個 agent 的 Bash 工具 shell，該 shell 底下的任何 `-- <命令>`／`--held` 就被判成持有者、**跨 worktree 直接繞過排隊執行 reset**；`--release` 同一判定，也會讓外人釋放別人的 hold。macOS pid 要繞一圈（~1e5）才重用，30 分鐘內要撞上特定 pid 機率很低，故標 PLAUSIBLE。

建議修法（一行，不改設計意圖——owner 腿本來就只服務「同一個還活著的 session」）：`[ -n "$h_owner" ] && alive "$h_owner" && is_ancestor "$h_owner"`。

**N3（minor）`scripts/ops/supabase-lock.sh:196`／`:337` — label 沒過濾換行，可往 holder 注入 key，留下「造假 holder」的卡死 lock**
