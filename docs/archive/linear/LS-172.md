## 範圍

1. **Edge Function** `supabase/functions/push-dispatch`（比照 `purge-storage`：只接受 service_role bearer、verify_jwt 預設、非 POST 405、500 body 不外洩原始錯誤）：
   * 取件：`notification_events` 中 `sent_at is null` 且 `occurred_at < now() - interval '5 minutes'`（視窗已穩定）的列，**先 claim 再送**（`update … set sent_at = now() where id = any($1) and sent_at is null returning …`，同一列不會被兩次執行重送）；批次上限與分頁比照 purge-storage 的分段 dequeue。
   * 對象判定：同 `family_id` 的成員（`family_members`）扣掉 `actor_id`；扣掉「已封鎖 actor 的成員」（`blocked_users` 單向、限同家庭，[LS-149](https://linear.app/little-sprout-app/issue/LS-149/taskls-23-後端-檢舉封鎖owner-移除內容-rpccontent-reportsblocked-users) 語意）；沒有 device_tokens 的成員略過。
   * 文案（繁中，長輩可讀）：依 `kind`＋`event_count`＋`target_type` 彙總——例：`album`／`diary` 新增「爸爸新增了 50 張照片」「媽媽寫了一篇日記」；`comment`「阿嬤在你的日記留言」；`reaction`「3 個人喜歡了你的照片」；actor 顯示名稱取 `profiles.display_name`（`actor_id` 為 NULL 時用「家人」）；**PLAN 風險章：批次上傳只發一則彙總**。
   * APNs：`ApnsProvider` 介面（token-based auth：`APNS_TEAM_ID`／`APNS_KEY_ID`／`APNS_P8`／`APNS_BUNDLE_ID`／`APNS_ENV` 皆從 EF secrets 讀，缺任一即 fail loud 不送）＋ `StubProvider`（本機／CI：只記錄 payload、可注入 410）；HTTP/2 對 `api.push.apple.com`／sandbox。
   * 失效 token：APNs 回 `410 Unregistered`／`BadDeviceToken` → 刪 `device_tokens` 該列；其他錯誤記 log 不重試（本票不做重試佇列；已 claim 的列不回滾 `sent_at`——寧可漏送不重送，寫進 API.md）。
   * 可觀測：每次執行回傳／記錄 `{claimed, recipients, sent, failed, tokens_removed}`。
2. **SQL 面**（新 migration，版本號取 `date -u +%Y%m%d%H%M%S`）：`private.claim_notification_events(limit int)`（SECURITY DEFINER、只給 service_role）封裝 claim 邏輯＋對象查詢 `private.notification_recipients(event_id)`（含封鎖過濾），讓 EF 只做 HTTP 與文案；`notification_events` 加 `sent_at` 部分索引（待送列掃描）。
3. **排程**：本機以直接呼叫 EF 驗證；正式站排程（pg_cron＋pg_net 每分鐘 http_post，service_role 由 vault）**只寫進 API.md §10 部署清單，不在本票執行**（同 [LS-153](https://linear.app/little-sprout-app/issue/LS-153/task後端-軟刪與刪除帳號後-30-天自動永久清除排程pg-cron排程-edge-functiondb-列硬刪storage) 的接線模式，待 [LS-8](https://linear.app/little-sprout-app/issue/LS-8/phase-0-4註冊-apple-developer-program個人佔-bundle-id-與-app-名稱) 金鑰到位一併由 orchestrator 部署）。
4. 測試：deno 單元測試（文案彙總矩陣、對象過濾含封鎖、410 清 token、缺 secrets fail loud、claim 冪等）；`supabase/tests/` 補 SQL 案（claim 兩次不重疊、封鎖對象排除、無 token 成員略過、跨家庭隔離）；CI deno 版本沿用 [LS-151](https://linear.app/little-sprout-app/issue/LS-151/taskls-24-後端-edge-function-delete-accountservice-role-刪-authusersrpc) 鎖定。
5. `docs/API.md` §3 `notification_events`（發送側語意、`sent_at` 由 EF 寫）、§10 Edge Functions 章節新增 `push-dispatch`（呼叫方式、secrets、部署清單、漏送不重送的取捨）；`docs/PLAN.md` 推播段一句。

## M1（major・PLAUSIBLE・正式站才會踩）APNs JWT 簽一次就永久重用，isolate 活過 1 小時之後全部推播靜默失敗且永久遺失

**檔案**：`supabase/functions/push-dispatch/apns.ts:104-112`（`cachedJwt` 與註解「下一次 invocation 是全新的 provider 實例，天然過期」）、`supabase/functions/push-dispatch/index.ts:50`（`const apnsProvider = …` 在**模組層級**建構）。

**問題**：`buildRealApnsProvider()` 內的 `cachedJwt` 只在第一次 `send()` 時簽一次，之後永不重簽，也沒有任何過期判斷；而 provider 是在 `index.ts` **模組層級**建構的——一個 isolate 只會建一次，不是「每次 invocation 一個新實例」。apns.ts:106 的註解（「下一次 invocation 是全新的 provider 實例，天然過期」）與 index.ts:44-49 自己的註解（「同一個 isolate 存活期間的所有請求共用同一個 provider 實例……天然涵蓋到跨請求」）**互相矛盾**，而正確的是後者——所以「天然過期」這個讓它可以不寫過期邏輯的前提不成立。JWT payload 只有 `{iss, iat}`（apns.ts:63），Apple 的 provider token 自 `iat` 起**最長 1 小時**有效，逾時回 `403 ExpiredProviderToken`。

**失敗情境**：依 `docs/API.md` §10 規劃的部署（pg_cron 每分鐘打一次），isolate 會長時間保持溫熱。冷啟動滿 60 分鐘之後，**每一次 `send()` 都拿到 403 ExpiredProviderToken** → `invalidToken=false` → 只累加 `failed` 並 `console.log`，HTTP 仍回 200；而事件在 claim 階段就已經寫了 `sent_at`、依設計不重試，所以**這段期間的所有通知永久遺失**，外部只看得到 `{"failed": N}`。沒有任何告警或健康檢查會發現。

**標 PLAUSIBLE 的原因**：我無法在本機量測 Supabase Edge Function isolate 的實際存活時間（可能被平台回收得比 1 小時早），所以「多久會踩到」不確定；但「JWT 不會被重簽」這件事本身是程式碼上確定的，且 `docs/API.md` §10 也自己寫了「最長 1 小時」這個限制卻沒有對應的處理。

**建議修法**（小改動，二選一）：
- (a) 記下 `issuedAt`，`getJwt()` 發現超過 ~45 分鐘就重簽（Apple 要求：不得比 20 分鐘更頻繁、不得超過 60 分鐘）；
- (b) 或在 `send()` 收到 `403 ExpiredProviderToken` 時清掉 `cachedJwt`、重簽並重試一次（同時也涵蓋時鐘漂移）。
兩者都要順手把 apns.ts:106 那句錯誤註解改掉。**若 orchestrator 判斷「反正 LS-8 之前不會部署」而選擇不在本 PR 修**，也請不要只留在 review 記錄裡——這是部署當下就會生效的缺陷，應該進 LS-8 部署票的檢查清單或 LS-96 池，否則會在「APNs 終於接上」那天以「推播偶爾整段不見」的形式出現。

## m1（minor・效能／平行）派送全程序列化，單次 invocation 最壞情況 1000 事件 × N token 全部逐一 await

**檔案**：`supabase/functions/push-dispatch/handler.ts:186`（逐事件 `await deps.getRecipients`）、`:207-212`（逐 token `await send`）；`index.ts` 的 `BATCH_LIMIT=50`／`MAX_BATCHES=20`。

**問題**：一次 invocation 最多處理 1000 個事件，每個事件先一次 RPC round trip（N+1：1000 個事件＝1000 次 `notification_recipients` 呼叫），再對每個 token 逐一 `await` APNs HTTP 呼叫，全部序列。以 APNs 單次 ~50–150ms 估算，1000 事件 × 平均 2 個 token ≈ 100–300 秒——超過 Edge Function 的執行時間上限就會被平台中止；而被中止時，**已 claim 但還沒送的事件同樣永久遺失**（claim 先寫 `sent_at`、不重試）。平常量體小不會踩到，但這正是「佇列積壓時」最需要它可靠的時候。

**建議**：(1) 逐 token 改成有上限的併發（例如一次 8–16 個），APNs HTTP/2 本來就支援多路複用；(2) `getRecipients` 改成接受 `uuid[]` 的批次版本（或至少同一批事件併發查詢），把 1000 次 round trip 收斂成個位數；(3) 加一個時間預算檢查，剩餘時間不足就不再 claim 下一批（claim 前檢查最安全，因為還沒標記 `sent_at`）。三項任一都能顯著拉高上限，不必全做。

## m2（minor・可觀測性）`tokens_removed` 在刪除**之前**就累加，刪除失敗仍計入

## R2 新發現（皆 informational）

### R2-i1（informational・PLAUSIBLE）併發 8 條同時撞到 403 時，會各自強制重簽一把新 JWT

`apns.ts` 的 `getJwt(true)` 無條件重簽。R2 之後送出是併發的（8），若 JWT 真的過期，最壞情況是 8 個 in-flight 的 `send()` 幾乎同時拿到 `403 ExpiredProviderToken`，於是**各自重簽一把新 token**（毫秒內 8 把）。Apple 對 provider token 的更新頻率有限制（建議不超過每 20 分鐘一次，過快會回 `429 TooManyProviderTokenUpdates`），這批重試因此可能連帶失敗——而失敗即漏送（claim 已標記、依設計不重試）。發生前提窄（45 分鐘主動重簽已經讓 403 很罕見）、影響有界（重簽後 `cachedJwt` 就是新的，後續送出正常），所以只列 informational。便宜的修法：`send()` 進來時記下這次用的是哪一把（例如比對 `cachedJwt` 的 promise identity 或加一個 generation 計數），只有「還沒有人替我重簽過」時才 `getJwt(true)`，否則直接用別人剛簽好的那把重試。若不在本 PR 改，建議併進 LS-8 部署前檢查清單。

### R2-i2（informational）常駐 claim race 案例沒有真的釘住 `SKIP LOCKED`

我把 `claim_notification_events` 的 `for update skip locked` 改成 `for update`，再跑同一組 `push_dispatch_claim_race_{setup,s1,s2,verify}`——**三段全綠、verify 也綠**。原因：拿掉 `SKIP LOCKED` 之後 S2 會被 S1 卡住，等 S1 commit 之後 EvalPlanQual 重檢把那 5 筆（`sent_at` 已非 NULL）濾掉、繼續往下抓到另外 5 筆，最終集合一樣不重疊。也就是說這支測試釘住的是**「不重疊」這個正確性不變量**（有價值，而且確實是最重要的那條），但沒有釘住 `SKIP LOCKED` 本身要保護的「不阻塞」性質——`s2` 檔案裡「若是 0 筆，可能是 SKIP LOCKED 沒有正確跳過…反而被卡住等待」那句提示因此不會成真。建議補一條耗時斷言（例如 S2 記 `clock_timestamp()` 差值，必須明顯小於 S1 持有的 2 秒），就能同時釘住兩件事。

### R2-i3（informational）測試輔助表在 suite 跑完後留在 `public`

`push_dispatch_claim_race_setup.sql`／`push_dispatch_claim_vs_record_setup.sql` 各建一張 `public.ls172_*_capture`（setup 開頭有 `drop table if exists`，所以重跑安全），但 `run.sh` 的併發清理區塊只刪家庭與使用者，**不刪這兩張表**——suite 跑完後我確認兩張都還在。我另外把 `60_default_privileges.sql`／`65_fk_reverse_index.sql` 在殘留狀態下各重跑一次，**皆 rc=0**（不會誤紅，因為兩支檢查的對象不含這種臨時表），所以今天沒有實害；但它是留給其他 agent／後續測試的殘渣。建議在 `run.sh` 的 cleanup 補兩行 `drop table if exists`。

### R2-i4（informational）我量到的實際天花板：單一批次可能吃掉大半個時間預算

造一個 20 位成員 × 每人 2 支裝置的家庭、50 筆已穩定事件，一次批次 `notification_recipients()` 回**1600 列**（執行 5.5 ms——批次化本身很有效，索引齊全：`device_tokens_user_idx`／`family_members_user_idx`／`blocked_users_blocker_idx`／`blocked_users_blocked_idx` 都在，計畫在這個量體選 hash join，量體長大後會自然切回 index scan）。但 1600 個送出 job 在 `concurrency=8` 下是約 200 輪 APNs 往返，以每輪 50–150ms 估算約 10–30 秒——時間預算只在「批次之間」檢查，所以**單一批次仍可能吃掉大半甚至超過 60 秒預算**。`docs/API.md` §10 已經誠實記載了這個殘餘風險與「為什麼不做動態批次大小」的取捨，我認同這個取捨（本產品規模是 5 人家庭，不是 20 人）；這裡只是把實測數字留下，供日後真的踩到時直接對照：要動的旋鈕是 `batchLimit`（50）而不是 `concurrency`。
