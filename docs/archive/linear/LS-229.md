### m1 — major（PLAUSIBLE）｜`LittleSproutUITests/ContentActionsAX3UITests.swift:52`（＋ helper `:82-91`）

**問題**：本票唯一在 CI 紅過的那支測試裡，還留著一個與被修的 `isEnabled` 同型、且暴露在**同一個機制**（XCTest 事件後的 `Wait for app to idle` 在高負載下提早返回）下的一次性快照斷言：`XCTAssertTrue(lastReason.isHittable, "捲到底之後最後一個原因（「其他」）應該可以點到")`，緊接在 best-effort helper `scrollUntilAllHittable` 之後。實作者的掃描條件是「tap 後立即查詢狀態」，漏掉了同族的「swipe 後立即查詢狀態」。

**具體失敗情境**：helper 迴圈第 2 圈就可能提早收手——`if currentYs == previousYs { return }` 比的是「上一次 swipe 前」與「這次 swipe 後」的 `frame.minY`。只要**一次** `app.swipeUp()` 沒生效（事件被丟、或 runner 負載高使 swipe 後的 idle 等待提早返回、frame 讀到尚未套用捲動的舊值），兩組值就相同 → helper 立刻 return，此時六個原因列並未全部 hittable → `:52` 一次性斷言紅。注意迴圈並不會為此重試（`maxAttempts: 6` 的預算在這條路徑上用不到）。
**為何這條路徑在本票特別要緊**：我本機 trace（`LS-229-ax3trace.log`）顯示這支測試在 AX3 下**真的需要捲動**——helper 實跑 2 次 `Swipe up`（t=14.51s／15.77s），每次 swipe 到下一次讀 frame 之間只隔 0.7–1.1s，正是負載敏感區；而 `isEnabled` 那一處是同一個 tap 後 idle 等待保護下的純 in-process 狀態翻轉。兩者暴露在同一機制，只修其中一個，等於留著另一個落點。加上第一節第 3 點（`0 unexpected` 不能排除互動型失敗），無法主張「真正根因必定是 isEnabled」。
