## (1) `AvatarLoadCoordinator` 抽出前後語意逐行比對 — 等價，無行為差異

抽出後兩個呼叫端（`CreateChildView+Avatar.swift:51-72`／`EditChildView.swift:84-105`）逐字相同，只剩委派＋三分支 switch。逐項對照：

**順序改變是否安全（handoff 點名要 reviewer 覆核的那一點）——安全，而且是機械可證的**：新寫法把 `isLoadingAvatar = true`／`avatarLoadErrorMessage = nil` 放到 `generation += 1` **之前**。要出問題必須有第三方在這兩者之間插進來，也就是 `await avatarLoadCoordinator.load { … }` 這個 `await` 得是真的 suspension point。三條證據說不是：
1. SDK 實測：`iPhoneSimulator26.5.sdk` 的 `SwiftUICore.swiftinterface:13636` 是 `@preconcurrency @_Concurrency.MainActor public protocol View {`——conform `View` 的型別（含 extension 的 `loadPickedAvatar()`）整個被推導成 MainActor 隔離。
2. `AvatarLoadCoordinator` 標 `@MainActor`。同 actor 的 async 呼叫不換 executor、不 enqueue，callee body 接著同步跑到自己的第一個真 suspension（`try await operation()`），中間沒有 MainActor job 插得進來。
3. 專案是 **Swift 6 語言模式**（`project.pbxproj` `SWIFT_VERSION = 6.0`）——若呼叫端不是 MainActor，傳非 Sendable 的 non-escaping 閉包給 MainActor 方法根本編不過。

即使退一萬步假設有 hop，後果也只是「舊 task 的結果短暫寫入、新 task 完成後覆蓋」的暫態，終態仍由最新世代決定，不會留下錯誤狀態。仍記一條 informational（i2）建議把這個前提釘住。

**`@State` 由 `Int` 換成 class 實例**：`AvatarLoadCoordinator` 是 global-actor 隔離的 class（隱含 Sendable），`@State` 生命週期語意與原本相同（同一個實例跨 body 重繪存活）。唯一差別是改 `generation` 不再觸發 view 失效——但同一個同步區塊裡 `isLoadingAvatar` 一定會寫，畫面更新不受影響（少一次多餘失效，方向是好的）。
