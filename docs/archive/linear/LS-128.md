## 一、scope 逐項裁決（handoff 自陳的四項額外）

**(a) `thumb_path` UNIQUE — 合理防禦，接受。** 票面未列，但 `media` 既有定義就是 `storage_path text not null unique`（`supabase/migrations/20260822120000_init_schema.sql`，media 表 body）。鏡像它是 conformance（CLAUDE.md Rule 10），不是新發明。且 thumb_path 由 media_id 推導、正常流程撞不了號，不會誤擋合法用例。

**(b) 尺寸 `> 0` CHECK — 合理防禦，接受。** 同表既有 `width integer not null check (width > 0)`／`height` 同款。差別只在本票版本允許 NULL，那是票面要求的 nullable。

**(c) 三欄同 NULL／同非 NULL 一致性 CHECK — 合理防禦，接受。** 這是唯一真正沒有既有對應的新約束。但它擋的「有縮圖路徑卻沒有尺寸」對讀取端有實害（瀑布流沒有尺寸就會 layout shift），且與 API.md 訂的「三欄一次 INSERT」契約嚴格同構，不會擋掉目前設計裡任何存在的用例。綁死風險與 (d) 合流，見 minor 1。

**(d) thumb_* INSERT 後不可 UPDATE — 這不是本 PR 加的東西，不算 scope。** migration 一個 grant 都沒動（檔內無 `grant`／`revoke`）；不可 UPDATE 純粹是 `20260822120000_init_schema.sql:364` 那句欄位級 `grant update (taken_at, deleted_at, width, height) on public.media to authenticated` 的自然結果——新欄位預設就不在授權清單裡。本 PR 新增的只有「一條測試把這個既有事實釘住」＋「一句 API.md 把它升格成契約」。釘住是好事；**升格成契約那句話才是會綁死後續的部分** → minor 1 要求把代價同時寫進契約。

**與 PLAN §7 egress 防線的關係（orchestrator 點名的問題）**：不衝突於**目的**（目的是列表少載原圖，本票正是為此），但確實留下一類「永遠只能載原圖」的列。這不是現在該改 migration 的理由——票面明文不回填、正式站無真實資料、日後要補是一支非破壞性 migration（加欄位級 grant＋trigger 限制 NULL→非 NULL 單向），而且 service_role／migration 本來就繞得過欄位級 grant，所以「永遠不能補」在事實上只對**客戶端**成立。要修的是文件沒把這個代價寫下來。

## minor

### 1. `docs/API.md:250` 與 `docs/API.md:259-261` — 契約自相矛盾，設計鎖死未落在契約文件裡

`:250` 宣告「**不存在「先建 `media` 列、之後才補上縮圖」的合法路徑**」，但同一節 `:259-261` 又把縮圖產生失敗祝福為正常結局：「不阻斷整體上傳——三欄留空插入 `media` 列即可……**不需要重試整個上傳**」。兩句合起來的實際語意是：失敗路徑是官方認可的常態產出，而它產出的列**永遠補不回縮圖**。

**具體失敗情境**：使用者在記憶體吃緊的裝置上一次送 20 張（LS-125 的佇列上限），其中幾張縮圖產生失敗（HEIC 解碼、影片首幀抽取尤其容易） → 這些列 thumb_* 恆為 NULL → 依 `docs/API.md:1246-1248` 的退回規則，時間軸**每次滑到都簽全尺寸原圖** → 正是 PLAN §7 要堵的 egress 漏口，且客戶端零補救路徑（重試上傳會撞 `media` PK／`storage_path` UNIQUE）。

**修法（不動 migration，手術式，一句話）**：在 `docs/API.md:250` 那句後面補上後果——「三欄留空的列在目前的 grant 下客戶端無法事後補寫；日後若要支援補縮圖，需新 migration 開 `update (thumb_path, thumb_width, thumb_height)` 欄位級 grant，並以 trigger 限制只允許 NULL→非 NULL 的單向轉換（否則會一併放掉 `storage_path` 等級的不可變保證）」。目前這件事只活在 handoff comment 裡，API.md 才是契約的存放處，下一個人不該重新發現一次。

### 2. `supabase/tests/98_media_thumbnails.sql:28`／`:36` — `data_type` 被 select into 卻從未斷言（dead read）

第 1 段把 `data_type` 讀進 `v_col`，但只斷言 `column_name` 與 `is_nullable`。**失敗情境**：日後有人把 `thumb_width`／`thumb_height` 改成 `bigint`／`numeric`，或把 `thumb_path` 改成 `varchar(n)`，本檔第 1 段仍全綠——而這是全檔唯一驗欄位形狀的地方（`api-contract-check.sh` 是表／RPC 粒度，不驗欄位，見下方查證）。**修法**：加一條 `v_col.data_type` 的斷言（`text`／`integer`／`integer`），或把 select 清單裡的 `data_type` 拿掉。傾向前者。

### 3. `supabase/tests/98_media_thumbnails.sql:95`／`:112`／`:129`／`:147`／`:165` — 負案例只捕 SQLSTATE 類別，不驗 constraint 名稱

handler 寫 `exception when check_violation`／`when unique_violation`，不驗是**哪一條**約束擋的。我逐條核對過目前每個負案例確實只違反一條約束（見下方 mutation 核對表），所以**現在**鑑別力是對的；但 `media` 日後再加任何 CHECK，某個案例就可能「為了錯的理由變綠」。修法：handler 內 `get stacked diagnostics v_c = constraint_name` 並斷言名稱。

### 4. `supabase/migrations/20260902101842_media_thumb_path.sql:60-61` — UNIQUE 的建索引方式與 NULL 索引項

`add constraint ... unique (thumb_path)` 取 ACCESS EXCLUSIVE 鎖、非併發建索引；btree 也會替（過渡期占多數的）NULL 列建索引項。**目前完全不成問題**（票面「無真實資料」，media 近乎空表），純記錄：日後在有量的表做同型變更，線上做法是 `create unique index concurrently` + `add constraint ... using index`；想省 NULL 索引項則是 partial unique index，代價是不再是 table constraint、與 `storage_path` 的既有寫法分岔。目前選擇跟既有 `storage_path` 一致，conformance 優先是對的判斷。

### 5. `docs/API.md:253-255` — 平行機會沒寫進契約

上傳順序寫成 ①原檔 → ②縮圖 → ③INSERT 的編號步驟。①②之間**沒有資料相依**，後續 iOS 票（`MediaUploadService` 補縮圖）完全可以把兩個 PUT 併發跑（`async let`／TaskGroup，並配並發上限），但編號很容易被讀成必須序列化——20 張佇列若逐一序列化兩個 PUT，等待時間直接翻倍。建議在 §3 補半句「①②無資料相依，可並行 PUT」。
