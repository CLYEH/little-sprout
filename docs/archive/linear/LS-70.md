**M1　`scripts/ops/supabase-lock.sh:131-149`（`reclaim`）＋`:169-179`：死鎖回收會殺掉「剛取得、holder 還沒寫完」的活鎖 → 兩個 holder 同時跑 `supabase db reset`**

`reclaim()` 把 lock `mv` 到 tomb 後，只有在 `[ -f "$tomb/holder" ]` 成立時才核對 pid／started；**tomb 沒有 holder 檔時直接跳過核對、無條件 `rm -rf "$tomb"`**（:138、:146）。而剛取得鎖的人在 `mkdir`(:152) 到 holder 落地(:179) 之間有一段空窗——這段要跑 `git rev-parse --show-toplevel`＋`git symbolic-ref`(:169-170) 兩次 fork，本機實測 **60–130 ms**。

失敗時序（A、B 都在等同一把死鎖）：
1. B 的 `is_stale` 讀到舊 holder（pid 已死）→ 呼叫 `alive` fork `ps`（~5-10 ms）；
2. 這段期間 A 完成 mv→核對→rm→`mkdir`，成為新 holder，接著進入 60-130 ms 的 git 空窗；
3. B 從 `ps` 回來，`reclaim` 的 `mv` 搬走的是 **A 的活鎖**；tomb 內沒有 holder → 跳過核對 → `rm -rf` 殺掉 A 的鎖，並印出「回收死鎖（持有者 pid <舊的死 pid>）」這種與事實不符的訊息；
4. B `mkdir` 成功 → **A、B 同時在 lock 內執行命令**＝ LS-57／LS-66 事故本身。

已重現（把既有空窗以 PATH shim 放大成可控：`ps` 對死 pid sleep 0.3s、`git rev-parse --show-toplevel` sleep 1.5s，**沒有改動任何 repo 檔案**）：off=12–30 ms 的啟動間隔下穩定重現，log 為 `A-START / B-START / B-END / A-END`（兩個 START 都在任何 END 之前），兩邊 stderr 都印「回收死鎖 持有者 pid 999999 已不存在」，而期間 holder 檔只看得到其中一個 pid——**巡檢／`--status`／其他等待者完全看不出有兩個持有者**。未加 shim 的真實機率：需要「先有一把死鎖 ＋ ≥2 個等待者 ＋ B 的 mv 落在 A 的 60-130 ms 空窗」，以 1s 輪詢的相位均勻分布估約 10%／每次爭搶回收，非天方夜譚。

這也讓檔頭 :20-21 與 COLLABORATION §7（`docs/COLLABORATION.md:203`）「先 mv 到 tomb 再核對，**不誤殺剛重取的鎖**」的保證不成立。

建議修法（兩者都做，都很小）：
- `reclaim()` 中 tomb 沒有 holder 檔時，**不得直接 rm**：要求 tomb 目錄 age > 30（＝`is_stale` 當初無 holder 分支所依據的同一個證據），否則搬回去／放棄。剛 `mkdir` 的鎖 age＝0，這條就把窗關掉了。
- 把 `wt=$(git rev-parse …)`／`br=$(git symbolic-ref …)`（:169-170）**移到等待迴圈之前**算好——它們不依賴持有鎖。空窗從 ~100 ms 縮到 ~1 ms，殘留機率再降兩個數量級。
- 附帶：自測 ⑥ 只涵蓋「一開始就沒有 holder 的鎖不回收」，沒有涵蓋「已判定 stale 之後、mv 到的卻是別人剛建的鎖」。修完請補這條負向測試，否則 gate 對自己沒牙。
