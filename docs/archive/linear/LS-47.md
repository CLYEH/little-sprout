## 描述

使用者需求（2026-08-24）：「建立家庭之後，還要可以建立數個寶貝 profile哦（有些家庭不只一個寶貝）」。

## 現況

* 資料模型**已支援**：`children (id, family_id, name, birthday, avatar_url, created_at)` 一對多掛家庭；`albums`/`diaries` 有 `child_id?`（PLAN.md §資料模型）。孩子檔案規格：姓名/暱稱、生日、大頭照、自動年齡標記（「1 歲 3 個月」）。
* **缺 UI 流程**：C/D 兩軌都只設計到登入/加入/邀請/建立家庭，沒有寶貝 profile 畫面。

## Spec 待定（開設計前釐清）

1. 建立家庭 onboarding 是否接著「新增第一個寶貝」（建議：是，但可跳過）？
2. 寶貝管理入口位置（設定？家庭頁？）；新增/編輯/刪除權限（僅管理員？）。
3. 多寶貝時主畫面/相簿的切換方式（分頁？下拉？全部+單寶貝篩選？）。
4. 刪除寶貝的資料處置（照片/日記掛在 child_id 下）——需破壞性保護。

## 後續

Spec 定案 → ui-designer 出 .pen 設計稿（設計 gate ≥3 輪）→ 實作。依賴：[LS-46](https://linear.app/little-sprout-app/issue/LS-46/設計定稿合併c-基準使用者指定調整-designlittlesproutpen) 定稿合併先行（沿用定稿語彙：褪色相紙、蠟筆字標、token 色票）。

## 留言（2）

### 2026-08-24T20:00:37.065Z · Chih-Lin Yeh · `dfd4765c`

**Orchestrator 對四個 Spec 問題的建議方案（供使用者晨間裁決；資料模型現況：`children` 一對多、`albums.child_id?`／`diaries.child_id?`、`feed_items.child_id`＋`get_family_timeline(p_child_id)` 已支援全部/單寶貝篩選）**

1. **建立家庭 onboarding 接「新增第一個寶貝」**：是——建立家庭成功頁直接接「幫寶貝建檔」（名字／暱稱、生日、大頭照可略），**可跳過**（相簿/日記的 child_id 本就可 NULL）。理由：沒有寶貝的家庭時間軸空得沒有意義；跳過保留給「先把家人拉進來」的使用者。
2. **入口與權限**：寶貝管理放「家庭」頁（與成員管理同層，不是設定深處）；新增/編輯 owner＋member（contributor）皆可，**刪除僅 owner**。理由：多半是爸媽（member）在填資料，但刪除是破壞性動作。
3. **多寶貝切換**：時間軸頂部一顆「全部｜寶貝 A｜寶貝 B」的分段（≤3 個直接排、>3 個變下拉），預設「全部」；相簿/日記發佈時必選歸屬寶貝（可多選？——建議**單選＋允許不指定**，避免 album_media 多對多再擴）。後端 `get_family_timeline` 已支援，UI 零後端成本。
4. **刪除寶貝的資料處置**：**不硬刪**——寶貝軟刪（`deleted_at`），其照片/日記保留、child 篩選項隱藏、「全部」仍可見；30 天內可還原；硬刪走 §10 帳號刪除同一套破壞性流程。理由：誤刪一個孩子的所有回憶不可逆，且 feed_items FK 已設 `on delete set null (child_id)` 但那是最後防線。

若採納：Spec 定案 → ui-designer 依 LS-46 定稿語彙出「寶貝建檔／寶貝管理／時間軸切換」三張 .pen（設計 gate ≥3 輪）→ 後端小切片（children 軟刪欄＋RPC）→ 實作票。

### 2026-08-25T01:02:48.209Z · Chih-Lin Yeh · `dbdc6363`

## 使用者定案（2026-08-25）：四題照建議
① 建家庭後接「幫寶貝建檔」，可跳過；② 管理入口在家庭頁，新增／編輯 owner＋member，刪除僅 owner；③ 時間軸頂部「全部｜寶貝A｜寶貝B」分段（>3 下拉），發佈時單選歸屬、可不指定；④ 刪寶貝＝軟刪 30 天可還原，照片日記保留。
