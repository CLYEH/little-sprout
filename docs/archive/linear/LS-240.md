## Findings

### M1（major）`scripts/ops/review-demo-seed.sh:741-781` — 重試把非冪等的 POST 原樣重送；物件其實已落地時 Storage 回 HTTP 400（`KeyAlreadyExists`），被本函式歸類成「永久性錯誤、不重試」直接中止

**具體失敗情境**：`storage_put()` 第一次嘗試把整個 body 送出去了、伺服器也真的寫進去了，但回應階段斷掉（curl exit 56＝receiving 失敗、exit 28＝逾時，兩者依定義都發生在 body 送出之後；或閘道 504——正是 LS-96 池項 `3f23757a` 那次事故的形狀）。腳本判定可重試 → 1s 後對**同一個 path** 再 POST 一次 → Storage 回 duplicate → `is_retryable_http` 不含它 → 印 `✗ 上傳失敗（curl exit 0，HTTP 400，不重試）` 並 `exit 1`。本票要救的正是這個情境，重試在這條路徑上救不到，而且因為 `-o /dev/null` 把 body 丟掉了，操作者只看得到光禿禿的「HTTP 400」，看不出「其實已經存在」。

**實測（本機 storage-api，非推測）**：同 path 重送回 `400`，body `{"statusCode":"409","error":"Duplicate","message":"The resource already exists","code":"KeyAlreadyExists"}`——注意**線上狀態碼是 400 不是 409**，所以「把 409 當成功」這種修法用 HTTP code 判斷會落空；加 `-H "x-upsert: true"` 重送則回 `200` 且 `Id` 與首傳相同（覆寫成功）。探針全程在 `bash scripts/ops/supabase-lock.sh --hold`／`--release` 之間、只碰 `ls240review/2026/09/` 測試路徑並已刪除。已驗證的是「後果」；「觸發條件（504／56 之後物件確實已落地）」是重送非冪等 POST 的標準風險，未實地製造，這一半屬推論。

**建議修法**：`storage_put()` 第 2 次起的嘗試加 `-H "x-upsert: true"`（首次維持現狀，保留「不該存在卻存在」的訊號），自測補一組「第一次 curl 56、第二次回 400/KeyAlreadyExists」的樣本並斷言最終成功；或至少把回應 body 留下來寫進 `✗` 訊息，讓操作者一眼看出要改用 `--storage-only`。

### m1（minor）`scripts/ops/review-demo-seed.sh:783-795` — `storage_exists()` 自己沒有重試，任何暫時性失敗都被讀成「物件不存在」

**具體失敗情境**：`--storage-only` 續傳時 list API 偶發 502／連線中斷 → `resp` 是空字串 → 不含 `"name"` → 回傳「缺」→ 對一個其實存在的物件重新上傳 → 撞上 M1 的 400 → 整支中止。本票的主題就是「暫時性錯誤要有韌性」，判缺這一半卻沒有。建議把 `storage_put()` 的重試抽出來共用，或至少把「curl 非 0／回應不是合法 JSON 陣列」與「確實回 `[]`」分開——前者 fail loud 比誤判成缺漏安全。

### m2（minor，效能）`scripts/ops/review-demo-seed.sh:783-822` — `--storage-only` 對同一個資料夾打 40 次 list，且素材白做

40 個路徑全部落在同一個 prefix（`<family>/2026/09`）底下，一次 `limit: 100` 的 list 就能列完再在本地比對；正式站 40 次來回每次 100–300ms。分頁不是問題（每次 `limit:1`＋`search` 全檔名，本來就不會分頁），問題純粹是次數。另外素材準備排在探測之前，所以「40 個全在」時仍會合成 2 支 mp4＋跑 7 次 sips——而 40 條路徑只依賴靜態 `photo_sources` 的副檔名，不需要素材就能先算出來。順帶：`storage_put()` 的 curl 沒有 `--max-time`／`--connect-timeout`，卡住的連線仍可能無限期掛住（就是 handoff 描述的 HEAD 掛住情境），也讓「curl exit 28 可重試」實務上幾乎觸發不到。
