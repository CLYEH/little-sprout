## M1（major）`scripts/ops/patrol.sh:239` — 螢幕鎖定偵測在真機輸出格式下永遠不會觸發；㉗ 自測的 stub 是照實作寫的，對這顆缺陷零鑑別力

現行判斷式要求 `"` 後面接「空格 `=` 空格」：

    if ioreg -n Root -d1 2>/dev/null | grep -q 'CGSSessionScreenIsLocked" = Yes'; then

但 `CGSSessionScreenIsLocked` 不是 Root 的頂層屬性，而是 `IOConsoleUsers` 這個 inline dict 裡的鍵；`-d1` 只印 Root 這一層，該 dict 一律以 compact 形式印出、巢狀鍵值**無空白**。本機實跑 `ioreg -n Root -d1`（未鎖定）原文：

    "IOConsoleLocked" = No
    "IOConsoleUsers" = ({"kCGSSessionOnConsoleKey"=Yes,"kSCSecuritySessionID"=100023,"kCGSSessionSystemSafeBoot"=No,...})

LS-190 comment `3dbaa03c` 當時**真的鎖定中**量到的字串也是 `CGSSessionScreenIsLocked=Yes`（無空白）；同票另一則 comment 寫的是帶前綴的 `kCGSSessionScreenIsLocked`——現行 pattern 對這兩種寫法都不匹配。

具體失敗情境：使用者螢幕真的鎖著（正是 LS-190 事故當下的狀態）時跑 `patrol.sh` 或 SessionStart hook，「螢幕鎖定」段印 `  ok`、`[screen-lock]` 旗標不出現，§4-b 排障順序 (b) 想機械化的那一步反而給出反向誤導（比沒有這段更糟：下一個人會據此排除螢幕鎖定）。

複驗（我實跑，唯讀）：用本機真實 `ioreg` 的輸出形狀＋LS-190 記錄的鎖定字串組一支 stub，對本 head 的 `patrol.sh` 跑兩次——

    # 真實格式（"IOConsoleUsers" = ({...,"CGSSessionScreenIsLocked"=Yes,...})）
    == 螢幕鎖定（LS-220；鎖定中會讓模擬器 Keychain 回 -34018，長得像 QA e2e 逾時失敗，§4-b 排障順序 (b)）
      ok
    # patrol.test.sh ㉗ 用的合成格式（頂層、" = Yes"）
    == 螢幕鎖定（LS-220；...）
      ⚠ 主機螢幕鎖定中——模擬器 Keychain 會回 -34018，QA e2e／互動式驗證卡住前先請使用者解鎖（§4-b 排障順序 (b)）

（唯一未取得的地基：我不能鎖使用者的螢幕取 ground truth，上面的 stub 是用本機真實未鎖定輸出的形狀＋LS-190 記錄的鎖定字串重建的。但 `-d1` 決定了該鍵只能出現在 inline dict 內，兩條獨立證據也一致，所以不標 PLAUSIBLE。）

連帶問題：`scripts/ops/patrol.test.sh:1224-1232` 的 stub 只印 `+-o Root …` 換行 `    "CGSSessionScreenIsLocked" = Yes`，這個形狀是照著實作的 grep pattern 造的、不是照 `ioreg` 真實輸出造的，因此 ㉗ 四條案例與那條 mutation 負控（拿掉偵測 → 轉 `ok`）全部成立，卻對「pattern 與真機格式對不上」零鑑別力（Rule 8：測到的是實作、不是意圖）。
