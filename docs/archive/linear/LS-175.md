## 1. 結構發現查實（派工第 1 點）——**成立，且比實作者說的更強**

實作者主張「`media` INSERT 當下拿不到相簿／日記歸屬，只能走 `target_type='family'`」。我逐條核實：

- **schema**：`supabase/migrations/20260822120000_init_schema.sql:118-137` 的 `create table public.media (…)` 區塊內 grep 不到任何 `album`／`diary` 欄位——`media` 確實沒有 `album_id`／`diary_id`。
- **iOS 上傳流程**：`LittleSprout/Services/Diary/MediaUploadService.swift:193-199` 的 `insertMediaRow` 是 `try await client.from("media").insert(row).execute()`；掛進日記是另一支 `LittleSprout/Services/Diary/SupabaseDiaryAPIClient.swift:61-67` 的 `attachMedia(diaryID:familyID:mediaIDs:)` → `client.from("diary_media")…`。兩者是兩個獨立的 PostgREST 請求＝兩個獨立交易，`insertMediaRow` 在 `MediaUploadService.swift:84`／`:140` 兩處呼叫點都是先完成 media 列、之後才由呼叫端做 attach。
- **有沒有「同交易寫入 junction」的路徑（派工要求：若有就列 major）**：**沒有**。`grep -rn "insert into public.media" supabase/migrations/*.sql` → **0 筆**，全 repo 沒有任何 SECURITY DEFINER RPC 會寫 `media` 列（更不用說同交易寫 junction）；Swift 端 `from("media")` 也只有 `MediaUploadService` 這一處 INSERT。
- **而且即使有同交易路徑，結論也不變**：`album_media`／`diary_media` 的複合外鍵 `references public.media (family_id, id)` 要求 media 列先存在，junction 只能後寫；本票的 trigger 是 **statement-level AFTER INSERT**（不是 deferred constraint trigger），在 `media` 那一句 INSERT 結束時就觸發，同交易稍後才寫的 junction 列它也看不到。所以「trigger 觸發當下這個資訊不存在」是結構性的，不是實作選擇。

**裁定：接受此設計，不列 finding。** migration 檔頭、`docs/API.md` §3「`media` 來源（LS-175）」、`docs/PLAN.md` 三處都如實記錄了理由與取捨（`kind='album'` 與 `kind='media'` 各發各的、不合併），沒有把「做不到」寫成「做了」。

### m1（minor・測試鑑別力）`104_` 沒有釘住「`event_count` 是張數、不是批次數」——票文驗收第一條的核心不變量

**為什麼還是 minor 而不是 major**：產品行為我另外實測是**對的**（單一敘述 50 列 → 1 筆事件 `event_count=50`；500 列 → +500），而且 iOS 端目前逐張 INSERT，實務路徑有被案例 1 覆蓋。這是「未來有人改壞不會被抓到」的風險，不是現在就錯。

### R1-i1（informational・harness）`migration-breaking-check` 沒有 `ALTER TYPE … ADD VALUE` 這條規則，而本票正好是它的反例

gate 的 B1–B6 全是 DDL 形狀（policy／revoke／函式／rename／schema），列舉加值不在其中，所以 `ALTER TYPE ADD VALUE` 永遠 rc=0、不會要求 PR body 交代。但**加一個列舉值的實質風險就是「既有消費端不認得新值」**——LS-149 加 `report` 之後 push-dispatch 的守衛沒跟上，後果是整批靜默漏送（就是 m2 那條）；本票加 `media`／`family` 時實作者是靠人工警覺才同步守衛的。建議把「`ALTER TYPE … ADD VALUE` → BREAKING（或新增一類 `ENUM-EXTEND`）」加進 gate，強制 PR body 列出消費端盤點（TS 型別守衛、`CASE` 無 ELSE 的 PL/pgSQL、iOS 端 enum 解碼）。這條建議適合入 LS-96（size S，價值直接對應一次真實事故的預防）。

`index.ts` 在模組層級呼叫 `Deno.serve()`（LS-151 起的既有形狀），所以測試不能 import 它——`isNotificationKind`／`isContentTargetType` 與 `claimEvents` 的列轉換／「未知 kind → 整批視為失敗」這條路徑**一個測試都沒有**（`handler.test.ts` 打的是注入的 `claimEvents`）。這正是 m2 那個缺口能存活這麼久的結構原因。建議把兩支守衛與行轉換搬到 `handler.ts`（純函式、無副作用），`index.ts` 只留下 `Deno.serve` 與依賴組裝——搬完之後 m2 那條就能被一個 3 行測試釘住。

### R1-i3（informational）media 事件的 advisory lock 鍵是 per-family，比其餘四種來源更粗

`record_notification_event()` 的鎖鍵含 `target_id`；media 事件的 `target_id` 恆為 `family_id`，所以**同一家庭的所有上傳都序列化在同一把 advisory lock 上**（其餘四種來源是 per 日記／相簿／留言）。實測成本可忽略（500 列單句 13.7 ms，鎖只在其中幾毫秒），而且同家庭的上傳本來就已經在 `families.storage_used_bytes` 的列鎖上序列化（額度 trigger），沒有新增一類序列化。純記錄，不需要改。

### R1-i4（informational・產品語意）合併事件的 `actor_id` 是「最近一次觸發者」，多人同時上傳只會顯示最後一位

沿用 `record_notification_event()` 的既有語意（`104_` 案例 2 就明文斷言「actor_id 換成最新觸發者」）。實務效果：爸爸傳 30 張、媽媽接著傳 30 張且都落在同一個 5 分鐘視窗 → 只發一則「媽媽新增了 60 張照片」。這與其餘四種來源一致、不是本票引入，但 media 是最容易多人同時操作的來源，值得讓產品端知道這個顯示語意（要改的話是 `record_notification_event()` 的設計，屬另票）。
