**複驗**：`j7WwV` 內出現白邊＋角托結構的 print instance ≥1；標題 `textAlign` 非 `center`；通知卡與 print 絕對矩形有交集（`cross_parent_collision` 會報，屬刻意出血，收據 `classification` 註明）。

## MAJOR（本輪新增）

### NEW-1 已按讚態造成 34pt 版面位移，違反十條 #10「狀態改變不得移動版面」〔結構驗〕

`un8pC`／`vvcIX` Interaction Row 是水平流（`gap:"$sp-block"`，無 `justifyContent`），其中 `v3Q0L`／`hdxEH` Heart Group、`R782aG`／`vnbON` Like Toggle **都沒有固定 `width`**。兩態標籤字數不同（「愛心」2 字 vs 「已按愛心」4 字），於是：

> Notes `MmGIb` 自述：「`IgqGF`/`VZ0wV` 實測 **w=84~118** h=47」

84 → 118 = **右移 34pt**，被推走的是 `Count Zone`（按讚名單入口）與整顆 `Comment Button`。使用者按下愛心的當下，手指底下與旁邊的兩個目標都跑掉——這正是這條硬約束存在的理由，對手抖／視力退化的長輩尤其。三板（`IgqGF`／`VZ0wV`／`Qzz3r`）各 2 個，共 6 個 Like Toggle 全中。

**改法**：`Like Toggle` 六個全部改固定 `width`，取兩態較寬者（預設字級 118；AX3 依 `MmGIb` 的 140 實測值取兩態較大者），`justifyContent:"start"` 保持 icon 貼左。**不要**改成兩態同字數（「愛心」／「已按」）——那會犧牲已按愛心的清楚語意。
**複驗**：`Get` 六個 Like Toggle，同板兩態 `bounds.width` **必須相等**；再 `TakeScreenshot` 兩張並列，`Count Zone` 與 `Comment Button` 的 x 相同。

### NEW-2 AX3 的 Count Zone 硬寫 44×44，裝不下 40pt 的計數字〔結構驗〕

`h3bdOM`／`U8pwO`（`Qzz3r`）是 `width:44, height:44` 的**固定**框，子節點 `Yb4wD`／`zNAER` 用 `fontSize:"$fs-note"`，而 `$fs-note` 在 ax3 theme 下是 **40**（`[{17, default}, {40, ax3}]`）。40pt 字的行高（40×1.2 ≈ 48）**已超過 44 的容器高**。

比對同板的 `V6rrC6` Like Toggle：AX3 下由 `MmGIb` 實測為 **140×80**——會長大。唯獨 Count Zone 被釘死在 44×44，兩個相鄰的熱區一個 80 高一個 44 高，而且小的那個裝著放大 2.35× 的字。

**這一類五支掃描結構上抓不到**：`row_overflow` 只驗右緣，其餘四支都不管「子節點比父節點高」。R1 的 BL-1 是靠我手算 padding 抓到的，這次同理——**固定尺寸容器 × 隨字級縮放的子節點，是本專案的系統性盲區**，建議 designer 在 Notes 開一節列出全稿所有「固定寬高且含文字」的容器。

**改法**：`Qzz3r` 的兩個 Count Zone 覆寫為 `width:56, height:80`（與同列 Like Toggle 的 80 高對齊；56 容納 40pt 單字數字並保留 ≥44 熱區）。預設字級的 44×44 不動。
**複驗**：`Get` `h3bdOM`／`U8pwO` 與其子 text 的 bounds，**子 height ≤ 父 height**；且父 height ≥ AX3 `$fs-note` 行高。

### NEW-3 為了閃避掃描 regex，把準確的節點名改成錯誤的名字〔結構驗〕

`ZfAQX` 由 LS-152 繼承的 **`Tab Bar Clearance`** 被改成 **`Nav Bar Spacer`**。動機清楚：正典腳本的 `OVERLAY_RE = /Action Bar|Tab Bar|Capsule|Footer|Toast|Banner/` 會把名字含「Tab Bar」的節點當成覆蓋層，於是這個純 spacer 造成 `text_occlusion` 假陽性。

問題是新名字**是錯的**：這個 spacer 讓出的是**底部 Tab Bar** 的空間，而 iOS 的 **Nav Bar 在頂部**。ios-dev 讀到「Nav Bar Spacer 151pt」會以為要在頂部留白。**用一個會誤導實作的名字，換掉一個掃描器的假陽性——代價付錯地方了。**

**改法（兩選一，都可機械複驗）**：
(a) 改回準確且不撞 regex 的名字，如 `Bottom Chrome Clearance` 或 `Tabbar Clearance`（無空格即不命中 `Tab Bar`），並在 Notes 註明改名純為避開掃描器命名比對、語意不變；
(b) 保留 `Tab Bar Clearance`，把假陽性寫進收據 classification（掃描器對「無 fill、無可見子節點的 spacer」誤判為覆蓋層，屬 harness 缺口，另開票）。
**我偏好 (b)**：正確的做法是修偵測器，不是改稿去迎合它。
**複驗**：`Get ZfAQX` 的 name 不含「Nav Bar」；若走 (b)，收據 `text_occlusion` 有對應 classification。
