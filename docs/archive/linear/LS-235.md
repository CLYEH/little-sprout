## Findings

### M1（major）`scripts/ops/prod-purge-health.sh:144` — 真實通道下這支腳本不存在成功路徑，健康與壞掉印同一個 ⚠

**重現（我剛跑的）**：在已 link 的主 checkout 執行 `bash scripts/ops/prod-purge-health.sh` → 只印 `⚠ 查無資料（purge_runs 為空、或查詢/解析失敗，見上方訊息）`、exit 1（沒有印「supabase db query --linked 執行失敗」那條，代表 CLI 回傳 rc=0、查詢其實是成功的）。把 `build_query()` 產出的同一段 SQL 原樣餵 `supabase db query --linked --output-format json`，正式站回了完整 7 列資料。

**根因**：CLI 的 `--output-format json` 是**多行 pretty-print 的信封**——`{ boundary, rows: [ { coalesce: [ … ] } ], warning }`，陣列跨多行；第 144 行 `printf … | grep -oE` 用的 `\[.*\]` 樣式是**逐行**比對，沒有任何一行同時含 `[` 與 `]` → 萃取出空字串 → 走進第 149 行的「查無資料」分支。fail loud 的方向沒錯，代價是這支腳本在真實通道下永遠印不出 `✓`：全 2xx、連線壞掉、purge_runs 真的空，三種情境的輸出與 exit code 完全一樣。票文驗收第 2 條（部署後隔日印最近一次 2xx）照現況必然過不了。

**為什麼 CI 全綠沒擋住**：12 組自測全部經 `--fixture` 注入「已經整理好的裸陣列」，完全繞過 `fetch_rows_json()` 的萃取層——缺陷剛好落在唯一沒被覆蓋的那一層。

**建議**：raw 直接交給下面那段既有的 python 解析信封（我單獨驗過：stdout 是純 JSON，CLI 升級提示走 stderr），取 `json.loads(raw)["rows"][0][<欄位名>]`；並補一組「餵真實 CLI 信封」的自測樣本（讓 `--fixture` 同時吃得下信封與裸陣列，或把萃取抽成可單獨測的函式），否則同一類缺陷下次仍然只會在正式站現形。

### m1（minor）`supabase/functions/purge-storage/queue_retry.ts:53-54` — 實際只重試 2 次、退避只用到 1s→2s，`4000` 是取不到的死值

### m2（minor）`supabase/functions/purge-storage/index.ts:390-392`／`index.ts:415-417` — 「已重試 N 次」把嘗試次數當成重試次數，差一

`readAttempts` 最小值是 1（`queue_retry.ts:70`），所以「一次都沒重試」的永久性錯誤（4xx／SQL 錯）會在 log 印「重試 1 次後放棄」、在 500 回應的 error 字串寫「已重試 1 次」。重現：`permission denied for table purge_storage_queue` → `attempts=1`（自測第 3 條已釘住這個值），操作者看到的訊息卻說重試過。改成 `readAttempts - 1`，或把字面改成「嘗試 N 次」。

### m3（minor）`supabase/functions/purge-storage/index.ts:570-576` — `attempts` 的語意註解在多批次時是錯的

註解寫「恆為 1 代表完全沒有重試，>1 代表期間有暫時性錯誤發生過但最終讀取成功」。但迴圈是「讀到空批次才 break」（`index.ts:426` 的 `if (!queue || queue.length === 0) break;`），處理 1 個批次的健康 invocation 會讀 2 次、2 個批次讀 3 次——**零重試也會 attempts ≥ 2**。這個欄位正是本票要給週檢看的觀測點，語意寫錯會直接誤導判讀（看到 attempts=3 會以為那晚有兩次暫時性錯誤，其實只是佇列有兩批）。建議改成「本次 invocation 的讀取總次數」，另外累計 `queueReadRetries`（Σ(attempts−1)）給「是否發生過暫時性錯誤」用。

### i1（informational，PLAUSIBLE）`queue_retry.ts:35-45` — 允許清單是 Node 用語，Deno fetch 層錯誤可能漏接

supabase-js 會把 fetch 層的 reject 轉成 `FetchError: <原訊息>`；Deno 的原訊息常見形狀是 `error sending request for url (…): client error (Connect) …` 或 `connection closed before message completed`，都不含 timeout／`fetch failed`／`network error` 字樣（後兩者是 Node/undici 的措辭）→ 會被判成永久性錯誤、第一次就放棄，正好是這票想接住的那類故障。我沒有實際造出一次 Deno fetch 失敗來驗證訊息原文，標 PLAUSIBLE。可補 `/error sending request/i`、`/connection closed/i` 兩條樣式。

### i2（informational）重試預算 × 呼叫端 60 秒逾時
