## 描述

來源：使用者 2026-08-23 提問「前後端實作前要不要先凍結 API 契約」。orchestrator 建議：**不做傳統凍結，做契約成品化＋機械對帳**（理由見下）；使用者若否決本票可取消。

## 為什麼不是「凍結」

1. 本專案的 API＝Supabase 自動生成（PostgREST）＋SECURITY DEFINER RPC——**契約的真身就是 migrations＋錯誤碼＋RLS 行為**，且後端側已被測試機械化（60_ RPC 白名單、80_ 行為測試、LS001-LS017 逐碼測）。
2. UI 尚未實作、無跨團隊協調成本——現在硬凍結只會製造變更申請的官僚成本，卻沒有要保護的消費者。
3. 本協作型態的真實風險不是前後端漂移，是 **agent 漂移**：實作 UI 的 ios-dev agent 用猜的（RPC 名／參數／錯誤碼語意）而不讀 migrations——migrations 又長又難消費。

## Scope

1. `docs/API.md`：RPC 逐支簽名＋語意（誰能呼叫、副作用、併發語意）、錯誤碼表（LS001-LS017＋後續）、client 會讀的表形狀（feed_items 等）、storage 路徑規約——**單一可消費文件**。
2. **對帳 gate**（前饋必有反饋）：CI 檢查 API.md 的 RPC 清單與 DB catalog 一致（比照 60_ 白名單式——新增／改簽名沒更新文件即紅；文件列了不存在的 RPC 也紅）。
3. Swift 側：`LSError` enum 對映全部錯誤碼＋列舉式單元測試（契約的消費端也被測）。
4. 變更紀律寫進 COLLABORATION 一段：**某 RPC 的 UI 首次上線後，該 RPC 傾向 additive-only**（加 v2 不破壞）；上線前可自由改，但 doc＋tests 同 PR 動（gate 會逼）。
