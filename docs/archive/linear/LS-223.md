## Findings

### N1（**minor**）`orphan_scan.ts:344-347` invocation 層跨家庭樣本上限沒有測試釘住

把迴圈裡的
```
if (invalidSample.length < 5) {
  invalidSample = invalidSample.concat(result.invalidSample).slice(0, 5);
}
```
改成無條件 `invalidSample = invalidSample.concat(result.invalidSample);` → **9 案全綠**。新增的樣本上限測試打在 `scanFamilyOrphans` 這一層（家庭層 `slice(0,5)` 拿掉會紅），但 F1 真正保護回應 JSON 的是 invocation 層這一道：家庭層只保證「每個家庭最多貢獻 5 筆」，沒有這道 guard 時 `orphanInvalid.sample` 會長成 5×（有不合規路徑的家庭數），也就是 F1 一開始要修掉的「長度隨數量線性成長、無上限」原封不動搬到 invocation 層。

**具體失敗情境**：某個 bucket 有 40 個家庭各含 3 個不合規物件（例如某次 service_role 側寫入繞過 storage insert policy 造成），未來有人重構這個迴圈（例如覺得 `if` 多餘而拿掉、或把累計搬進 helper）→ `orphanInvalid.sample` 一次回 120 筆路徑進 EF 回應與 cron 的 `net._http_response`，而 CI 129 案全綠、沒有任何訊號。

**建議修法**：`scanOrphanStorageObjects` 層補一案——≥2 個家庭、每家 ≥3 筆不合規，斷言 `result.invalidSample.length === 5` 且 `result.invalidCount === 總筆數`（現有 F2 那案已經有 3 家庭的治具，加一個家庭的不合規路徑即可，約 10 行）。程式碼本身今天是對的，這是 Rule 8 的「測試要釘住意圖」缺口，不是 live bug，所以是 minor 不是 major。

### N2（**minor**）`docs/API.md:426-428` 回應欄位清單沒有跟著加 `orphanInvalid`

該句逐一列出回應 JSON 的 `orphanEnqueued`／`orphanDropped`（括號註明 LS-222 新增）／`orphanScanCompleted`／`orphanScanCursor`，本 PR 新增的 `orphanInvalid` 沒有進去——而這個 PR 正好改了同一段往上 7 行的 §3 正文（`:407-419`），也就是說改文件的那一手就在旁邊。LS-222 加 `orphanDropped` 時是有寫進這句的，先例明確。§6 的 purge-storage 小節同樣沒提 `orphanInvalid`。

**具體失敗情境**：QA 或接排程巡檢的人依 §3／§6 對照 EF 回應欄位（本 repo 的 `api-contract-check` 只驗 RPC／表，不驗 EF 回應形狀，沒有機械 gate 會抓），會把 `orphanInvalid` 當成未文件化的意外欄位，或反過來在寫巡檢 SQL／告警時漏掉它——而它正是 F1 想提供的那個觀測出口。

**建議修法**：在 `:426` 那句的 `orphanDropped` 之後補一項「`orphanInvalid`（LS-223 新增，`{count, sample}`，形狀不合規路徑的真實計數＋前 5 筆樣本；`count` 是 `orphanDropped` 的子集合，見 N5）」，一句話的事。

### N3（informational）classify 失敗分支的 `considered` 語意沒有測試

`orphan_scan.ts:191`（`classified.ok === false` 時 `considered: pastGraceCandidates.length`）改成 `considered: 0` → 9 案全綠。這是本 PR 明確用註解宣告的**刻意選擇**（「classify 本身失敗，無法區分合規／不合規——維持舊行為」），意圖是讓 classify 持續失敗的家庭仍然吃掉預算、不會讓一次 invocation 無止境往下走。缺口在本 PR 之前就存在（該分支從來沒有測試），本 PR 只是重寫了 return 字面值，所以不算本次引入。若採納 N1 的補測，順手加一案（`classifyPaths` 回 `{ok:false}` → `considered` 等於候選數）成本很低。

### N4（informational・**PLAUSIBLE**）F2 移走了「不合規路徑」這一側的工作量上界

改法之後，一個家庭若全部候選都不合規就對預算貢獻 0，round-robin 會繼續往下走；極端情況（大量不合規物件橫跨多數家庭）一次 invocation 會把整個 bucket 走完，每個家庭各一輪 `listPaged`（year／month／file 三層）＋一次 `classifyPaths` RPC，可能撞上 cron 的 `timeout_milliseconds := 60000`。我標 PLAUSIBLE 且只列 informational，理由有二：(a) 今天不可達——storage insert policy 的 `WITH CHECK` 就是 `is_media_object_path()`，客戶端寫不出不合規路徑（LS-222 R1 F1 已如此判定）；(b) 同型的上界缺口**本來就存在於寬限期那一側**（還在寬限期內的物件同樣不計入 `considered`，一個全是新物件的 bucket 早就會被整個走完），F2 沒有引入新的類別。真的踩到時要動的旋鈕是「每次 invocation 最多走幾個家庭」，不是把 F2 改回去。

### N5（informational）`orphanDropped` 與 `orphanInvalid.count` 是包含關係，回應／文件都沒說
