#### M2｜新增的 race 測試驗不到它宣稱驗的那把鎖；而鎖真正吃重的那條路徑沒有測試
`supabase/tests/concurrency/diary_children_race_s2.sql:29-33`

```
if v_elapsed < 0.5 then
  raise exception
    'FAIL 併發：S2 的 update_diary_entry 沒有被 S1 阻塞（僅等待 % 秒）—— update_diary_entry 開頭的 `for update` 沒有真的鎖住日記列',

我做了 mutation 實測：把 `update_diary_entry` 逐字複製成一支 `update_diary_entry_nolock`，**只拿掉 `for update`**，用完全相同的兩連線腳本重跑——

```

MUT 終態 child_ids={...004}  body=S2 改的內容

兩條斷言（阻塞 ≥0.5 秒、終態＝S2 的完整集合）**都照樣通過**。原因是 RPC 內部本來就有 `update public.diaries d set body = ...`，那一句自己就取了列級寫鎖，S2 在那裡被擋 1.82 秒；`for update` 對這個場景的終態沒有增益（READ COMMITTED 下後續 statement 各自取新 snapshot，終態一樣是後 commit 那方的完整集合）。所以錯誤訊息裡那句歸因是錯的，而這個 case 對「鎖有沒有被拿掉」是完全不敏感的。

**真正吃重的地方沒被測到**：`set_album_children`（`supabase/migrations/20260902011514_diary_album_multi_child_tags.sql:576-604`）**完全沒有對 `albums` 下 UPDATE**——

```sql
select a.* into v_album from public.albums a where a.id = p_album_id for update;
...
delete from public.album_children ac where ...;
insert into public.album_children ...;
```

這裡 `select ... for update` 是兩個並行覆蓋呼叫之間**唯一**的序列化手段。而 `supabase/tests/run.sh:371-378` 只加了 diary 那一組 race case。

**具體失敗情境**：有人把 `set_album_children` 的 `for update` 拿掉（或把 delete/insert 移到取鎖之前）——兩個連線同時對同一本相簿覆蓋成互斥的集合 {B,C} 與 {D}，各自的 DELETE 依自己看到的舊集合算「多的」，兩組 INSERT 交錯落地，終態可能是 {B,C,D} 這種合併結果。整個測試套件不會有任何一條紅。（實作目前是對的——我確認鎖在、順序也對；紅的是這件事沒有反饋。）

**建議修法**：補一組 `album_children_race_*`（同樣 4 檔形狀，S1 覆蓋 {B,C}、S2 覆蓋 {D}、verify 終態不得混合）；並讓 diary 那組能真的分辨鎖（例如改成斷言「取得鎖之後才動連結表」的順序性，或把等待斷言的歸因文字改成誠實描述是 `UPDATE diaries` 在擋）。
