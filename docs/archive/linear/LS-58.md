## 範圍

* 對照 PLAN 資料模型：`comments`、`reactions`、`device_tokens`（`register_device_token` RPC 已存在）現況盤點；缺的補齊（索引、軟刪、反向索引）。
* 寫入路徑：`create_comment`／`update_comment`（作者限 contributor）／`set_comment_deleted` 已由 [LS-52](https://linear.app/little-sprout-app/issue/LS-52/db-安全albums-updatecomments-update-owner-分支不限欄位-owner-可改寫他人相簿標題與留言內文) 建立；`toggle_reaction`（同一 user×target 唯一、冪等）；`comments` INSERT 是否收斂 RPC-only（比照 diaries）由本票裁量並在 API.md 明寫。

* 推播基礎：`notification_events`（或等價）表＋trigger：留言/愛心/新日記/新相簿寫入時產生待送事件（彙總策略：同 target 同 5 分鐘視窗合併）——**只做資料面**，發送由 Edge Function 票。
* RLS：成員可讀本家庭；作者可改自己；owner 可軟刪（走 RPC，只 SET deleted_at）；被踢出/降級規則對齊 [LS-48](https://linear.app/little-sprout-app/issue/LS-48/taskls-21-後端-diaries-schema-補全時間軸查詢-rpcrls測試)/[LS-52](https://linear.app/little-sprout-app/issue/LS-52/db-安全albums-updatecomments-update-owner-分支不限欄位-owner-可改寫他人相簿標題與留言內文)。
* 測試：角色矩陣（含已離開/降級）、冪等 reaction、分頁邊界、trigger 事件產生、併發（雙 toggle）；mutation 自證；50_ 效能探針走 RPC 本體。
* API.md §2/§3/§4/§5/§9 同步（gate 會擋）；新錯誤碼補 `LSErrorCode`（error-codes gate）。

### BLOCKER-1　`notification_events` 合併鍵不含 `family_id`，可被跨家庭挾持／吞掉通知

`supabase/migrations/20260825020000_comments_reactions_notifications.sql:519-532`（`private.record_notification_event`：advisory lock 鍵 L520、合併 SELECT L523-532）；契約面同源 `docs/API.md` §3「彙總策略：同一 `kind`＋`target_type`＋`target_id`」。

合併鍵是 `(kind, target_type, target_id)`，**唯獨少了 `family_id`**，但寫進去的列帶 `family_id`。這個鍵預設「一個 target_id 只屬於一個家庭」——而 schema 明文放棄保證這件事（多型關聯無 FK，migration L90-92 自己寫了「target_type／target_id 不驗證目標是否存在」）。兩者相加，合併視窗變成跨家庭共用的。

**具體失敗情境**（不是 UUID 猜測；被踢出的前成員手上本來就有該家庭的 album／diary／media id）：前成員 X 開一個自己的家庭 A，對受害家庭 V 的相簿 id 呼叫 `create_comment(A, 'album', <V的相簿id>)`；5 分鐘內 V 的真正成員在同一本相簿留言 → 兩者合併成**同一列**，且那列的 `family_id` 是 A。LS-22 的 Edge Function 依 `family_id` 決定通知對象（API.md §3 自己這樣寫），結果是 V 的成員收不到推播、A 收到一則指向自己讀不到的 target 的推播，且 `actor_id` 是 V 的成員（推播文案會帶出對方 `display_name`）。X 只要每 5 分鐘打一次就能持續壓住 V 對該 target 的所有留言／按讚通知。

複現（本機 `supabase db reset` 後）：

```
docker exec -i supabase_db_little-sprout psql -U postgres -d postgres --no-psqlrc <<'SQL'
... (建 V/A 兩家庭與 V 的相簿 b1；delete from public.notification_events;)
-- 攻擊者以家庭 A 對 V 的相簿留言
select public.create_comment('…f2','album','…b1','攻擊者佔位留言');
-- V 的成員對同一本相簿留言
select public.create_comment('…f1','album','…b1','受害者的真留言');
select kind, family_id, target_id, event_count, actor_id from public.notification_events where kind='comment';
SQL
```
實測輸出（只有一列，family_id 是攻擊者的 f2）：
```
  kind   |              family_id               |              target_id               | event_count |               actor_id
---------+--------------------------------------+--------------------------------------+-------------+--------------------------------------
 comment | c1000000-…-0000000000f2 | c1000000-…-0000000000b1 |           2 | c1000000-…-0000000000a1(受害者)
```

**建議修法**（一處，兩行）：`record_notification_event` 的 advisory lock 鍵與合併 SELECT 都補上 `p_family_id`——lock 鍵改成 `p_family_id::text || ':' || p_kind::text || ':' || …`，SELECT 補 `and e.family_id = p_family_id`；同步改 `docs/API.md` §3「彙總策略」的鍵描述，並在 `87_` §7 加一條「兩個家庭對同一 target_id 的事件不得合併」的斷言（現有 §7 全部在同一個家庭內，抓不到）。這是本票核心交付物的鍵設計，且已寫入的列之後再遷移比現在改貴，建議在本 PR 內修完，不要留給 LS-22。

### 應修-1　`notification_events` 對 `service_role` 也沒有 grant——唯一的預期消費者讀不到

`supabase/migrations/20260825020000_comments_reactions_notifications.sql:452-499`；`docs/API.md:77`、`docs/API.md:298`（皆寫「只有 `service_role`（LS-22 的 Edge Function 用）能讀寫」）；PR body 同樣宣稱「僅 `service_role` 可讀寫」。

實測這句是假的：

```
docker exec -i supabase_db_little-sprout psql -U postgres -d postgres --no-psqlrc -c "\dp public.notification_events"
 public | notification_events | table | postgres=arwdDxtm/postgres+
        |                     |       | service_role=Dxtm/postgres
```
`Dxtm` ＝ TRUNCATE/REFERENCES/TRIGGER/MAINTAIN，**沒有 r/a/w/d**。實跑：
```
set role service_role; → SELECT / UPDATE notification_events 皆 42501 permission denied for table notification_events
```
原因是 `pg_default_acl` 裡 postgres 在 public schema 對 tables 的預設只給 service_role `Dxtm`（`postgres | public | r | {postgres=arwdDxtm/postgres,service_role=Dxtm/postgres}`）。既有表不受影響是因為它們的實際使用者是 `authenticated`（有逐表明文 grant）；`notification_events` 是第一張「只給 service_role」的表，於是這個預設破口第一次真的咬到。service_role 的 `BYPASSRLS` 只跳過 policy，跳不過 grant。

`87_comments_reactions_notifications.sql:724-745` 只有反向斷言（authenticated／anon 無 grant），**沒有 service_role 的正向對照**；而且 L724 的註解把 `postgres`（表 owner，本來就不受 grant 限制）當成「service_role 等級的存取」，正是這個 bug 沒被抓到的原因。

**建議修法**：migration 補 `grant select, update on public.notification_events to service_role;`（送出流程只需要讀＋標記 `sent_at`；要不要給 delete 由 retention 策略決定），`87_` 補一條 `has_table_privilege('service_role', 'public.notification_events', 'select'/'update')` 的正向斷言並修掉 L724 的措辭。這個「不要依賴會因環境而異的平台預設，自己 migration 釘住」的作法在本 repo 已有先例——`20260822120300_harden_default_privileges.sql` §2 對 sequences 就是這樣處理的，理由一字不差適用。

### informational（請在 handoff 逐條寫明處置：修 / 不修＋理由 / 轉票）

**I1　`private.notify_*` 的逐列迴圈把 statement-level trigger 的好處抵銷掉了**
`…notifications.sql:563, 584, 607, 627`——四支都是 `for r in select * from new_rows loop … perform private.record_notification_event(…)`。檔頭 L547-549 宣稱「比照既有 `feed_sync_*` 慣例」，但 `feed_sync_*`（`20260822120100_triggers.sql:111-129`）是 set-based 的單句 `insert … select … from new_rows`；這裡是 O(N) 序列往返，每列各取一次 advisory lock。實測（同一交易內，5 萬列批次）：
```
insert 50000 comments（trigger 開）: 26868.341 ms
alter table public.comments disable trigger comments_notify_insert;
insert 50000 comments（trigger 關）:   538.371 ms
```
50 倍。四張來源表在產品上目前都是一次一列（RPC 寫入），所以線上影響≈0；但 `50_rls_plan_no_percall_subquery.sql` 新增的 5 萬則灌測讓該檔案多花約 27 秒（本機實測整檔 32.7s）。若要修，方向是把合併改成「部分唯一索引 `(family_id, kind, target_type, target_id) where sent_at is null` ＋ `insert … select from new_rows … on conflict do update`」，順帶連 advisory lock 都可以省掉（也一併解掉 BLOCKER-1）。

**I2　migration 檔頭對 PR body 的引述不成立**
`…notifications.sql:31-32` 寫「PR body 標成「comments 直接 INSERT/UPDATE 自本 PR 起一律 42501」」——`gh pr view 85 --json body` 全文沒有這句，也沒有 `BREAKING` 字樣。（規約上不算違規：COLLABORATION §6「LS-25 之前全部 RPC 視為上線前」，`BREAKING:` 段落此時非必需。）但這正是本 PR 順帶在修的 LS-52 F1「文件指向錯地方」的同一類缺陷，請二選一：把那句話真的加進 PR body，或改掉 migration 註解。

**I3　`toggle_reaction` 的收回路徑忽略 `p_family_id`**
`…notifications.sql:224-227`——`delete from public.reactions where target_type/target_id/user_id` 沒有 `family_id` 條件（與 `reactions_target_user_key` 一致，但與參數語意不一致）。實測：同一人在家庭 B 對 B 的相簿按讚後，改用家庭 A 的 `p_family_id` 對同一 target 呼叫 → 回傳 `false` 並把家庭 B 的那一列刪掉：
```
 in_b: t → reactions(family_id=f2) = 1 筆
 toggled_via_a: f → remaining = 0
```
只能動到呼叫者自己的反應，不是越權；但 UI 會顯示「已收回」而實際收回的是另一個家庭的紀錄。建議在 `docs/API.md` 的 `toggle_reaction` 條目明寫「唯一鍵不含 `family_id`，`p_family_id` 只用於授權與新增列的歸屬，收回路徑跨家庭生效」。

**I4　`occurred_at` 用 `now()`（交易起始時間），且與未來 LS-22 sender 有一個未序列化的視窗**
`…notifications.sql:529, 536`。實測併發兩筆留言合併正確（S2 在鎖上等 ~2s 後 `event_count=2`，符合預期），但寫入的 `occurred_at` 是 S2 的**交易起始**時刻（21:18:42.44），比它實際 commit（21:18:44.45）早 2 秒——被鎖擋住的時間完全沒有反映進「5 分鐘穩定視窗」。另外 `record_notification_event` 取 advisory lock，而 LS-22 的 sender 若只做 `update … set sent_at = now() where sent_at is null and occurred_at < now()-5min` 而不取同一把鎖，會有「sender 讀到列 → trigger 併發把 `event_count` 加上去 → sender 標記已送」的漏送窗口。請把「sender 必須取同一把 advisory lock（或用 `for update skip locked`）」寫進 LS-22 的票文，別讓它變成 LS-22 才發現的隱含契約。

**I5　測試裡一句無效斷言**
`87_comments_reactions_notifications.sql:349`：`select body, deleted_at into v_body from public.comments where id = v_comment;` — plpgsql 對「多欄位 INTO 單一純量」會靜默丟棄第二欄（已實測確認不報錯）。所以「已軟刪除的留言仍可編輯」這段從頭到尾沒有斷言那則留言真的被軟刪過；若 `set_comment_deleted` 哪天靜默 no-op，這段仍會綠。補一個 `v_deleted timestamptz` 並斷言 `is not null`。

**I6　`get_reaction_counts` 的兩個小缺口**
`…notifications.sql:392-414`：(a) 沒有成員檢查，非本家庭成員靠 `reactions_select` RLS 靜默回空集合——與同一 PR 的 `list_comments`（明確 42501）行為不一致；`docs/API.md:602` 只寫「誰能呼叫：該家庭任一角色的成員」，沒有像 `get_family_timeline` 條目那樣明寫「傳別人家庭不報錯、回 0 列」，呼叫端讀了會誤以為會拿到錯誤。(b) `p_target_ids` 沒有長度上限，而同 PR 的 `list_comments` 對 `p_limit` 有 `least(greatest(…,1),100)` 的夾制——建議至少在 API.md 寫明建議批次大小，或比照加一個 `array_length` 上限。維持 `security invoker` 這個裁量本身我同意（見下）。

**I7　harness 缺口（給 orchestrator 的 lesson learning）**
`.github/workflows/ci.yml:123` 的破壞性關鍵字清單只認 `DROP …`／`TRUNCATE`／`DISABLE ROW LEVEL SECURITY`／`ALTER … TYPE`，**不認 `REVOKE … FROM authenticated` 與 `ALTER POLICY … (false)`**。本 PR 收回 `comments` 的 INSERT/UPDATE、`reactions` 的 INSERT/DELETE 並把四條 policy 改成 `false`，對呼叫端的效果等同 DROP POLICY，卻完全沒觸發 LS-45 gate（LS-48 對 diaries 也是同一寫法、同樣沒觸發）。此刻無實害（UI 未上線），但這是「規則有、gate 沒有」的一個實例。

**I8　`notification_events` 無 retention**
已送出（`sent_at is not null`）的列沒有任何清理路徑，也沒有涵蓋它的索引（`notification_events_pending_idx` 是 `where sent_at is null` 的部分索引）。表會單向成長。票文沒要求，記下來給 LS-22 或後續票。
