## Findings

### M1（major）`supabase/functions/push-dispatch/handler.ts:236-239`、`241-244`：多則文案宣稱「N 人」，但 `event_count` 是事件數、不是人數 — 資料端根本給不出這個數字

具體失敗情境（可重現，非 PLAUSIBLE）：

- 阿嬤在 5 分鐘滾動視窗內對媽媽同一篇日記連留 3 則留言 → `private.notify_comment_created()`（`supabase/migrations/20260825020000_comments_reactions_notifications.sql:702-710`）依 `(family_id, target_type, target_id)` 分組、拿 `count(*)` 當 `p_increment`；`record_notification_event()` 同檔 671 行 `event_count = e.event_count + p_increment`、同時 `actor_id = p_actor_id`（覆寫成最新觸發者）→ 併成單列 `event_count=3, actor=阿嬤`。
- `claim_notification_events()`（`supabase/migrations/20260904095205_push_dispatch.sql:104-141`）回傳欄位只有 `actor_id`／`actor_display_name`／`event_count` — **整條管線沒有任何 distinct actor 計數**。
- 實跑純函式（輸出存 `scratchpad/LS-219-r1-probe.log`）：`buildMessageBody("comment", 3, "diary", "阿嬤")` → `阿嬤等 3 人留言了`。實際只有 1 人留言。
- reaction 支更容易踩到：`toggle_reaction()`（同 migration 298-308 行）是 delete-else-insert，同一人把愛心收回再按會產生新的 INSERT → 再觸發一次 `notify_reaction_added`；同一份 probe log 裡 `buildMessageBody("reaction", 3, "media", "阿嬤")` → `阿嬤等 3 人按了愛心`，實際 1 人。

為什麼列 major 而非 minor：

- (a) comment 支是**本 diff 引入的退步**：舊文案「你的{標籤}收到了 N 則新留言」的 N 就是事件數、與資料一致；改成「等 N 人」之後才開始宣稱一個資料庫給不出來的數字。（reaction 舊文案「N 個人喜歡了你的{標籤}」已有同類問題，屬既有、非本次引入，但本次沿用並把同一句型擴大到 comment。）
- (b) 同一支函式正上方的檔頭註解（`handler.ts:210-224`，LS-172／LS-175 落地時 merge-review 認可的先例）明文寫「這裡不虛構一個資料庫給不出來的數字」，`album` 支正是為此放棄帶張數。本次改字違反同一份就地成文的不變式。
- (c) handoff「風險」欄列了 diary／album 多則量詞與 report 多則類推，**唯獨沒有列這一項**，照現況會靜默出貨。

建議修法（三選一，需 orchestrator／文案 owner 拍板，不建議實作者逕自選）：

- 留在 XS 範圍：多則改回事件數句型（保留舊的「你的{標籤}收到了 N 則新留言」，或改成「{actor}等人留言了 N 則」），**並**比照 `album`／`diary` 把這個「票文字面 vs 實際可用資料」的分歧補進 `handler.ts` 檔頭既有的分歧記錄區塊與 `docs/API.md`。
- 若產品確定要「N 人」語意：SQL 端需補 distinct actor 計數（`notification_events` 加欄，或 `claim_notification_events` 回傳 `count(distinct actor)`），已超出本票 XS 範圍，應另開票並先 block 本票。
- 若裁定近似可接受：至少把分歧寫進上述兩處。現行 `docs/API.md` 只寫「點名最近一位 actor，不是匿名彙總」，那句說明的是 actor 來源，沒有說 N 的語意。

### m1（minor）`handler.ts:272-274`、`docs/API.md:2782`：report 文案的量詞「則」套到 `media`／`album` 標籤不成話

`TARGET_LABEL` 是 `media→照片`／`album→相簿`，代入後實跑輸出（同 `scratchpad/LS-219-r1-probe.log`）：`家庭裡有一則照片被檢舉，請前往處理`／`家庭裡有一則相簿被檢舉，請前往處理`／`家庭裡有 3 則照片被檢舉，請前往處理`。「則」只搭得上日記與留言。**單則句型是 LS-189 0905 補註的逐字原文**（補註用 `{label}` 泛寫，量詞衝突是繼承來的、不是實作者引入），多則「N 則{label}」則是實作者依單則類推、把同一個問題複製到多則分支。列 minor 不列 major：不影響正確性，且改動需文案 owner 同意。建議（供 owner 裁）：改成不帶標籤量詞的「家庭裡有一則檢舉待處理，請前往查看」／「家庭裡有 N 則檢舉待處理…」，一次解掉四種 label。

## Findings

### m1（minor）`handler.ts:250-251` 的多則鐵律沒有涵蓋 `media`，而 `media` 是唯一真正可達的多則分支

判準原文寫「**多則文案的鐵律：只能引用 event_count；任何『N 人』字樣都禁止**」，字面上是無例外的全稱句，但四行之下的 `handler.ts:288` 仍是 `` `${actorDisplayName}新增了 ${eventCount} 張照片` `` —— 多則分支引用了 `actorDisplayName`，不符鐵律第一子句（符合第二子句：沒有「N 人」）。

這不只是措辭問題，因為歸屬對象在 `media` 上真的會錯：`private.notify_media_created()`（`supabase/migrations/20260904170933_media_notification_events.sql:55-70`）**只 group by `family_id`**，彙總鍵是 `(family_id, 'media', 'family', family_id)` ——整個家庭共用一個桶。5 分鐘滾動視窗內媽媽上傳 3 張、爸爸上傳 2 張會併成同一列，`event_count=5`、`actor_id` 被覆寫成最後一位上傳者，文案輸出「爸爸新增了 5 張照片」（爸爸只傳了 2 張）。對照之下，R2 把 `diary`／`album` 多則改成「家人」的理由正是「無法確認合併的多筆事件是否同一人觸發」——而那兩支的彙總鍵含各自的 `target_id`（日記／相簿自己的 id），`event_count>1` **根本不可達**（純防禦性）。等於防護加在兩支死分支上，唯一活的多則分支反而沒加。

**為什麼列 minor 而不是 major**：(a) `media` 文案是 LS-175 既有、本票（R1／R2）從未觸碰，要求在此票改它屬 scope 擴張；(b) `docs/API.md` 已明確處理過 `media`（「未受 LS-219 R2 M1 影響——`media` 的 `event_count` 本來就只用來組數字，從未宣稱人數」），可見是想過後的判斷而非疏漏；(c) 使用者可見的錯誤歸屬是既有行為，本 diff 未使其惡化。

**但仍須處置的理由**：那句 API.md 的免責只擋掉「宣稱人數」這一項指控，沒有回應真正的殘留問題（把家庭層級的彙總數歸給單一具名者）；而 `handler.ts` 的鐵律連免責都沒有。維持現狀等於用一條讀起來像全稱的規則，把 `media` 的既有不準確度默示為「已合規」——這正是 R1 M1 當初能溜過去的機制。
