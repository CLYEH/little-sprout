### F1（major）`LittleSprout/Features/Auth/EmailSignInView.swift:72` — `onCodeSent(model.trimmedEmail)` 在 await 之後重讀可變狀態，寄碼與驗證仍可能拿到不同 email

本票 scope 第 1 條的括號寫得很明白：「`OTPVerificationView` 的 `verifyEmailOTP(email:)` 路徑用**同一個** trimmed 值（避免寄碼與驗證的 email 不一致）」。目前的作法達成了「兩邊都是 trimmed」，但沒達成「同一個值」——`trimmedEmail` 是 `email` 的 derived 計算值，而 `send()` 是在 `await model.sendCode()` **回來之後**才第二次去讀它。跨過那個 suspension point，`email` 可能已經不是寄碼時的那個了。

**具體失敗情境**（時序）：
1. 使用者輸入 `a@b.com`，按「寄送驗證碼」。
2. `sendCode()` 同步跑完 `guard EmailFormat.isValid(trimmedEmail)`、`isSending = true`，然後 `await authStore.sendEmailOTP(email: trimmedEmail)` —— 參數在 suspend 前就求值完畢，**送出去的確實是 `a@b.com`**。此時 MainActor 被釋出，網路往返期間（正常數百 ms，弱網數秒）主執行緒是空的。
3. 使用者在等待期間發現打錯、直接在欄位裡改成 `typo@x.com`。這條路徑是通的：`LabeledTextField`（`LittleSprout/DesignSystem/…/LabeledTextField.swift:22`）沒有 `disabled` 參數，`EmailSignInView` 也沒傳任何禁用旗標——`isSending` 只餵給 `PrimaryButton(isLoading:)`，輸入框在送出中全程可編輯、鍵盤也還在。binding setter 呼叫 `updateEmail("typo@x.com")`，`email` 被改寫、`errorMessage` 一併清空（沒有任何視覺阻擋）。
4. `sendCode()` 回 true → 第 72 行讀到的 `model.trimmedEmail` 已經是 `typo@x.com` → `path.append(.otpVerification(email: "typo@x.com"))`（`WelcomeView.swift:41-42`）→ `OTPVerificationModel(email: "typo@x.com")`。
5. 驗證碼實際寄到 `a@b.com`（使用者收得到），但 `OTPVerificationModel.verify()`（`OTPVerificationModel.swift:203`）打的是 `verifyEmailOTP(email: "typo@x.com", token: <正確的碼>)` → GoTrue 必然失敗，而且每試一次就燒掉一次 `remainingAttempts`；OTP 畫面顯示的也是錯的信箱。`resend()`（同檔 `:344`）同樣會寄到 `typo@x.com`。

這不是 data race（全程 `@MainActor`，無並行存取），是跨 await 的 TOCTOU 狀態不一致。**這個 race 在改動前的 `onCodeSent(model.email)` 就存在**——但本 PR 正是為了「讓 verify 路徑拿到與寄碼相同的值」而重寫了這一行並在註解裡宣告了這個性質，所以屬本票範圍，不算 scope creep。

**建議修法**（擇一，都在已經動到的兩個函式內，不擴大範圍）：把「實際送出的是哪個值」由 model 說了算，不要讓 View 事後重算。

```swift
@discardableResult
func sendCode() async -> Bool {
    guard !isSending else { return false }
    let sending = trimmedEmail            // 只求值一次
    guard EmailFormat.isValid(sending) else { ... }
    isSending = true
    defer { isSending = false }
    do {
        try await authStore.sendEmailOTP(email: sending)
        lastSentEmail = sending           // private(set) var lastSentEmail: String?
        return true
    } catch { ... }
}
```
View 端 `if await model.sendCode(), let sent = model.lastSentEmail { onCodeSent(sent) }`（或把回傳型別改成 `String?`，代價是既有 5 個測試的 `XCTAssertTrue(result)` 要改成 `XCTAssertNotNil`——由實作者權衡）。局部 `let sending` 同時把「驗證過的值 == 送出的值」這個不變量寫成明文，不必再依賴「同一 actor 的 async 呼叫不會 hop」這種編譯器行為推論。

不建議只在 View 裡改成 `let sent = model.trimmedEmail` 再 await ——那依賴 same-actor 呼叫不插入 suspension，語言層面沒保證，而且形同把邏輯繼續留在測不到的 View 層（見 F2）。

順帶記一筆**做對的地方**：`sendCode()` 內部 `guard EmailFormat.isValid(trimmedEmail)`（`:36`）與 `sendEmailOTP(email: trimmedEmail)`（`:43`）之間沒有 suspension point，參數在 suspend 前求值，所以「驗證的值」與「送出的值」必定一致——這半邊沒有 race。

### F2（minor）`LittleSproutTests/EmailSignInModelTests.swift:97-104` — `test_trimmedEmail_isSameValueForwardedToVerifyPath` 名不副實，驗收條件的 verify 半邊實際上沒有測試守住

這個測試唯一的斷言是 `XCTAssertEqual(model.trimmedEmail, "a@b.com")`，只驗了計算屬性本身，**沒有任何東西觀察到 `EmailSignInView.send()` 轉送了什麼**。把第 72 行改回 `onCodeSent(model.email)`，全套測試依然全綠。驗收條件「`sendEmailOTP`／`verifyEmailOTP` 收到 trimmed 值（XCTest）」的後半只靠註解文字保證，不是機械保證（Rule 8：測試要能在行為改變時失敗）。

專案沒有 ViewInspector（已確認；`AuthButtonsState.swift:7`、`InvitePhase.swift:6` 都明文記載了這個限制與對策），而這個 codebase 既有的解法正是**把 View 層邏輯抽成可測的純值／model 計算**。所以 F1 的修法同時解掉 F2：`lastSentEmail`（或 `String?` 回傳值）一旦落在 model 上，就可以用檔案裡既有的 handler 注入手法直接釘住 F1 的情境——`test_sendCode_reentrantCallWhileSending_isIgnored:52` 已經示範了「在 await 期間讓別的東西跑在 MainActor 上」：

```swift
stub.setSendEmailOTPHandler { _ in model.updateEmail("typo@x.com") }  // 模擬送出中使用者又打字
let ok = await model.sendCode()
XCTAssertEqual(stub.sentEmails, ["a@b.com"])
XCTAssertEqual(model.lastSentEmail, "a@b.com", "轉送給 verify 路徑的必須是實際寄碼的那個值")
```

### F3（minor）測試對「驗證要用 trimmed 值」這半邊沒有鑑別力

我用獨立 Swift probe 複製未改動的 `EmailFormat.isValid` 實測（`EmailFormat.swift` 確認未被本 PR 觸碰）：

```
raw="  a@b.com\n"  isValid(raw)=true   trimmed="a@b.com"  isValid(trimmed)=true
raw="   "          isValid(raw)=false  trimmed=""         isValid(trimmed)=false
raw=" @b.com"      isValid(raw)=true   trimmed="@b.com"   isValid(trimmed)=false
```

推論兩件事：
- **mutation 存活**：把 `:36` 改回 `EmailFormat.isValid(email)`（只保留 `:43` 的 trim），測試 (a) 仍然全綠——因為 `isValid("  a@b.com\n")` 本來就是 true。突變後的真實後果正是本票要修的病：輸入 `" @b.com"` 會通過客戶端驗證、把 `"@b.com"`（local part 空）送進 GoTrue 換一個泛用 400。
- **測試 (b) 無鑑別力**：`"   "` 在有沒有 trim 的情況下 `isValid` 都是 false，這個案子在 trim 被移除時**不會變紅**。它是票文明文要求的行為保留守衛（該留），但不能算作 trim 的 mutation 守衛。

建議在測試 (a) 旁補一行輸入 `" @b.com"` 的案子（斷言回 false、`sentEmails` 為空）——那是唯一能區分「驗證用 raw」與「驗證用 trimmed」的輸入，一行就把 `:36` 這半邊釘住。

### I1（informational）中間空白不在本票範圍

`isValid("a @b.com")` 在 trim 前後都是 true（見上表），仍會撞 GoTrue 400。票文「不做」與「不動 `EmailFormat` 規則」已明確排除，**本 PR 沒做是正確的**。若要處理屬 `EmailFormat` 規則變更，建議記入 LS-96 待辦池而非本票。

### I2（informational）`.whitespacesAndNewlines` 涵蓋 NBSP

實測 `"\u{00A0}a@b.com"` 會被 trim 成 `"a@b.com"`（NBSP 屬 Unicode Zs，落在 `whitespaces` 內）。從網頁複製 email 最常見的隱形字元因此有涵蓋到，選字集合正確。

### 四維度結論

1. **Race condition**：見 F1。其餘正確——`EmailSignInModel` 是 `@MainActor @Observable`，`trimmedEmail` 為純同步計算屬性無隔離問題；`sendCode()` 內驗證與送出之間無 suspension；既有的 `guard !isSending` 再入閘門未被破壞（`test_sendCode_reentrantCallWhileSending_isIgnored` 仍綠）。測試用 `StubAuthService` 的參數記錄是 race-safe：`OSAllocatedUnfairLock<Box>` 保護 `sentEmails`／`verifyAttempts`，`@unchecked Sendable` 的理由成立（`StubAuthService.swift:29、107、113`），本 PR 未動它、也不需要動。
2. **運算效能**：無可審之處。本票是單一同步字串 trim，無 SQL／RLS／查詢／分頁／圖片解碼路徑；`trimmedEmail` 每次讀取重算一次短字串，在 `sendCode()` 與 `send()` 各數次呼叫，量級可忽略。
3. **平行優化**：無可審之處。無批次、無迴圈內 await、無可併發化的工作。
4. **Scope**：**乾淨**。改動嚴格落在票文允許的 3 檔（`EmailSignInModel.swift`／`EmailSignInView.swift`／`EmailSignInModelTests.swift`），`StubAuthService.swift` 未動（本來就不需要）。`EmailFormat` 規則、錯誤文案、`JoinCodeView` 皆未觸碰，符合手術式要求。無順手重構、無無關改動、無新增未被要求的功能。新增註解偏長，但與本 repo 既有註解密度一致（Rule 10），不列 finding。
