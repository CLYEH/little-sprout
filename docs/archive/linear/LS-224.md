### (a) §9 豁免與出處確實存在，理由成立

`supabase/tests/60_default_privileges.sql` 第 619–657 行（§9 標題「LS-40：schema private 的函式必須 SECURITY DEFINER＋search_path 收斂，例外逐支登記」）確實早於本票就把四支列為登記在案的 invoker 例外，逐支寫明出處：`is_media_object_path` → LS-40；`is_avatar_object_path` → LS-169 R2；`deletion_bypass_active`／`enforce_deletion_bypass` → LS-179 R2（MAJOR-2）。inlining 這條事實在 repo 內另有三處獨立記錄，我逐處讀過確認不是本票新造的說法：`supabase/migrations/20260824010000_diaries_write_path_and_timeline.sql` 第 403–406 行（merge-reviewer PR #60 review F1 的實測數字：深頁 3516 buffers／稀疏 child 4638 buffers vs 手寫等值查詢 4 buffers）、`supabase/tests/50_rls_plan_no_percall_subquery.sql` 第 346–356 行、`docs/API.md` 第 1442 行。函式本體也與說法相符：`private.is_media_object_path(p_name text)` 與 `private.is_avatar_object_path(p_name text)` 皆 `language sql`＋`immutable`＋純 `p_name ~ '...'` regex，不參照任何資料庫物件（`supabase/migrations/20260904060700_avatar_object_path.sql` 第 29–46 行、`supabase/migrations/20260904081435_avatar_family_write_policy.sql` 第 26–35 行），且確實掛在 `storage.objects` 的 `media_bucket_insert` WITH CHECK（`20260823030000_storage_policies.sql` 第 188–195 行）與 `media_bucket_update`／`media_bucket_delete` 的 USING／WITH CHECK（`20260904081435_avatar_family_write_policy.sql` 第 52–88 行）。

### (b) EXPLAIN 實測：inlining 損失是真的（我自己跑，不採信 handoff）

實測一（直接對該函式的呼叫路徑，`docker exec … psql`，同一 session 內 A→B）：

```
A_baseline_no_SET（HEAD 現狀）
 Seq Scan on storage.objects o
   Filter: (o.name ~ '^[0-9a-f]{8}-...(_thumb\.jpg|\.(jpg|jpeg|png|heic|heif|mp4|mov))|avatars/...\.jpg)$'::text)

B_with_SET_search_path（tx 內 alter function private.is_media_object_path(text) set search_path = ''; 後 rollback）
 Seq Scan on storage.objects o
   Filter: private.is_media_object_path(o.name)
```

實測二（走真正的 storage.objects RLS policy 路徑，`set role authenticated;` 後 `explain (verbose, costs off) update storage.objects set metadata = metadata where bucket_id = 'media';`）：

```
C_policy_path_as_authenticated（HEAD 現狀，media_bucket_update 的 USING）
   Filter: (... OR ((objects.name ~ '^[0-9a-f]{8}-...-...{12}/avatars/[0-9a-f]{8}-...\.jpg$') AND (ANY ((storage.foldername(objects.name))[1] = (hashed SubPlan 13).col1))) ...)

D_with_SET_on_both_predicates（tx 內對兩支都加 set search_path = '' 後 rollback）
   Filter: (... OR (private.is_avatar_object_path(objects.name) AND (ANY ((storage.foldername(objects.name))[1] = (hashed SubPlan 13).col1))) ...)
```

加了 `SET` 之後，policy 的逐列判準從「規劃器已內聯、可估選擇度的 regex 運算式」退化成「對規劃器不透明的函式呼叫」，每一列多一次 fmgr 呼叫。這正是每次媒體／頭像 INSERT／UPDATE／DELETE 都會走到的寫入熱路徑。

## 7. Findings

### minor-1 — 兩支新加 `search_path` 的函式，理由寫錯了（「plpgsql 呼叫沒有 inline 可言、純收益沒有代價」不成立）

- 位置：`supabase/migrations/20260906123430_advisors_hardening_search_path.sql` 第 38–41 行（「plpgsql 呼叫函式一律走真正的函式呼叫（fmgr），不會有『規劃器 inline 進外層查詢』這件事可言……關掉這個 WARN 是純收益，沒有對應代價」）；同一說法複製到 `supabase/tests/60_default_privileges.sql` §9 第 638–657 行的兩段註解。
- 事實：plpgsql 的運算式（`if <expr> then`、`perform`、`b := f()`）是**交給規劃器規劃的 SQL 查詢**，SQL 函式在其中照樣是 inlining 的候選。實測（`docker exec … psql`）：
  ```
  E_head_with_SET（HEAD 現狀）  explain verbose select private.deletion_bypass_active();
   Result
     Output: private.deletion_bypass_active()
   NOTICE:  WITH SET  200k calls: 00:00:00.261667 / 00:00:00.242581

  F_reset_no_SET（tx 內 reset search_path 後 rollback）
   Result
     Output: (COALESCE(current_setting('ls179.account_deletion'::text, true), ''::text) = 'on'::text)
   NOTICE:  NO SET    200k calls: 00:00:00.024101 / 00:00:00.024039
  ```
  即：加了 `SET` 之後 inline **確實被關掉**，plpgsql 內每次呼叫從 ~0.12 µs 變成 ~1.25 µs（20 萬次迴圈，兩輪，約 10×）。
- 具體失敗情境（為什麼仍要記）：`private.deletion_bypass_active()` 的唯一呼叫處 `private.enforce_not_suspended()` 是掛在 16 張表上的 **for each row** trigger（`20260904212530_suspension_and_registrations.sql` 第 499–555 行），所以這是逐列成本，不是每次呼叫一次的成本。絕對值上仍是雜訊（同一個 trigger 內的 `private.caller_is_active()` 要查表，貴上好幾個數量級；批次 100 列也才多 ~0.11 ms），**所以我不把它當 major、也不要求改 migration 行為**——要求改的是**理由那段文字**：這兩份註解是本 repo 記錄「為什麼某支函式加／不加 SET」的正典位置（本票自己就引用了 LS-40／LS-48 F1 的同類註解），把「plpgsql 呼叫不會 inline」寫成通則，下一張票很可能據此對一支真的很熱的 plpgsql-called 函式加 SET，而那時沒有人會回頭實測。
- 建議修法：把兩處註解改成準確版本——「plpgsql 語境同樣會 inline，加 SET 一樣關掉 inline 並多一層 fmgr GUC 存還；實測每次呼叫 ~0.12 µs → ~1.25 µs。這裡仍然值得加，因為呼叫端雖是逐列 trigger，但同一 trigger 內已有查表成本，1 µs 落在雜訊裡，換掉一個 advisor WARN 划算」。可在本 PR 補一個 commit，或由 orchestrator 記 LS-96；不阻擋合併。
