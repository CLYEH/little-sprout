## Findings

### F1（major）孤兒掃描在任何有規模的 bucket 上都會餓死，且與「沒有孤兒」無法區分
`supabase/functions/purge-storage/index.ts:108`（`ORPHAN_SCAN_BATCH_SIZE = 500`）＋`:178-266`（掃描本體）：預算 `considered` 計的是「**看過的檔案數**」（`:228` 每個檔案項都 `considered++`，含正常有對應列的物件），而不是候選數；而且掃描每次 invocation 都從 bucket 根目錄 `bucket.list("")` 重頭走（`:168`），**沒有任何續掃游標**，`break familyLoop`（`:179`／`:192`／`:209`）之後就返回。

具體失敗情境（已實測）：`storage.list()` 預設 `sortBy=name asc`，排序在最前面的家庭前綴一旦累積 500 個物件（＝250 張照片，原圖＋縮圖各一個物件），預算就在那個家庭最早的月份資料夾用完，其餘家庭／月份永遠掃不到；下一次 invocation 又從同樣那 500 個看起。實測（`scratchpad/LS-213-rev-starve.sh`）：在 `a0000000-…` 前綴放 600 個寬限期內的物件、在排序較後的 `e1000000-…` 前綴放一個 48 小時前、無對應 `media` 列的真孤兒 → 回應 `{"processed":0,…,"orphanEnqueued":0}` HTTP 200、`purge_storage_queue` 0 筆、該孤兒物件原封不動，**沒有任何 warning**——外觀與「本來就沒有孤兒」完全相同。

建議修法：(a) 預算改計「候選數」（過了 `MEDIA_OBJECT_PATH_RE` 與寬限期的物件）而不是看過的檔案數；(b) 持久化續掃游標（例如一張單列的 `private.orphan_scan_cursor(bucket_id, last_key)`，每次從上次結束處續掃、掃完一輪回到開頭），或至少對家庭前綴做 round-robin；(c) 掃到預算上限而尚未掃完一輪時，在回應裡回報（例如 `orphanScanTruncated: true`），讓「還沒掃完」與「沒有孤兒」在觀測上可區分。

### F2（major）對照 `media` 的 `.in()` 一次帶 500 條路徑，會被 gateway 以 HTTP 414 擋掉——同一支檔案 `:91` 已經記過這個教訓
`supabase/functions/purge-storage/index.ts:244-252`：`supabase.from("media").select(...).in("storage_path", candidatePaths)` 走的是 GET query string，`candidatePaths` 上限＝`ORPHAN_SCAN_BATCH_SIZE`＝500，每條路徑約 78 字元，filter 字串約 44 KB。

具體失敗情境（已實測，本機 stack）：對 `/rest/v1/media` 直接發同形狀的請求，n=80 → HTTP 200（filter 長度 7041）、**n=90 → HTTP 414 `URI too long`**（filter 長度 7921）、n=100／300／500／1000 皆 414。也就是任何一個月份資料夾裡有 ≳85 個超過寬限期的物件（＝約 43 張照片的原圖＋縮圖，一個家庭一個月很容易達到），`byStorage.error` 就成立 → `warnings.push` → `continue monthLoop`，該資料夾整個被跳過、孤兒永遠收不到，並且回應永久變成 HTTP 207。方向上是 fail-safe（不會誤刪），但功能在常見資料量下等於不會運作。實作者的 e2e 只有 4~6 個物件，所以沒撞到。

值得注意的是同一支檔案 `:91` 已經有這條教訓的既有結論：`const DELETE_CHUNK_SIZE = 50; // dequeue 時 .in() 帶的 id 數上限（i3），避免 URL 過長`——新程式碼沒有沿用。

建議修法：把 `candidatePaths` 切塊（沿用既有 `chunk()`，每塊 ≤50~80 條）分次查詢再合併 `knownPaths`；同時補一道保險——`supabase/config.toml` 的 `max_rows = 1000` 會靜默截斷回傳，而本處「查不到列 ⇒ 是孤兒 ⇒ 刪檔」是 fail-open 推論，切塊後每塊大小也必須遠小於 `max_rows`，建議另加「回傳筆數等於上限就視為不可信、跳過本批」的斷言。

### F3（minor）沒有 `offset` 續頁、三層 `list()` 全序列、且掃描排在既有消化迴圈之前；`docs/API.md`／`docs/PLAN.md` 寫的「分頁掃描」與實作不符
`index.ts:168`／`:183`／`:197`／`:213` 四處 `bucket.list(..., { limit: 1000 })` 都沒有 `offset` 續頁——單一資料夾超過 1000 項時第 1001 項之後永遠看不到（與 F1 疊加）。四層 `await` 全序列，list 呼叫次數是 1+F+F·Y+F·Y·M 次序列 HTTP round-trip，而檔頭註解自己也寫「這裡的成本主要來自 `storage.list()` 的分層呼叫次數，不是佇列列數」——但上限計的卻是檔案數，管不到這個成本。掃描又放在既有佇列消化迴圈**之前**（`:343`），掃描慢就連帶拖延 LS-153 既有的清除工作。文件面：`docs/API.md` §3／§6 與 `docs/PLAN.md` §5 都寫「分頁掃描」，實作其實是「每層單頁 1000 筆的分層走訪」。

### F7（minor，運算效能）新 partial index 沒有被它要支撐的查詢用到

### N2（minor，PLAUSIBLE）續掃游標只在整趟掃描結束時才寫回，且 `scanFamilyOrphans()` 對單一家庭沒有內部上限——單一超大家庭可讓游標永遠停住

### N3（minor）`index.ts` 的 `MEDIA_OBJECT_PATH_RE` 比 `private.is_media_object_path()` 寬，縮圖分支對不上——落差區間的物件會被「永遠掃到、永遠靜默丟棄」
`supabase/functions/purge-storage/index.ts:138-142` 的註解寫這支 regex 是「比照 `private.is_media_object_path()`（原檔／縮圖那一支形狀）」，但兩者不等價：TS 是 `[uuid](?:_thumb)?\.(?:jpg|jpeg|png|heic|heif|mp4|mov)$`，SQL（`supabase/migrations/20260904060700_avatar_object_path.sql:36-38`）是 `[uuid](_thumb\.jpg|\.(jpg|jpeg|png|heic|heif|mp4|mov))$`——**縮圖只允許 `.jpg`**。所以 `…/{uuid}_thumb.png`（或 `_thumb.mp4`…）這種路徑：TS 端算候選 → RPC 回報「無對應列」→ 進 `purge_storage_queue_enqueue_orphans()` 被 `private.is_media_object_path(path)` 靜默丟掉（migration `…050606…sql:208-209`），而該函式的回傳值同時也被 `on conflict do nothing` 稀釋，呼叫端無從分辨「被驗證丟掉」與「本來就已在佇列」——`index.ts:345-350` 只把回傳值當 `enqueued`，不比對 `orphanPaths.length`，也不發 warning。後果是這類物件每一輪都被重新掃到、每一輪都被丟掉，永遠不會被回收也永遠不會有人知道。今天不可達（`media_bucket_insert` 的 WITH CHECK 用的就是 SQL 那支判斷式，client 只寫 `_thumb.jpg`），所以列 minor 而非 major。建議：把 TS regex 的縮圖分支收成 `(?:_thumb\.jpg|\.(?:jpg|jpeg|png|heic|heif|mp4|mov))$` 與 SQL 對齊（一行），或在 `enqueued < orphanPaths.length` 時 `warnings.push` 一條。這也回答本輪審查重點 3 的後半題：目前**沒有**計數回報。

### N4（informational）並發兩次 invocation 對游標是 last-writer-wins，但推不出漏掃
本輪審查重點 1 的並發題。`readScanCursor()`（`index.ts:207-222`）→ 掃描 → `writeScanCursor()`（`:224-242`）之間沒有 advisory lock，兩次重疊的 invocation（pg_cron 重疊或手動＋排程）會讀到同一個游標、重複掃同一批家庭，最後一個寫入者決定游標。**這不會造成漏掃**：游標的值一律是「寫入者這次真的處理完的某個家庭」，而 resume 規則是 `familyIds.findIndex(f => f > resumeAfter)`（`:410`），起點只會落在某個已處理家庭的後繼，被覆寫只可能讓游標往回退＝下一輪多掃，不可能跳過沒掃過的家庭；入列端 `on conflict (bucket_id, object_path) do nothing` 天生冪等。此結論是讀碼推導（不是實測），代價僅為重複的 `storage.list()` 呼叫。不建議為此加 advisory lock。另兩個子題也一併查了：掃完一輪 `orphanScanCompleted:true` 後游標寫 `null`、下一輪確實從頭（我的 invoke2→invoke3 實測到了）；游標指向已不存在的前綴時，`f > resumeAfter` 的字串比較天生降級成「從下一個更大的前綴開始」，不會卡住（`index.ts:409-412`）。

### N5（informational）候選預算的語意讓成熟 bucket 的掃描速率退化成「每次 invocation 約一個家庭」，且 `orphanScanCompleted` 幾乎永遠是 false
