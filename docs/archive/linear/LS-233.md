**m1（minor）`scripts/ops/patrol.sh:183-186` — pending 與 fail 同時存在時，fail 被整個吞掉**
重現（PATH stub 打真的 `scripts/ops/patrol.sh`，非合成斷言）：fixture PR 912 = `ci fail`（run 777111）＋`ci-ipad pending` → 實得 `⏳ CI 跑中（ci-ipad，head ccccccc 已 60m）`，`ci` 的紅與 run id 一字未印。真實時序：required job `ci` 第 10 分鐘紅、`ci-ipad` 還要跑 20 分鐘（required check 紅 → `mergeStateStatus` 就是 `BLOCKED`，#355 即為此形）→ 巡檢告訴 orchestrator「CI 跑中」，它就等；20 分鐘後才看到紅——正是本票要消滅的那種等待。會自癒（pending 結束後轉成 check 紅），故 minor 不是 major。
修法：pending 分支尾巴接 `"${fail_names:+（另有 fail：${fail_names}）}"`，或把 fail 判定移到 pending 之前。

**m2（minor）`scripts/ops/patrol.sh:184` — 「head <sha7> 已 <n>m」的 n 是 PR `updatedAt` 年齡，不是 CI 跑了多久**
#365 事故當下正是這形狀：`updatedAt` 48 分前（R2 派工後沒人再動 PR），CI 其實剛開跑。新訊息印「CI 跑中（db、ci，head a5773c0 已 48m）」，很容易被讀成「CI 已經跑 48 分鐘 → 卡住了 → rerun」，跟票文要消除的語意含混同類（只是換了個方向誤導）。
修法：同一次 `gh pr checks` 加 `startedAt` 欄位（不加呼叫），印「最早 pending 起 <m>m」；或字樣改成「PR 已 48m 未更新」把量測對象講白。

**m3（minor）`scripts/ops/patrol.sh:244` 只套 catch-all，`scripts/ops/patrol.sh:239` 的 `UNSTABLE` 仍是「⚠ CI 紅」**
票文範圍 1 字面列了 {BLOCKED, UNSTABLE, BEHIND}。窄化本身**裁定為合理最小手術**（兩起事故都是 BLOCKED；BEHIND 的處置與 check 無關；UNSTABLE 是「立即標」不受 stale 門檻保護，套上去等於每輪都打 gh），實作者也在 PR body／handoff 明白列出待裁——流程正確。但 `UNSTABLE` 的「⚠ CI 紅」不含 check 名與 run id，orchestrator 仍得手動 `gh pr checks`，缺口沒被記下就會消失。
