### major

**M1（效能／egress，本票新引入）`LittleSprout/Services/Timeline/TimelineStore.swift:180-186` × `PhotoCardView.swift:30-32`——有縮圖的影片會在每次卡片重新出現時重打一次注定失敗的 `AVURLAsset` 請求**

```swift
func loadVideoDuration(mediaID: UUID, url: URL) async {
    guard videoDurations[mediaID] == nil, !loadingDurations.contains(mediaID) else { return }
    loadingDurations.insert(mediaID)
    defer { loadingDurations.remove(mediaID) }          // ← 失敗後 in-flight 標記也被清掉
    let asset = AVURLAsset(url: url)
    guard let duration = try? await asset.load(.duration), … else { return }   // ← 失敗不寫任何東西
    videoDurations[mediaID] = CMTimeGetSeconds(duration)
}
```
成功會被 `videoDurations` 記住、失敗**什麼都不記**。`PhotoCardView` 的 `.task(id: content.id)` 只 guard `content.type == .video, let url = content.signedURL`，而 LS-130 之後這個 `signedURL` 對有縮圖的影片就是 JPEG 縮圖 → `load(.duration)` **必然**失敗（handoff 自己觀察到徽章退回「影片」，正是走這條 nil 分支）→ 沒有記憶 → 下次 `.task` 再跑一次。

失敗情境（可重放）：時間軸有 N 支已上傳縮圖的影片卡；使用者往下捲把某張卡捲出 `LazyVStack` 的存活視窗、再捲回來 → 該卡被重建 → `.task` 重跑 → 又一次 `AVURLAsset` 對縮圖 JPEG 發請求、又一次失敗。來回捲 10 趟 ≈ 每支影片 10 次無用請求，沒有任何上限或退避。這在 LS-126 時代不是問題（失敗是例外），LS-130 讓它變成**必經路徑**——一張「為了省 egress」的票留下一個按捲動次數線性成長的請求源。

誠實界定：我沒有量測單次失敗載入實際下載多少 bytes（AVFoundation 會先發 range 請求探容器再放棄，縮圖本身只有數十 KB），所以**位元組量級未經實測**；但「每次重新出現＝至少多一次 HTTP 請求、且永遠不會成功」這件事是構造上確定的。另外確認**沒有**更糟的副作用：不會誤簽全尺寸（這條路徑只吃 `content.signedURL`，全尺寸只有 `signFullSizeURL` 一個入口）、不是無 `.task` 觸發的自旋（`refresh` 換掉 `entries` 時 `TimelineEntry.id`／`content.id` 不變，`.task(id:)` 不會重跑，只有 view 真的被重建才會）。

建議修法（二選一，皆 ≤3 行）：
- **(a) 根本不打**（首選，零請求）：呼叫端在 `content` 顯示的是縮圖時就不呼叫。`MediaContent` 已帶 `thumbWidth`，而 `media_thumb_dimensions_consistency` CHECK 保證三欄同為 NULL／同為非 NULL（`TimelineModels.swift:96-99` 自己寫了這個不變式），所以 `thumbWidth != nil` ⟺ 顯示的是縮圖。更穩的話由 assembler 在算 `displayPath` 的同一處帶一個顯式 `isThumbnail: Bool` 進 `MediaContent`，就不必倚賴 CHECK 不變。
- **(b) 記住失敗**：`TimelineStore` 加 `private var failedDurations: Set<UUID>` 並入 guard——這條對「真正壞掉的影片檔」也有用，屬一般性硬化。
