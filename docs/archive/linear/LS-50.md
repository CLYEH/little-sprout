## 描述

來源：[LS-38](https://linear.app/little-sprout-app/issue/LS-38/實驗第二輪軌-c-pen-軌-d-canvas-粉色調漸層各-5-輪對抗) 收尾巡檢發現 `feature/LS-38-pink-tracks` 疊了 [LS-31](https://linear.app/little-sprout-app/issue/LS-31/實驗design-canvas-管線-vs-pen-同-brief-三輪對抗比較)（軌 B）的三個 commit，[LS-31](https://linear.app/little-sprout-app/issue/LS-31/實驗design-canvas-管線-vs-pen-同-brief-三輪對抗比較) 從未開 PR——違反 CLAUDE.md「一張 ticket＝一個 worktree＝一條 branch」，卻沒有任何機械 gate 攔到。

## 規則

feature|fix|hotfix 分支自 merge-base（對 development 或 main）以來的所有 commit，其第一行的 `LS-<n>` 必須等於分支名的 `LS-<n>`（merge commit 除外）。

## Gate（前饋必有反饋）

* `scripts/gates/push-gate.sh`：push 前檢查，異票號 → FAIL 並列出違規 commit；提供具名逃生口（例如 commit body 含 `Bundles: LS-<m>` 且 PR body 同步宣告）供刻意夾帶的情況，逃生口使用要在 PR body 可見。
* CI rules job 同步檢查（PR head vs base 的 merge-base）。
* 負向測試：造一條分支含異票號 commit → 紅；加 `Bundles:` 宣告 → 綠且印出宣告。
* COLLABORATION §7 補列。

### 二、Informational（無一為 blocker／major）

1. **`scripts/gates/branch-ticket-check.sh:89`** — 只有「無票號」違規、`undeclared` 為空時，補救訊息會印出空的逃生口：`` 刻意夾帶：本票 commit body 加獨佔一行 `Bundles: ` ``。復現：分支 `feature/LS-49-x` + subject `wip`。無票號本來就沒有逃生口，這行會誘導 agent 加一條不合 regex 的空宣告、白跑一趟（加了仍紅，fail closed，不是洞）。建議 `undeclared` 為空時只印「非刻意」那行。
2. **`scripts/gates/merge-conflict-check.sh:57`** — 所有非 0/1 的 rc 都套同一句「`--write-tree` 需 git ≥ 2.38」。復現：orphan 分支 → `fatal: refusing to merge unrelated histories`、rc=128，被誤導成 git 版本問題。fail closed 正確，只是歸因誤導；建議改成「見下方 git 原文；若是 `unknown option --write-tree` 才是版本問題」。（附帶 PLAUSIBLE：`--name-only` 可能要 git ≥2.40 而非 2.38，兩者都 fail closed，不影響安全性。）
3. **`docs/COLLABORATION.md` §7 第二列措辭** — 寫「本機 `origin/<target>` **落後**遠端即紅」，腳本實際是 sha **不相等**即紅（本機較新／遠端被改寫也擋）。腳本較嚴、方向正確，但「逐字一致」要求下建議改成「與遠端不同」。
4. **§7 第二列盲區少一條（與 §2 打架）** — §2「本地合併版 back-merge（LS-56 補記）」明載 GitHub 曾把 back-merge PR **誤判** CONFLICTING 而本地 `merge-tree` 零衝突（LS-54 PR #71）。也就是本 gate 綠 ≠ GitHub 一定可合併，「PR 開了 CI 永遠不跑」在 GitHub 誤判時仍會發生。建議在 §7 該列盲區補這一句，跟 §2 對齊。
5. **§7 第一列盲區可再補一條** — 我實測 `git merge --squash` 異票分支後以本票訊息 commit → **綠**。訊息合規、內容夾帶的形狀本 gate 看不見。與既有「跨 worktree 編輯無 gate」同類，但值得逐字寫明（現行只寫「只看 subject 第一個票號」）。
6. **第 6／7 步排在 xcodebuild test 之後** — 我同意 orchestrator 的判斷：**不是本 PR 的 blocker**（PR body 已列、「不重排」是既定約束）。但補一個具體代價：第 7 步的 ls-remote 是**時間敏感相等比對**，跑在數分鐘的 xcodebuild 之後，只要測試期間有人推 development，就 exit 2 要求 fetch，fetch 後整套測試要重跑；平行 agent 多時會 ping-pong。第 7 步約 3s、第 6 步 <0.1s，前移到 SwiftLint 之前成本極低。**建議另開 ticket**。
7. **既有同類的繞過路徑（非本 PR 引入，記錄用）**：(a) detached HEAD、或站在保護分支上 `git push origin <branch>` 時，第 6／7 步整段跳過——pre-push hook 其實能從 stdin 拿到被推的 ref，改用 stdin 可堵，但會動到第 5 步，宜另票；(b) `pull_request` 預設 types 不含 `edited`，先綠再把 `Bundles:` 從 PR body 刪掉不會轉紅（反方向是 fail closed：漏宣告的紅不會因為補 body 而自動變綠，仍要重推）——與既有 DESTRUCTIVE-APPROVED／BREAKING: 同一類，commit body 宣告仍在，影響低。
8. **PLAUSIBLE：`hotfix/*` 開向 `development`（方向矩陣允許）時，第 6／7 步仍以 `origin/main` 為對象** — 第 6 步不受影響（保護分支 ref 排除已驗證）；第 7 步則檢查了錯的方向，理論上 main 有未 back-merge 且會衝突的內容時可能誤紅。沿用第 5 步既有矩陣、本 repo 慣例 hotfix 自 main 切且 PR 回 main，機率低，不要求本 PR 處理。
