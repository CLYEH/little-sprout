`Entry.upload` 是 `let`，`PendingUpload.kind` 的整份照片位元組被 `entries` 一直持有到 store 釋放為止，**完成的那些也不例外**。失敗情境：LS-166 的 34 張壓測（HEIC 常見 5–10MB）→ 全部上傳成功後 store 仍常駐約 170–340MB；而「在背景繼續」的設計本來就要求 store 活過 sheet dismiss，這份記憶體會撐很久，舊機（記憶體上限約 1–2GB）配上 PhotosPicker 自己的解碼峰值有 jetsam 風險。修法：`finish(_:state:)` 在 `.completed` 分支把該筆 payload 丟掉（`kind` 改可選／改 var，只有失敗列需要留位元組供重試）。整批一次全載進記憶體這件事是 `MediaUploadService(data:)` 協定決定的、屬「上傳引擎本身」不在本票，但「完成後仍不放」是本 store 自己能修的。

**I2（informational）每次 body 求值重算**：`rows`／`sections` 每次讀都做 3 次 `filter`＋3 次 `sort`，`remainingCount`／`waitingCount`／`uploadingCount`／`retryableFailedCount` 各 O(n)，且 `retryableFailedCount` 一次 body 被讀兩次（`:77`／`:112`）；`entries` 是單一字典 → 任何一筆狀態變動都會整張 sheet 重評。n 在數十量級時完全可忽略（UITest 實測無延遲），**現在不建議快取**（多一份要同步的狀態＝多一個競態面）。純記錄，非要求修改。

**I3（informational, 契約）`UploadQueueModels.swift:20-22`** — `PendingUpload.thumbnail` 是裸 `UIImage`，型別與文件都沒約束尺寸；LS-166 若直接把原圖塞進來，48pt 的格子會在主執行緒解一張全解析度圖（正是「列表誤載原圖」）。建議在該欄位文件註解明寫「必須是已縮小的縮圖（長邊 ≤ N px）」，把契約寫死在被呼叫的那一端。
