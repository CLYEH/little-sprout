## 一、四維度結論

### Race（票文點名維度）—— 找不到問題

- **分段寫回與 last-writer-wins「只重掃不漏掃」的推導我獨立驗過，成立**（`supabase/functions/purge-storage/orphan_scan.ts:259-278`）：每個寫入者只在**自己剛完整處理完**的家庭上寫游標，且訪問順序是從 `startIndex` 起連續（含 `% familyIds.length` 繞回），因此區間「(讀到的游標, 寫回的游標]」必定被該寫入者完整掃過；被較慢的 invocation 用較舊的值覆寫，只會讓下一輪起點往回退（重掃），不存在「游標跳過沒人掃過的家庭」的路徑。兩次 invocation 同時繞完一圈也只是把 `null` 與某家庭值互相覆寫，最壞是下一輪多繞。
- **v2 與舊 enqueue 並存期間無雙寫問題**：兩支 SQL 本體相同、共用 `on conflict (bucket_id, object_path) do nothing`（`supabase/migrations/20260906091007_purge_orphan_dropped_reporting.sql:116-121` 對照 `20260906050606_soft_delete_unreferenced_media.sql:205-212`），並發呼叫任一支都只會有一列，`enqueued` 各自為真正新增列數。
- **游標寫回排在 enqueue 之後**（`orphan_scan.ts:178-189` → `:269`）：enqueue RPC 失敗時游標仍前進，但 round-robin 保證下一圈會再訪同一家庭，物件不會永久漏掉（且 warning 已記）。
- **掃描中物件被正常路徑刪除／新增**：候選只取 `created_at` 超過 24h 寬限期者（`orphan_scan.ts:139-143`），掃描期間新上傳的物件不會進候選；掃描期間 `media` 列被硬刪則該路徑被判為孤兒並入列，之後由既有消化迴圈處理——這段語意本 PR 完全未動（屬 LS-213 既有範圍）。

### 效能 —— 找不到退化

- `purge_storage_classify_orphan_paths` 對 `p_paths` 走兩趟 `unnest`（valid／invalid 各一，migration `:56-64`）；`private.is_media_object_path()` 是 `language sql immutable`（`supabase/migrations/20260904060700_avatar_object_path.sql:29-33`），可被 planner inline 成純 regex，500 元素量級成本可忽略，**不是 per-row 子查詢退化**。
- 內部呼叫的 `purge_storage_unknown_media_paths()` 的 `not exists (... m.storage_path = path or m.thumb_path = path)`：兩欄皆有 UNIQUE 索引（`20260822120000_init_schema.sql:124`／`20260902101842_media_thumb_path.sql:61`），不是全表掃；且此函式本 PR 未改，行為與 LS-213 R2 已審版本相同。
- 無新增 OFFSET SQL 分頁（`storage.list()` 的 offset 續頁是 Storage API 既有寫法）。`orphanDropped` 累計是每家庭一次 `dropped += result.dropped`（`orphan_scan.ts:264`），O(家庭數)、非 O(路徑數)。
- **每家庭多一次游標 upsert round-trip**（1 次 → F 次／invocation）是票文範圍 2 明文要求的取捨，今日家庭數極少，不列 finding；若未來家庭數上千可改成「每 K 個家庭或每 T 秒寫一次」。

### Scope —— 乾淨

- migration 只 `create or replace` 兩支**新名字**函式＋兩行 `revoke ... from public, anon`，不 DROP、不改既有簽名；`migration-breaking-check.sh --base origin/development` **零命中**（見下方 gate 原文）。
- 抽出 `orphan_scan.ts` 屬票文範圍 3「EF deno 測試」的必要前置（`index.ts` 頂層直接 `Deno.serve()`，import 即起 listener），沿用 `delete-account/handler.ts` 既有拆分慣例，不是順手重構。
- 佇列消化本體（attempts／退避／死信／confirmed-delete／`storage.remove()`）逐行未動；`index.ts` 在掃描區塊之外只多了 `orphanDropped` 的 `console.log` 與回應欄位兩處。**刪除語意未動**（票文「不做」項）。

## 二、Findings（無 blocker／major）

**F1（minor，PLAUSIBLE）`supabase/functions/purge-storage/orphan_scan.ts:166-172`——不合規路徑 warning 無上限且每輪重複**
`invalidPaths.join(", ")` 把該家庭**全部**不合規路徑塞進一條 warning，而 warning 會進 EF 回應 JSON 與 `console.log`。這些路徑永遠不會被入列（就是被 dropped），所以每一輪掃到都重複產生同一條 warning，長度隨不合規物件數線性成長、無上限。具體失敗情境：某家庭累積 N 個不合規物件（例如未來放寬 TS／SQL 其中一側的副檔名規則），單次 invocation 的回應與 log 各多 N×約 80 bytes，N=10k 時單條 warning 約 800 KB。標 PLAUSIBLE：今日 storage insert policy 的 `WITH CHECK` 就是 `is_media_object_path()`，client 寫不進不合規路徑，N 實際為 0。建議：`invalidPaths.slice(0, 10).join(", ")` ＋「…等 N 條」。

**F2（minor）`supabase/functions/purge-storage/orphan_scan.ts:142-151`——形狀不合規的候選現在會吃掉 batch 預算（LS-213 R1 F1 修法的部分回退）**
LS-213 R1 F1 當時特意把 `considered` 收成「形狀合規＋過寬限期」，避免非候選物件吃掉預算；本 PR 把形狀判斷移到 SQL 之後，`considered` 在 `classifyPaths()` 之前就定案（＝所有過寬限期物件）。具體失敗情境：某家庭有大量不合規、永遠清不掉的物件時，每一輪都在該家庭吃掉整個 500 預算，其它家庭要多繞幾輪才輪到（round-robin 每輪仍推進游標，**不會餓死**，只是變慢）。同 F1 今日不可達。`docs/API.md` 已如實改寫成「過了寬限期的物件數」，不是文件不實，只是這個對 F1 的部分回退沒有被明說。建議一行修法：classify 之後把 `considered` 修正為 `pastGraceCandidates.length - invalidPaths.length`。

**F3（minor）`docs/API.md:2481`／`supabase/tests/60_default_privileges.sql:515`——舊 RPC `purge_storage_queue_enqueue_orphans` 已零呼叫端，但契約清單未標 deprecated**
