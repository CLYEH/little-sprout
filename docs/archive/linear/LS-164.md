## Findings

### N1（minor）`LittleSprout/Features/Auth/PasswordSignInModel.swift:66-73` — 429／404／422 也會被說成「帳號或密碼錯誤」

`apply()` 用 `if case .validationRetryable = appError` 當「帳密錯誤」的唯一判準，但 `AppError.mapAPIStatus`（`LittleSprout/Errors/AppError.swift`）把 **400／404／422／429** 全部歸進 `.validationRetryable`（429 還特地帶 `code: "bare_http_429"` sentinel 讓呼叫端能辨識）。票文 scope 1 寫的是「`invalid_credentials`／400 → 單一文案」，實作放寬成整個 tier。

**具體失敗情境**：審核人員連打幾次密碼撞上 GoTrue `/token` 的限流（或前面的反向代理吐裸 429），畫面顯示「帳號或密碼錯誤，請再試一次。」＋兩欄變紅——他手上的帳密是對的，只會照著提示一直重試，把限流窗口越拉越長，畫面永遠不會告訴他「請稍等」。同理，專案 URL 打錯導致 404 時也是同一句。

**建議修法**：`apply()` 先攔限流碼再落一般分支，例如 `if case .validationRetryable(_, let code) = appError, code == "bare_http_429" || code == "over_request_rate_limit" { isCredentialsError = false; errorMessage = appError.userFacingMessage }`——`OTPVerificationModel.nonAttemptConsumingCodes` 已有同型前例可抄，不必新造文案。

### N2（minor）`LittleSprout/Features/Auth/WelcomeView+PasswordSignIn.swift:23` — 連結熱區只比 44pt 多 0.33pt

我把 `PasswordSignInUITests:17` 的斷言暫時改成印值實測：`frame=(24.0, 729.67, 354.0, 44.33333333333337)`（一般字級、iOS 26.0）。組成是 `.note` 17pt 的行高 ≈20.33 ＋ `AppSpacing.group` 12×2。餘裕 0.33pt。

**具體失敗情境**：同一位作者在 `LabeledTextField.swift:92` 的註解已經記錄過踩到的事故——`.frame(minHeight: 44)` 實測量到 43.9x 被判 FAIL，所以那裡改用 46。這條連結沒有比照：只要日後某個 iOS 版本／某個語系把這行字的行高改掉 0.34pt 以上（LS-167 的 iOS 26.2 sheet 0.96 縮放就是同一類事故；本畫面不在 sheet 內，這次 CI 26.2 是綠的），熱區就掉到 44 以下，`PasswordSignInUITests` 會紅（gate 有接住），而在 gate 之外的真機上長輩硬約束已經破了。

**建議修法**：`.padding(.vertical, AppSpacing.group)` 後補 `.frame(minHeight: 46)`（`contentShape` 已在），與同 PR 的 toggle 用同一個保險係數。

### N3（informational）`PasswordSignInModel.swift:54` — 空欄位按「登入」完全沒有回饋

`guard !signingEmail.isEmpty, !password.isEmpty else { return false }` 靜默 return。同一目錄的 `EmailSignInModel.sendCode()` 對空／格式錯的 email 是**給錯誤文案**的（「這個 Email 好像沒打完…」），兩個姊妹畫面的行為不一致。票文只要求「不送出」、稿面也沒有空欄位態，所以不算違規；但長輩優先的 app 讓主 CTA 按下去毫無反應，屬 UX 缺口。**處置建議**：記入 LS-96 待辦池（P3・size:XS），或本票順手補一句 help text，由 orchestrator 裁定。

### N4（informational）`LittleSproutTests/PasswordSignInModelTests.swift:165-190` — 再入測試在 guard 迴歸時會「掛住」而不是「變紅」

mutation 3 實測：拿掉 `guard !isSigningIn` 之後，這個測試的 stub handler 會遞迴呼叫 `model.signIn()` → 無限遞迴，整個 test suite 不結束（我 600s 後 kill）。測試確實偵測得到迴歸，但呈現方式是 CI job timeout（燒滿整個 job 額度、log 裡看不到原因），不是一條清楚的紅。**建議**：handler 裡用一個只重入一次的旗標（或 `stub.passwordSignInAttempts.count < 2` 才遞迴），讓迴歸時是 `XCTAssertEqual(1, 2)` 這種秒紅。**處置建議**：記入 LS-96。

### N5（informational）`LittleSprout/TapTargetGateScreenName.swift:79` — `.welcome` 註冊了但不量測，`WelcomeView` 同時仍留在 exemptions
