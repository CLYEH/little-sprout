## Handoff — LS-52

**Ticket**：albums_update／comments_update owner 分支不限欄位（LS-48 同形狀洞）

**已完成（修法選擇與理由）**
- 裁量選 **(b) RPC**，不選 (a) column-level grant。理由：`families`／`family_members`／`content_reports`／`media` 能用 column-level grant 收斂，是因為它們的 UPDATE policy 各分支允許改的欄位集合本來就一致；`albums_update`／`comments_update` 的兩個分支（作者全改 vs owner 只改 `deleted_at`）欄位集合本來就該不同，column grant 是角色層級、不分列，物理上表達不出「依這一列是不是我建立的給不同欄位集合」。
- **本機用 Supabase CLI 映像（PostgreSQL 17.6）實測**過「RLS WITH CHECK 自我 join 比對 OLD 值」這條路：純寫法會被 Postgres 判 `42P17 infinite recursion`；包一層 SECURITY DEFINER 繞過遞迴後**確實可行**（owner 竄改內容會被 WITH CHECK 擋下、噴出真正 `42501`，deleted_at-only 更新正常放行）。最終沒有採用——不是做不到，是這個寫法要求逐欄列舉「除了 deleted_at 以外都要跟舊值一樣」，日後 albums/comments 加新欄位容易忘記同步、悄悄重開同一種洞；RPC 版本「函式裡只 SET 一欄」由程式碼形狀保證，對 schema 演進更安全（這與 LS-48 對 diaries 選 RPC 同一個理由）。
- 與 LS-48 diaries 的差異（刻意，非漏做）：這裡的洞只在 owner 分支，作者改自己內容的分支本來沒問題，**不擴大範圍**——albums/comments 的作者直接 UPDATE 路徑與 grant 完全不動，只把 owner 分支從 policy 移除，改走新增的 `set_album_deleted`／`set_comment_deleted`（只碰 `deleted_at`）。

**已知的行為差異（重要，已寫進 docs/API.md）**：owner 對別人 albums/comments 直接 `.update()` 改內容欄位**不會**拿到 `42501`——USING 比對不上該列，Postgres 標準反應是靜默排除、影響 0 列（本機實測驗證）。這跟原票文字預期的「owner 改他人 title/body → 42501」不同：那個預期成立的前提是選 (a) 設計（owner 分支留在 USING）；選 (b) 之後那一列完全不在 USING 範圍內，不會走到會噴錯的 WITH CHECK。owner 真正會拿到明確 `42501`／`LS023`／`LS024` 的路徑是新的兩支 RPC，這才是 owner 該用的介面。
