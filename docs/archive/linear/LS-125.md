### Major（2，皆為新發現）

**P1（PLAUSIBLE）— `ignoreDuplicates: true` 會讓重試前的拖曳排序／移除被靜默丟棄（n1 修法引入）**
`LittleSprout/Services/Diary/SupabaseDiaryAPIClient.swift:56-58`
```swift
try await client.from("diary_media")
    .upsert(rows, onConflict: "diary_id,media_id", ignoreDuplicates: true)
    .execute()
```
`ignoreDuplicates: true` → `Prefer: resolution=ignore-duplicates` → Postgres `INSERT … ON CONFLICT (diary_id, media_id) DO NOTHING`。**衝突列的 `sort_order` 完全不會被更新。**

而 `DiaryComposerStore` 的續傳保護保證重試一定用同一個 `diaryID`＋同一批 media id（這正是 n1 修法成立的前提），但 **`mediaIDs` 的順序是跟著當下的 `photos` 陣列走的**（`uploadAllMedia()` 依 `for draft in photos` 收集），而 `sort_order` 是 `attachMedia` 依 `mediaIDs.enumerated()` 現算的。兩者一衝突，新算出來的 `sort_order` 就被 `DO NOTHING` 吃掉。

**失敗情境（排序遺失）**：使用者選 A、B、C 三張 → 發佈 → 上傳完、`create_diary_entry` 成功、`attachMedia` 在伺服器端**已經 commit**、但回應在網路上遺失（行動網路逾時／連線中斷，正是 n1 當初要處理的那個窗）→ client 判失敗、進 12c → 使用者順手把 C 長按拖到第一格（票文 Scope 2 明訂的功能，驗收條件也列了）→ 按「重新發佈」→ `mediaIDs` 變成 `[mC, mA, mB]`、rows 帶 `sort_order` 0/1/2 → 三列都撞主鍵 → **全部 DO NOTHING** → DB 裡仍是 A=0、B=1、C=2 → `.success` → dismiss。時間軸（LS-126）依 `sort_order` 排出來的是**拖曳前的順序**，使用者看到的是「成功」。

**兩個更難看的變形**：
- **移除**：使用者在同一個窗之後移掉 B 再重試 → `mediaIDs` 只有 `[mA, mC]`，但 `diary_media` 裡 B 的那一列**沒有人刪**（upsert 只 insert 不 delete）→ 發佈出去的日記帶著一張使用者明確刪掉的照片。
- **前插**：使用者新增 D 並拖到第一格 → D 以 `sort_order=0` 成功 insert，A 保留舊的 `0` → **同一篇 diary 出現兩個 `sort_order=0`**（該欄沒有唯一約束，DB 不會報錯），這兩列之間的排序從此不確定。

**修法（一個 token）**：`ignoreDuplicates: false`（＝`resolution=merge-duplicates` → `ON CONFLICT DO UPDATE`）**同時**達成 n1 的目標與正確排序——既不會撞 `23505` 死路，又會把既有列的 `sort_order` 更新成新值。權限我查過可行：`20260822120000_init_schema.sql:369` 是 `grant select, insert, update, delete on public.diary_media to authenticated`，且 `20260822120200_rls_policies.sql:261-263` 有 `diary_media_update` policy（`using`／`with check` 皆為 `family_id in (select private.contributor_family_ids())`），UPDATE 這條路是通的。

**連帶要改測試**：`SupabaseDiaryAPIClientTests.test_attachMedia_usesUpsertWithIgnoreDuplicatesOnConflictKey` 目前把錯誤的語意釘死了——斷言訊息寫「應該帶 ignore-duplicates，**不是預設的 merge-duplicates**」。改修法時這條要一起反轉，否則會被自己的測試擋住。

**「移除」那個變形 `merge-duplicates` 解不掉**（需要 delete-not-in-set，或收斂成一支 `set_diary_media` RPC）。也請注意 LS-96 `d8634a08` 第二條目前的描述是「已上傳成功、之後被移出佇列的 media **不會被 attach** 也不會被刪」——在 upsert＋回應遺失這條路徑上它**已經被 attach 了**，那條池項的敘述涵蓋不到這個情況，入池時要補一句。

**誠實標註**：`DO NOTHING` 不更新 `sort_order` 是 Postgres／PostgREST 的確定語意（讀碼可證）；但觸發前提「伺服器端已 commit、回應遺失」我在本 gate **無法重現**，故標 PLAUSIBLE。之所以仍列 major 而不是 minor：後果是**靜默的錯誤資料＋回報成功**（跟 R1 M3、R2 N1 同一類），比 R2 n1 原本那個「大聲的死路」更難被使用者察覺；而且它打到的正是票文 Scope 2／驗收條件明列的拖曳排序功能。coordinator 在派工時已預先裁定此情況屬 major，我獨立複核後同意。

第三條是關鍵——有了這條負向斷言，「字串剛好包含」這種假綠就過不了；R3 版本只有正向斷言且把語意釘反了，這輪反轉得乾淨。PostgREST 對這兩個 `resolution` 值的語意（merge → `ON CONFLICT DO UPDATE`；ignore → `DO NOTHING`）是它的公開契約，測試釘在「我方送出的意圖」這一層是正確的邊界。

`sort_order` 的實際數值另有既存的 `test_attachMedia_insertsRowsWithSortOrderMatchingArrayIndex` 覆蓋（逐列斷言 `sort_order == 0`／`1`＋`media_id`／`diary_id`／`family_id`），跟本輪新增的 store 層順序測試、以及這條 Prefer 測試，三條合起來把 client 端的鏈路補完整了。

權限面我 R3 已核、本輪複查不變：`init_schema.sql:369` 有 `update` grant，`rls_policies.sql:261-263` 的 `diary_media_update` policy `using`／`with check` 都是 `family_id in (select private.contributor_family_ids())`，`DO UPDATE` 走得通。另外確認 `diary_media` **沒有任何 trigger**，所以 `DO NOTHING`→`DO UPDATE` 不會多觸發任何副作用。

**(2) q2 的 wire 日期字串比對有沒有時區陷阱** —— 沒有，且比原本的 `Date` 比對更安全。
關鍵在於快照與送出用的是**同一支函式、同一個輸入**：store 存 `BirthdayFormat.wireString(from: entryDate)`，`SupabaseDiaryAPIClient.createDiaryEntry`／`updateDiaryEntry` 送的也是 `BirthdayFormat.wireString(from: entryDate)`。而 `wireString` 的語意是「用 `Calendar.current` 抽本地年月日 → 重建成 UTC 午夜 → 格式化」，所以字串永遠等於使用者在 `DatePicker` 上看到的那一天。

同一天不同 TZ 的情境我推過：若裝置時區在兩次嘗試之間改變（跨時區飛行／DST／手動改），同一個 `Date` 會算出不同的 wire 字串 → 快照不等 → 觸發 `updateDiaryEntry` → 送出的正是**新算**的那個字串。比對端與送出端始終一致，不會出現「比對說沒變、實際送了別的」或反過來的錯配；多打的那一次 update 本身是正確行為（app 認定的「哪一個日曆日」確實隨裝置時區改變了）。唯一的理論窗是「同一次 publish 內、store 算快照到 client 編碼 payload 之間時區改變」（次秒級），而且下一次重試會自動收斂，不構成問題。

**(3) 重排重試測試是否真的檢查送出的序列而非只數呼叫次數** —— 有，檢查的是序列。
`test_publish_retryAfterAttachMediaFailure_afterReorder_sendsMediaIDsInNewOrder`：
```swift
XCTAssertEqual(diaryClient.attachMediaCalls.first?.mediaIDs, [firstMediaID, secondMediaID], "第一次嘗試依原始佇列順序送出")
store.move(id: originalOrder[1], toIndex: 0)
XCTAssertEqual(diaryClient.attachMediaCalls.last?.mediaIDs, [secondMediaID, firstMediaID], "重試前重新排序過，第二次送出的 mediaIDs 順序要跟著新排序走…")
```
前後兩次各斷言一次**完整陣列**（不是 count、也不是只看首元素），中間夾一次真正的 `store.move(...)`。鑑別力：若 `uploadAllMedia` 拿的是舊快照、或記憶表以插入順序而非佇列順序回傳，第二條就會紅。`sort_order` 整數本身在 store 邊界還不存在（`AttachMediaCall` 只帶 `mediaIDs`，`sortOrder` 是 `SupabaseDiaryAPIClient` 用 `enumerated()` 現算的），所以「斷言陣列順序」是這一層能做到的最強形式，且該測試的文件註解自己就把分工寫清楚了（另一半交給 wire 層那兩條），沒有把覆蓋範圍講得比實際大。
