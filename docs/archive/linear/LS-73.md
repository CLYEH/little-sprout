## 描述

## 事故

2026-08-25 [LS-46](https://linear.app/little-sprout-app/issue/LS-46/設計定稿合併c-基準使用者指定調整-designlittlesproutpen) 分支 merge development 後 push：push-gate 的 `xcodebuild -resolvePackageDependencies` 對七個相依套件全部 `fatal: unable to read tree <sha>`，100% 重現，清 cache 無效；在 hook 外 `env -u GIT_DIR xcodebuild -resolvePackageDependencies` 一次成功。

## 根因

pre-push hook 由 git 啟動時會 export `GIT_DIR`（linked worktree → `.git/worktrees/<n>`）等環境變數；xcodebuild 內嵌的 SPM 用 git 操作相依套件 mirror 時繼承這些變數，去 little-sprout 的 repo 找套件的 tree。只有「本次 push 前 SourcePackages 尚未解析（merge 帶進新相依／全新 worktree）」時才觸發——先前被誤判為「SPM 瞬斷」（[LS-56](https://linear.app/little-sprout-app/issue/LS-56/harnesserror-codes-check-抽取規則硬化註解掉的-case表格首欄格式artifact-retention) 加了 10 秒重試）。

## 修法

`scripts/gates/push-gate.sh`（與 `commit-gate.sh` 若有呼叫 xcodebuild／swiftlint）開頭 `unset GIT_DIR GIT_WORK_TREE GIT_INDEX_FILE GIT_PREFIX`；[LS-56](https://linear.app/little-sprout-app/issue/LS-56/harnesserror-codes-check-抽取規則硬化註解掉的-case表格首欄格式artifact-retention) 的重試保留但註解改寫根因；COLLABORATION §4 push gate 敘述與 §7 補記。回歸證明：hook 環境模擬（`GIT_DIR=.git/worktrees/x` 下跑 resolve → 炸；unset 後 → 過）。

### 根因驗證（不只 PLAUSIBLE）
在 clean worktree（LS-46）另建一個獨立 scratch git repo，模擬「SPM 內嵌 git 在別的 repo 目錄下執行、但繼承了 little-sprout 的 `GIT_DIR`」這個情境：

```
cd <scratch-repo>            # 一個全新、與 little-sprout 無關的 repo
GIT_DIR=/…/.git/worktrees/LS-46 git log --oneline -3
# → 印出 little-sprout 的 commit history，不是 scratch repo 的
GIT_DIR=/…/.git/worktrees/LS-46 git cat-file -t <scratch-repo-的-tree-sha>
# → fatal: git cat-file: could not get object info（exit 128）
```

這與票上描述的「`unable to read tree <sha>`」錯誤形態一致：一旦 `GIT_DIR` 被匯出且被子 process 繼承，git 會無視 cwd、強制去該 `GIT_DIR` 指向的 object database 找東西——SPM 在套件 checkout 目錄下跑 git 操作時正是這個情境。根因判定成立。

另外用同一顆 GIT_DIR 在**同一個** repo 內測試（`git rev-parse --show-toplevel`、`git diff --stat`）皆正常返回——證實只有「cwd 與 GIT_DIR 指向不同 repo」時才會炸，與 LS-46 事故只在「SPM 需要重新解析相依」時觸發（fresh worktree／merge 帶新相依）的描述吻合。

### 副作用檢查
- **push-gate.sh 自己的 git 指令**：unset 發生在 `cd "$(git rev-parse --show-toplevel)"` 之前，但因為此時 GIT_DIR（若未清）本來就指向「當前這個 repo」（hook 由這個 repo 的 git 啟動），所以清或不清這行 `rev-parse --show-toplevel` 結果相同；清掉之後續所有 `git ls-files`／`git symbolic-ref`／`git rev-parse --verify`／`git merge-base`／`git diff --name-only` 皆在 cd 過的 toplevel 下以一般 discovery 運作，逐一核對語意不受影響。
- **子腳本**（`merge-conflict-check.sh`、`branch-ticket-check.sh`）以 `bash <path>` 呼叫，繼承 push-gate 已清空的環境；兩者所有 git 呼叫（`rev-parse -q --verify`、`ls-remote`、`merge-tree --write-tree`、`symbolic-ref`）皆為當前 repo 內操作、無 `-C` 到其他目錄，不受影響，且反而少了被誤帶 GIT_DIR 污染的風險（原本沒觸發是因為它們也都在同一 repo 內操作）。
- **stdin refs**：pre-push hook 用 `exec` 取代自身 image 執行 push-gate.sh（`.githooks/pre-push`: `exec ".../push-gate.sh"`），保留原 stdin fd；push-gate.sh 本身不讀 stdin，不受此變更影響。
- **GIT_PREFIX**：script 清掉之前就已 `cd` 到 toplevel，之後所有指令 cwd＝toplevel，prefix 本來就是空——unset 無實質差異，純粹補齊語意完整性，不是回歸風險。

### commit-gate.sh 不清（informational，同意判定正確）
`commit-gate.sh` 沒有呼叫 xcodebuild／SPM，唯一的外部 git 依賴敏感點是 pre-commit hook 下 `GIT_INDEX_FILE`——git 在某些 partial commit 情境（如 `git commit -a`、`git commit -p` 之後）會把它指向一個反映「即將被 commit 的內容」的暫存 index，`commit-gate.sh` 的 `git diff --cached`／`git ls-files`／`tracked-ignored-check.sh`／`evidence-path-check.sh` 都仰賴這個 index 的準確性。若比照 push-gate 也 unset 掉，會退回讀 `.git/index`（工作目錄目前的 stage 狀態），在這些 partial-commit 情境下可能與「實際要被 commit 的內容」不一致，等於引入新 bug 去修一個不存在的問題（commit-gate 沒有 xcodebuild/SPM，没有本票要修的症狀）。PR 未動 commit-gate.sh 是正確判斷。
