## 逐條查實

**1. 根因主張 — 成立（敘述有一處方向倒置，見 N1）**
`TimelineStore.refresh` 是 `@MainActor`（`TimelineStore.swift:18`／`:88`），`apiClient` 是 `TimelineAPIClient: Sendable` existential（`TimelineAPIClient.swift:18`），`StubTimelineAPIClient` 是 `final class ... @unchecked Sendable`（非 actor），`box` 是 `OSAllocatedUnfairLock(initialState: Box())`——`fetchPointersCalls.append(call)` 在 lock 內是**原子的、但兩次獨立呼叫之間沒有順序保證**。`await apiClient.fetchTimelinePointers(...)` 這一跳離開 MainActor 到 cooperative pool，所以「MainActor 這側看到 `refreshState == .submitting`」只證明 refresh 走到了 await 之前那一行，不證明 stub 的 append 已經發生；測試接著發出的第二次呼叫的 append#2 於是可能先於 append#1 完成 → `fetchPointersCalls.last` 是第一次呼叫（`childID == nil`）→ 正是 CI 原文 `("nil") is not equal to ("Optional(6E60...)")`。順序問題出在**兩次 append 之間**（lock 只保證互斥，不保證誰先），不在 `OSAllocatedUnfairLock` 本身。

**2. 修法 — 同步點正確**
`TimelineStoreTests.swift:144` `await gate.waitForWaiters(count: 1)`。`AsyncGate.waitForWaiters` 的等待者計數遞增點在 `wait()` 內 `await withCheckedContinuation { continuations.append($0) }`（`AsyncGate.swift:26`），而 stub 的 `box.append(call)` 是 `fetchTimelinePointers` 本體中**在 handler 呼叫之前**的同步步驟（`StubTimelineAPIClient.swift:75-77`：先 append，再取 handler，再 `await handler(...)` → handler 內才 `await gate.wait()`）。所以 `waitForWaiters` 回傳 ⇒ 第一次呼叫的 append 必已完成（同一 task 的 program order＋actor hop 的 happens-before，`box` 的 lock 另外保證可見性）。第二次 `refresh` 是 inline `await` 到完成才斷言 ⇒ append#2 必在其後。`.last` 因此決定性等於第二次呼叫。無 `Task.sleep`；`waitForWaiters` 內的 `Task.yield()` 是條件式自旋（退出條件＝真正要的那個保證），不是猜時間。

## Findings

**N1（minor，文件精確度，不阻擋）** `LittleSproutTests/Support/AsyncGate.swift:14-15`（與 `TimelineStoreTests.swift:121-123` 同句）：「`box.append(call)` ⋯ 跟 MainActor 這側先做完的 `refreshState = .submitting` 賦值之間**沒有 happens-before 保證**」方向倒置——就第一次呼叫這條 task 而言，賦值→`await`→callee 的 append 是 program order，賦值**確實** happens-before append。真正缺的是反向蘊含：**測試 task 觀察到 `.submitting`，推不出 callee 已經 append**，因此 append#1 與測試緊接著觸發的 append#2 之間無排序。建議改寫成「`refreshState == .submitting` 只證明 refresh 走到 `await` 之前那一行，不證明 stub 已 append；兩次呼叫的 append 落在 cooperative pool，完成順序不定」。下一句「兩次獨立呼叫各自的 `box.append` 有時會以相反順序完成」已是正確機制，結論不受影響——這是長期文件（未來測試會照抄這段推理），值得把方向講準。

**N2（informational）** `AsyncGate.swift:42-46`：`waitForWaiters` 無逾時、也沒擋 `isOpen` 已開的情況——若在 `open()` 之後呼叫，`wait()` 走 `if isOpen { return }` 不會登記等待者，迴圈會永久自旋，測試變成掛到 XCTest 全域逾時（而不是乾淨落紅）。本票唯一呼叫端在 `open()` 之前，現況安全；建議 doc 明寫前置條件「必須在 `open()` 之前呼叫」，或加一個 deadline 後 `XCTFail`。

**N3（informational，scope 外）** `AlbumsStoreTests.swift:11` 還有第三份同構的 `AlbumsTestAsyncGate`。票文只點名「`EULAStoreTests` 同名 helper」，未動是對的（手術式修改）；建議記入 LS-96 待辦池，日後與 `Support/AsyncGate.swift` 統一。
