## 規則（寫進 CLAUDE.md 設計 gate 段＋COLLABORATION §1/§7＋`.claude/agents/{ui-designer,visual-reviewer}.md`）

1. **聚焦輪條款**：≥5 輪不收斂且 reviewer 明示「爭點為可機械複驗項、非品味僵持」時，orchestrator 得裁定「定點修＋只核銷修項＋溢出重掃」的聚焦輪，不進使用者仲裁；reviewer 需在裁決中寫明性質。
2. **收工溢出掃描必跑**：ui-designer 每輪 handoff 必附全樹絕對座標溢出掃描輸出（`TOTAL_NODES`／`FLAGGED`／逐筆分類）；visual-reviewer 以同方法重掃比對。
3. **分段落地**：每完成一項即落地＋commit＋push；`.pen` 不透明檔無法事後拆 commit。
4. **掃描收據 gate（機械）**：`design/littlesprout.pen` 在磁碟上是**明文 JSON**（CI 的 `design-landing-check` 已在解析節點結構；[LS-72](https://linear.app/little-sprout-app/issue/LS-72/設計-chorels-46-r10r11-informational-f6-f8print-edge-token-合併tokens) review／sweeper 2026-08-25 實測確認），但溢出掃描與截圖需要 Pen app 的**版面引擎**（絕對座標由 layout 算出），GitHub runner 沒有 Pen，所以掃描本身不能在 CI 跑。改為 handoff 時把掃描結果寫成 `design/evidence/<票號>-r<n>-overflow.json`（TOTAL_NODES、FLAGGED、分類表、HEAD sha、節點數）隨 PR 提交；CI `design-landing-check` 加驗：.pen 有變更的 PR 必附同 sha 的 overflow.json、`TOTAL_NODES` 與 landing gate 節點數一致、`FLAGGED` 每筆有分類。正負對照自測。CI 能做的靜態檢查（節點數、token 引用存在、文字節點非空）盡量搬進 CI，不靠收據。

### F1（major，假陽性——擋住本票自己規定的工作流程）

`scripts/gates/design-evidence-check.sh:100-176`（`for ev in "${candidates[@]}"` 迴圈把**每一份**本 PR 新增的收據都拿去比對**工作區當下**那份 .pen 的節點數）

**失敗情境（已實跑重現）**：一票＝一條 branch＝一個 PR、設計票至少 3 輪迭代（CLAUDE.md／§1），所以 r1／r2／r3 收據會累積在同一個 PR 的 diff 裡。合成 repo：base 2 節點 → 第 1 輪落地 3 節點＋`LS-67-r1-overflow.json`(total_nodes=3) → gate 綠；第 2 輪落地 4 節點＋`LS-67-r2-overflow.json`(total_nodes=4) → gate **紅**：

```
✗ design-evidence gate：design/evidence/LS-67-r1-overflow.json 未通過：
    - total_nodes 不符：收據=3，design-landing-check 算出的節點數=4
✓ design-evidence gate 通過：design/evidence/LS-67-r2-overflow.json（…total_nodes=4…）
rc=1
```

r1 收據記錄的是第 1 輪那個時點的 .pen，永遠不可能等於第 2 輪之後的節點數。ui-designer 只有兩條路可走，兩條都是把證據弄假：(a) 回頭改 r1 的 `total_nodes` 讓它「對得上現在」——收據就不再是第 1 輪的掃描結果；(b) `git rm` 掉 r1 收據——已實測這樣 gate 就綠（`LS-68-workaround.sh`），但每輪證據鏈被毀，正好違反本票新寫進 CLAUDE.md 的「**每輪**收工必附全樹溢出掃描收據」。也就是說：這支 gate 目前只能承受「一個 PR 一份收據」，而規約要求的是每輪一份。LS-67 第 1 輪會綠、第 2 輪就會撞牆。

**建議修法**（與 F2 同一支修改）：每份收據改成比對**它自己 `head_sha` 那個時點**的 .pen 節點數（`git show <head_sha>:<pen>` 落暫存檔後餵 `design-landing-check.sh --print-nodes`），而不是比對工作區當下的檔；工作區當下的比對只留給「最新那份收據」。

### F2（major，假陰性——票文原意「收據對應 .pen 最終狀態」未被任何機制守住）

同檔 `head_sha` 判定：`if not isinstance(sha, str) or sha not in pen_commits:`（只驗**歸屬**，不驗**是不是最後一次**）

**失敗情境（已實跑重現）**：commit A 落地 .pen（a、b 兩節點重疊）→ commit B 交收據引用 A → 掃描發現碰撞、commit C 把 b 移開修好（**節點數不變**）。gate 綠：

```
最後一次動 .pen 的 commit=0cb290b，收據引用的是 14b06b6
✓ design-evidence gate 通過：…（head_sha=14b06b6，total_nodes=3，兩支掃描皆有輸出）
rc=0
```

這正是 PR 內兩次 .pen 落地、收據只引用第一次、**最後一次變更完全沒有收據**的情形。要點在於：handoff 與 §7 都把它寫成「只要 `total_nodes` **剛好**沒變才抓不到」的巧合型盲區，但實際上**溢出修正的標準動作就是搬位置／改寬高，節點數天生不變**——這個「盲區」在本 gate 最該守的那條路徑上是常態而非巧合，殘餘保護幾近於零。

而「自我指涉不可能」只證明了「不能比對 PR 最終 head sha」，**沒有**證明「不能比對最後一次動這份 .pen 的 commit」。後者完全可驗、且本票規定的兩支分開 commit 工作流程天然滿足它（收據那支 commit 不碰 .pen，所以最後一次 .pen commit 就是收據要引用的那一支）——我在同一個合成 repo 印出 `git rev-list <base>..HEAD -- <pen> | head -1` = `0cb290b`，正是漏掉的那次。建議與 F1 合併修：**輪次最高（或最新）那份收據的 `head_sha` 必須等於 `base..HEAD` 範圍內最後一次觸碰該 .pen 的 commit**，早期輪次的收據則按 F1 用各自的 snapshot 對帳。這樣 F1 的假陽性與 F2 的假陰性一起解，且不需要任何人偽造或刪除收據。
