## Blocker／Major

### F1（major）retry 的時間預算是「每頁」而不是全域，可讓 `rules` job 撞 `timeout-minutes: 10` 被整支取消
`scripts/gates/pr-body-check.sh`（`curl_with_retry` 與其外層 `while True:` 分頁迴圈，約 236–283 行）＋`.github/workflows/ci.yml:29`（`rules: timeout-minutes: 10`）

`curl_with_retry` 放在**分頁迴圈裡面**，所以「4 次嘗試＋退避 5/15/30s」是**每一頁各一份**，不是整次反查一份。實測數字：

| 項目 | 值 | 來源 |
|---|---|---|
| `rules` job 上限 | 600s | `ci.yml:29` |
| 本 PR 該 job 實際耗時 | 370s（step 9＝197s、step 13＝167s） | job 101347043257 step timings |
| pr-body-check（step 6）健康時 | **1s** | 同上 |
| LS-96 comment 數 | **>250**（`list_comments limit=250` 仍 `hasNextPage:true`） | 實查 |
| GraphQL 每頁 | `comments(first: 100…)`（`pr-body-check.sh:233`）→ **≥3 頁** | 程式碼 |
| 每頁最壞加時 | 3×25s（`--max-time 25`）＋50s 退避 ≈ **126s**（第 4 次成功）／150s（全敗即 die） | 程式碼 |

**失敗情境**：Linear 間歇逾時（＝本票要修的 2026-09-05 22:13–23:25 那段），PR body 帶 LS-96 池項申報（PR #327 自己就有 8 條，這條路徑天天走）。只要 **3 頁裡有 2 頁**各吃滿退避階梯：370 + 252 = **622s > 600s**，job 直接 timeout 被取消——比原本「25s 乾脆紅掉、job 6 分鐘內收工」更糟，而且被取消的正是本 PR 剛加 `if: always()` 的那兩支自測（step 9＋13 佔全 job 98% 時間、且排在 step 6 之後，pr-body-check 慢多久就從它們的預算裡扣多久）。三頁全吃滿＝370+378=748s，必 timeout。

審查交辦裡「總等待 ≤50s＋3×25s」這個前提，在單頁時成立、在實際的 ≥3 頁下不成立。

**建議修法**（擇一或併用）：(a) 改成**全域 deadline**——`deadline = time.monotonic() + PR_BODY_CHECK_LINEAR_BUDGET`（預設 90～120s），每次重試前檢查，跨頁共用，總時間與頁數脫鉤；(b) 退避縮成 3/6/12 並把 `--max-time` 降到 10s；(c) `first: 250`（Linear 上限）把頁數從 3 降到 2；(d) `rules` `timeout-minutes` 提到 20。自測要斷言的是**總 wall time 預算**，不是只斷言「有重試到」——現在的 ⑥g 只數了 curl 呼叫次數。

### F2（major）`--hold` 排隊逾 20 分的續等提示，在正式預設下是**不可達的死碼**
`scripts/ops/supabase-lock.sh:105`（`long_wait=${SUPABASE_LOCK_HOLD_LONG_WAIT:-1200}`）vs `:104`（`timeout=${SUPABASE_LOCK_TIMEOUT:-900}`）、等待迴圈 `:404–421`

迴圈順序是「先判 `waited >= timeout` → `exit 124`，之後才判 `waited >= long_wait` → 印提示」。預設 `long_wait=1200`（20 分）> `timeout=900`（15 分），所以 `waited` 永遠在 900s 就退出，**1200s 的那行永遠印不出來**。CLAUDE.md／各 agent 定義寫死的也是「`--hold` 最多等 15 分鐘、exit 124」，所以 20 分鐘這個數字本身就與現有規約衝突。

**實測**（fixture lock，非真容器）：
- 預設 `SUPABASE_LOCK_HOLD_LONG_WAIT`（1200）＋`SUPABASE_LOCK_TIMEOUT=3` → 輸出含「已排隊超過」**0 次**。
- 控制組 `SUPABASE_LOCK_HOLD_LONG_WAIT=1`＋同樣 timeout=3 → 印出「⚠ supabase-lock：--hold 已排隊超過 0 分鐘仍未取得…逾時上限 3s」。

自測 ㉟（`supabase-lock.test.sh`）同時覆寫 `SUPABASE_LOCK_TIMEOUT=3 SUPABASE_LOCK_HOLD_LONG_WAIT=1`，把 long_wait < timeout 這個**出貨預設沒有的關係**做成前提——這支測試在出貨預設壞掉時不會紅（CLAUDE.md Rule 8「測試要能因業務邏輯改變而失敗」）。`docs/COLLABORATION.md` §7 新列也把這個印不出來的行為寫成已交付。

順帶：控制組輸出「已排隊超過 **0** 分鐘」——`$(( long_wait / 60 ))` 整數除法，秒級覆寫時訊息會退化。

**建議修法**：預設改成小於 timeout 的值（例如 600s＝10 分），並在參數驗證處加 `long_wait < timeout` 的檢查（不成立就 clamp＋印一行警告，別靜默）；自測補一組「不覆寫 long_wait、只縮 timeout」的負控，斷言預設關係下提示仍印得出來。

### F3（minor）waiter 檔沒有回收機制（tomb 語意缺一半）

### F4（minor）`simulator-lock --udid` 部分套用後不復原，且復原失敗完全靜默
`scripts/ops/simulator-lock.sh:139–146`（`apply_sim_ui`／`restore_sim_ui`）


**失敗情境 A**：`content_size medium` 成功、`appearance light` 失敗 → `ui_changed` 停在 0 → `restore_sim_ui` 直接 return → 模擬器被留在 medium，原值（例如 large）再也回不來，而且一個字都不印。自測 ⑤ 的 `setfail` stub 讓**所有** set 都失敗，所以「先成功後失敗」這個部分套用的情況沒被覆蓋。
