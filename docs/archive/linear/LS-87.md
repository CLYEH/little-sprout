## 描述

## 來源

使用者 2026-08-25 問「gate 全部放在 script，是否都由 orchestrator 主動執行？被執行有硬門檻嗎？」盤點現況：

| 層 | 機制 | 硬度 |
| -- | -- | -- |
| 伺服器端 | GitHub 保護（main／development／test）：必經 PR、required checks `ci`／`lint`／`rules`／`db`、enforce_admins、禁 force push | **硬**（orchestrator／agent 都繞不過） |
| 本機自動 | `core.hooksPath=.githooks`：commit-msg／pre-commit／pre-push 對每個 worktree 自動觸發 | 硬（只有 `--no-verify` 可繞，規約禁止；CI `rules` job 為伺服器端兜底） |
| orchestrator／agent 手動 | pr-body-check（CI 兜底→實質硬）、**merge-reviewer 派工與 APPROVE**、**QA PASS 才晉升**、visual-reviewer 輪次、收尾儀式、巡檢／lane／cycle | **軟**：沒有任何機械門檻——`gh pr merge` 只看 CI 綠（approvals=0）；promote 不檢查 QA；全靠 orchestrator 記得 |

軟層的兩個核心裁決（審查、QA）目前只存在於 Linear comment，與 merge／promote 動作之間沒有機械連結。

## 前饋（規約）

* F1 COLLABORATION §1／§4：merge-reviewer 的裁決除寫 Linear comment 外，**必須**對 PR head SHA 貼 GitHub commit status `merge-review`（APPROVE→success、ITERATE／REQUEST_CHANGES→failure，description 帶 Linear comment id）；head 變動（新 commit）即需重貼。
* F2 qa agent 的裁決同樣貼 status `qa`（PASS→success；FAIL→failure；BLOCKED→failure 並在 description 註明原因）到 test 分支 tip SHA。
* F3 §2：test→main 晉升條件明寫「該 SHA 的 `qa` status 為 success」。
* F4 §4 push gate：`git push --delete`／zero-sha 的推送不跑 gate（純 ref 刪除）。

## 反饋（機械）

* **G1 GitHub 保護**：development／test／main 的 required checks 加 `merge-review`（`gh api -X PATCH …/protection/required_status_checks`），`gh pr merge` 在無 success status 時被 GitHub 拒絕；head 更新後舊 status 不隨 SHA 走 → 自動要求重審。promote／back-merge PR（head 為保護分支）由 orchestrator 依 §2 貼 `merge-review=success`＋description「promote: no content diff」（[LS-85](https://linear.app/little-sprout-app/issue/LS-85/harness晉升改-fast-forward-pushpromotesh取消-back-merge-github) 落地後 promote 不再走 PR，此例外消失）。
* **G2 merge-reviewer／qa agent 定義**：`tools` 已含 Bash；定義加「裁決後執行 `bash scripts/ops/post-status.sh <sha> merge-review|qa <success|failure> "<desc>"`」；腳本封裝 `gh api repos/…/statuses/<sha>`，自測（stub gh）。
* **G3 [promote.sh](<http://promote.sh>)（**[LS-85](https://linear.app/little-sprout-app/issue/LS-85/harness晉升改-fast-forward-pushpromotesh取消-back-merge-github)**）**：test→main 前檢查 tip SHA 的 `qa` status 為 success，否則拒絕（[LS-85](https://linear.app/little-sprout-app/issue/LS-85/harness晉升改-fast-forward-pushpromotesh取消-back-merge-github) 若先落地，本票補這一段）。
* **G4 push-gate 早退**：pre-push 讀 stdin 的 `<local_sha>`，全 0 即為刪除 → 直接 exit 0（2026-08-25 [LS-86](https://linear.app/little-sprout-app/issue/LS-86/harness結案清理機制-github-併入即刪-head-分支done-收尾必移除-worktree本機分支cleanup) 清理實測：29 條分支刪除每條都跑整套 push-gate 含 xcodebuild，>5 分鐘一條）；自測補。
* **G5 SessionStart／patrol**：檢查 `git config core.hooksPath` 為 `.githooks` 且三支 hook 可執行，否則印警示（hooks 未安裝時本機 gate 靜默不跑，CI 才會攔）。
* **G6 §7 對照表**：審查裁決（前饋 F1；反饋 G1＋G2）、QA 裁決（前饋 F2/F3；反饋 G3）、刪除推送（F4；G4）、hooks 安裝（G5）。盲區：status 由 agent 貼，agent 說謊仍可過——但「沒審就併」「審完 head 又改」兩類事故被機械擋住。

## 驗收

* 造一個無 `merge-review` status 的 PR → `gh pr merge` 被拒；貼 failure → 拒；貼 success → 可併；push 新 commit → 又被拒。
* `git push origin --delete <branch>` 在 3 秒內完成。
* hotfix 從 main；排 [LS-70](https://linear.app/little-sprout-app/issue/LS-70/harness並行後端票搶同一個本機-supabase-容器db-reset-互踩-隔離或序列化) → [LS-30](https://linear.app/little-sprout-app/issue/LS-30/harnesslittle-sprout-brand-專案-skill設計語言定案後) → [LS-85](https://linear.app/little-sprout-app/issue/LS-85/harness晉升改-fast-forward-pushpromotesh取消-back-merge-github) 之後（與 [LS-85](https://linear.app/little-sprout-app/issue/LS-85/harness晉升改-fast-forward-pushpromotesh取消-back-merge-github) 共用 protection 變更，可合併實作）。

## Merge review — PR #146（`hotfix/LS-87-verdict-status` → main，head `60f78c5`，base `10bfb30`）

**Verdict：REQUEST_CHANGES**（1 blocker、0 major、3 minor、3 informational）

---

### Blocker

**B1 — `scripts/ops/post-status.test.sh:104`（案例 ⑦「gh 未安裝 → exit 2」）在 Linux runner 上必紅，PR head 的 required check `rules` 目前是紅的**

- 事實：`gh pr checks 146` → `rules fail`（run `32828232343` / job `97740896708`），`mergeStateStatus=BLOCKED`。失敗行就是 `✗ ⑦ gh 未安裝應 exit 2（實得 1）`，其餘 patrol／supabase-lock／promote／post-status ①–⑥ 全綠。
- 失敗情境（根因）：測試用 `PATH="$work/nobin:/usr/bin:/bin"` 想「拿掉 gh」，但只拿掉了 stub——GitHub Actions ubuntu runner 的**真 gh 就在 `/usr/bin/gh`**，`command -v gh` 命中它，腳本因此走到 POST，再因 runner 無 `GH_TOKEN` 失敗 → exit **1**（非 2）。本機 macOS 上 gh 在 `/opt/homebrew/bin`，`/usr/bin:/bin` 裡沒有 gh，所以親跑會過——這是純環境相依的假綠。
- 我本機重現：以 `sysbin/gh`（模擬 runner 上的真 gh）放進 PATH 後跑同一情境 → `rc=1` ＋「POST … 失敗 … status 未貼」，與 CI log 一字不差。
- 附帶問題：在**有** `GH_TOKEN` 的環境，這個自測會真的對 `repos/{owner}/{repo}/statuses/0123…4567` 發 POST（假 SHA → 422）。自測不該碰網路。
- 修法（兩種我都實測 → `rc=2`、訊息「需要 gh」）：
  1. `out="$(cd "$repo" && env PATH="$work/nobin" /bin/bash "$post" "$SHA" qa success 'x' 2>&1)"`（可行是因為 `post-status.sh` 的 `command -v gh` 檢查排在 `git rev-parse` 之前）；
  2. 更耐改動：`ln -s` 把 `bash`／`git` 放進 `$work/nobin`，再 `PATH="$work/nobin"`（日後若把 gh 檢查移到 git 檢查之後也不會壞）。
- 腳本 `post-status.sh` 本身沒問題——「有 gh 但未登入 → exit 1 並明說未貼」是正確行為；壞的只有測試的 PATH 隔離。

---

### Minor

**M1（race）— `.claude/agents/merge-reviewer.md:28`：主推的取 SHA 指令是「當下 head」而非「你審的 head」**

步驟 1 首選 `gh pr view <PR#> --json headRefOid -q .headRefOid`，取到的是**執行當下**的 head。失敗時序：reviewer 對 H1 做 `git diff` → 審查期間 ios-dev（或上一輪 R1 的修法）push 出 H2 → reviewer 收尾時才跑該指令拿到 H2 → 對**沒審過的 H2** 貼 `merge-review=success` → H2 直接可併。這正是本票要擋的「審完 head 又改」的殘餘缺口。後半句「必須是你 `git diff` 的那個 SHA」寫對了，但排在推薦指令後面、且沒有機械保障。
建議：把 `git rev-parse <orchestrator 給的 head>`（開審當下就取，記進 verdict）列為首選；`gh pr view` 只用來**比對**，不一致時貼在已審的 SHA 並在 verdict 明說 head 已前進、需再審。若要機械化，`post-status.sh` 可加 `--pr <n> --expect <sha>`：head 與 `--expect` 不符即 exit 2 拒貼（另票即可）。

**M2（scope）— `scripts/ops/protection-apply.sh:77-84`：development 的 PATCH 順手把 `lint`／`rules` 從 any-app 收緊成 app 15368**

票文 G1 只要求「required checks 加 `merge-review`」。dry-run 的 `before` 顯示 development 現況是 `lint@any,rules@any`，套用後會變 `@15368`。實際風險低（兩個 check 確實只由 Actions 產生），PR body 的 dry-run 也揭露了，但這是**套用當下會一起生效、票文沒要求**的變更，§2 正文沒寫。建議二選一：檔頭／§2 明寫「順帶把 development 的 lint／rules 收緊到 app 15368」，或 development 的 request 保留原 app_id。

**M3（文件）— `docs/COLLABORATION.md:51` 核對指令的失敗路徑**

`git diff <merge> $(git merge-tree --write-tree <merge>^1 <merge>^2)`：`git merge-tree --write-tree` 在有衝突時 exit 1 並把衝突報告印到 stdout，命令替換會把那坨文字當成 tree-ish 餵給 `git diff`，orchestrator 看到的是看不懂的 git 錯誤而不是「非空＝有手解內容」。建議寫成先取 rc：`t=$(git merge-tree --write-tree A B) || { echo "衝突→不貼"; }; git diff <merge> "$t"`。

**I1 — ops 自測只掛 CI、不在 push-gate 跑**，所以「只有 Linux 會紅」的自測（B1）要等 CI 才看得到；本輪代 push 後也沒看 `gh pr checks` 就送審。建議把 `post-status.test.sh`＋`promote.test.sh`（本機各 <15s）加進 push-gate，或派 merge-reviewer 前先看一次 `gh pr checks`（LS-88 的 Stop／PreToolUse hook 可承接）。

**I3 — `.claude/agents/qa.md` 沒有 `tools:` 白名單**（繼承全部工具，Bash 可用，所以現在沒問題）。但日後有人替它補白名單而漏掉 Bash，新加的「必貼 status」會靜默不可執行。merge-reviewer.md 已明列 Bash ✓。
