### Findings

#### M1（major・效能／正確性）張數用「整頁 album_media 全抓回來 client 端 count」，會被 PostgREST `max_rows` 靜默截斷
`LittleSprout/Services/Albums/SupabaseAlbumsAPIClient.swift:43-55`（無 `.order()`、無 `.limit()`）＋ `LittleSprout/Services/Albums/AlbumsContentAssembler.swift:17,25-27`

`supabase/config.toml:18` `max_rows = 1000`（Supabase 雲端預設同值）。一頁 20 本相簿的 `album_media` 連結列總數一旦超過 1000，PostgREST 只回前 1000 列，而這支查詢**沒有 `.order()`**，回哪 1000 列不保證。

- **具體失敗情境**：家庭有 3 本相簿分別 700／400／50 張。`fetchAlbumMediaLinks` 回 1000 列（截斷），落在被截掉那段的相簿張數變小甚至為 0 → 卡片顯示「0 張相片」＋`.empty` tier（連扇影都不畫），看起來像空相簿；使用者點進去卻有照片。沒有任何錯誤、沒有 log。
- **次要成本**：每次 `refresh`（切 tab 觸發 `.task`、下拉、建立相簿後）都要傳整頁相簿的全部連結列（1000 列 JSON ≈ 90KB）；而且 `select("album_id,media_id")` 的 `media_id` 在沒有封面 fallback 的情況下**完全沒用到**，白付一半 payload。
- 不能沿用時間軸的先例：`TimelineContentAssembler.fetchDiaryContents` 的註解明寫「一頁 20 篇日記、每篇**上限 20 張**附照」，相簿沒有這個上限。
- **建議修法**（擇一）：(a) PostgREST 內嵌計數 `select=id,title,cover_media_id,created_at,album_media(count)` 一支查詢帶回張數（需先驗證目前 supabase-swift／PostgREST 版本支援）；(b) `select("album_id")` 只取一欄，張數改用每本 `head: true, count: .exact` 的 20 個小請求併發；(c) 開 `list_albums` RPC 回 `photo_count`（要 migration，屬另票）。至少要有「count 可能被截斷」的防線，不能靜默顯示錯的張數。

#### M2（major・race／資料完整性）建立相簿兩步非原子，第二步失敗＋重試＝多一本刪不掉的空相簿
`LittleSprout/Services/Albums/AlbumsStore.swift:107-121`（`createAlbum` → `setAlbumChildren`）＋ `LittleSprout/Features/Albums/CreateAlbumView.swift:175-189`（失敗不 dismiss，使用者只會再按一次）

- **具體失敗情境**：使用者填名稱、選了寶貝，按「建立相簿」。`INSERT albums` 成功、`set_album_children` 撞到網路瞬斷（或該寶貝剛好被別的成員軟刪 → `LS044`）→ `createAlbumState = .failure`、**不 refresh**，列表上看不到剛建好的那本，sheet 停在原地顯示錯誤。使用者理所當然再按一次 → 又 `INSERT` 一本 → 重複相簿。每重試一次多一本。
- 而且本票與 LS-142 稿面 LS-166 的「更多」選單（只有改名／刪除相簿）之前，**app 內沒有任何刪除相簿路徑**（repo 全文查無 `set_album_deleted` 呼叫端），使用者清不掉。
- **建議修法**：store 記住已建立的 `albumID`，重試時跳過 INSERT、只重跑 `setAlbumChildren`（`set_album_children` 是全覆蓋語意、天生冪等）；或第二步失敗時仍 `await refresh(...)` 並把文案改成「相簿已建立，但寶貝標記沒設定成功，可稍後再設定」。
- 測試也缺這條：`AlbumsStoreTests` 只有「createAlbum 本身失敗」，沒有「create 成功 + setAlbumChildren 失敗」的案例。
