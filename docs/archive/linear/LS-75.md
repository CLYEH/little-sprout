## 來源

使用者 2026-08-25 同意：「把 WIP 上限寫進規約——harness lane 1 張、後端 lane 2 張（[LS-70](https://linear.app/little-sprout-app/issue/LS-70/harness並行後端票搶同一個本機-supabase-容器db-reset-互踩-隔離或序列化) 落地後可放寬）、設計 lane 1 張、UI 實作 lane 依設計核可數；巡檢每次多做一步：某 lane 有空位 → 取該 lane Backlog 中優先度最高、依賴已解的票 → 改 Ready → 派工；票文要有 lane 與 blocked-by（用 Linear blockedBy 關係）。」

## 規則（寫進 `docs/COLLABORATION.md` §5「Lane 與 WIP」新節＋§4-b 巡檢步驟＋§7 列；`CLAUDE.md` 一行）

* **Lane**＝Linear label：`lane:harness`、`lane:backend`、`lane:design`、`lane:ui`、`lane:product`（需使用者決策的規格題，不派工）。每張票必帶一個 lane 標籤（開票即標）。
* **WIP 上限**（同 lane 狀態 In Progress＋In Review 的票數）：harness 1、backend 2（[LS-70](https://linear.app/little-sprout-app/issue/LS-70/harness並行後端票搶同一個本機-supabase-容器db-reset-互踩-隔離或序列化) 落地後 3）、design 1（Pencil 單一實例）、ui＝已核可設計稿對應的畫面群數（目前 [LS-46](https://linear.app/little-sprout-app/issue/LS-46/設計定稿合併c-基準使用者指定調整-designlittlesproutpen) → 1；[LS-67](https://linear.app/little-sprout-app/issue/LS-67/設計多寶貝-profile-三畫面建檔管理切換-ui-designervisual-reviewer-3-輪) 核可後 +1）。
* **依賴**只用 Linear `blockedBy` 關係，不用文字；「依賴已解」＝所有 blockedBy 皆 Done。
* **Backlog→Ready 機械規則**（巡檢每輪、以及任一票進 In Review／Done 時）：對每個 lane，若 In Progress＋In Review < 上限 → 取該 lane Backlog 中 priority 最高、blockedBy 全 Done、且不需使用者決策（非 `lane:product`）的票 → 改 Ready → 立即派工（Ready 不停留）。同 priority 取 createdAt 最早。
* 例外：`lane:design` 與 `lane:ui` 共用 Pen 時，ui 票的「設計稿讀取階段」期間 design lane 視為滿。
* 巡檢輸出多一段「lane 狀態表」（每 lane：上限／在飛／候補票）。

## 機械面

* `scripts/ops/patrol.sh` 無 Linear token，lane 步驟由 orchestrator 用 MCP 執行；§4-b 的 cron prompt 模板加入 lane 步驟（列 Backlog by label、查 blockedBy、算在飛數）。
* CI／pre-push 不驗（Linear 側規則）；§7 列標 ⚠️ 巡檢承載，盲區：忘了標 lane 的票不會被補位——巡檢輸出列「無 lane 標籤的 open 票」提醒。

### Findings

**F1（major）** `docs/COLLABORATION.md` §4-b cron prompt 模板（約行 124）與 §5-b 守門句（約行 165：「候補票文須已有可驗證驗收條件與 scope（Spec 出口），缺者不算候補、在 lane 狀態表標『待 Spec』」）不一致。cron 模板裡「候補」的判定只寫「該 lane Backlog 中非 `lane:product`、priority 最高、`blockedBy` 全 Done」，完全沒有檢查驗收條件／Spec 出口，也沒有輸出「待 Spec」標記的步驟。

**失敗情境**：cron 模板被當成自包含的可執行 prompt（§4-b 明寫「hook 引用的就是這段」），若照字面執行，一張只有標題、還沒寫驗收條件的 Backlog 票（尚未過 Spec gate）會被判定為候補、`save_issue` 直接改 Ready 並派工——正是 §5-b 這條守門句想擋的情況，守門句形同虛設。此守門句是 PR 自行加碼（票文原文沒有要求），既然決定加、且 PR body 已註明「orchestrator 已採納」，就該在唯一的可執行落地處（cron 模板）同步落地，否則等於寫了規則但沒有對應動作，違反本專案「新增重要規則＝同時新增它的 gate」的最高原則（此處"gate"退而求其次是巡檢流程本身，更該與敘述一致）。

**建議修法**：在 cron 模板「候補以 `get_issue`（includeRelations）查 `blockedBy` 全 Done」那步之後或之前，加一句「候補票文須具備可驗證驗收條件與 scope，否則標『待 Spec』並看下一張」，跟 §5-b 的敘述與 lane 狀態表的「待 Spec」輸出對齊。
