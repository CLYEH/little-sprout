### F2　`supabase/tests/95_children_backend.sql:388-398` — **major**：30 天時鐘凍結的「mutation 自證」是空的，換個 mutation 就整包綠
第 5 段那條斷言的註解寫「這是 mutation 自證：拿掉 set_child_deleted 裡『只在 deleted_at is null 才寫入』的 if guard，這裡會直接變紅（**deleted_at 會被刷新成 pg_sleep 之後的新時間**）」。

這句話不成立：`now()` 就是 `transaction_timestamp()`，在同一個 DO 區塊（同一交易）內是**凍結的**——我實測 `t1 := now(); pg_sleep(0.2); t2 := now();` → `t1 = t2` 為 `t`（同時 `clock_timestamp()` 有前進）。所以第 392 行那個 `pg_sleep(0.05)` 完全推不動 `now()`，就算 guard 被拿掉、`update … set deleted_at = now()` 真的執行了，`v_deleted_at_2` 仍然等於 `v_deleted_at_1`，**第 395 行的斷言不可能開火**。

R1 那次 mutation 之所以變紅，是 `deleted_by` 那半在紅（我這輪實跑的錯誤訊息是「第二位 owner 重複軟刪之後 deleted_by 被洗成 …」，`deleted_at` 那條在它之前、靜靜通過了）。

**具體失敗情境**（我實跑構造出來的逃逸）：把 `set_child_deleted` 的軟刪分支改成
```sql
update public.children c
   set deleted_at = now(),                               -- 時鐘每次都刷新（bug 回來了）
       deleted_by = coalesce(v_child.deleted_by, v_uid)  -- 歸屬仍凍結
 where c.id = p_child_id;
```
→ **`95_children_backend.sql` 整包 rc=0 全綠**，而我的離線探針立刻抓到「重複軟刪把 29 天前的 `deleted_at` 刷成今天」。也就是說：I2 真正要保護的那條性質（owner 不能靠重複軟刪無限延後不可還原時點）目前**沒有任何回歸覆蓋**；第 6 段的 30 天邊界測試也不涵蓋——它從來不對「已軟刪的孩子」再呼叫一次 `true`。

這條特別值得釘住，因為 LS-57 對 diaries/albums/comments 的規則正是「只凍結 `deleted_by`、不管 `deleted_at`」；日後有人「統一兩票語意」時，最自然的改法就是上面那個 mutation，而 CI 會全綠放行。

**建議修法**：比照同檔第 6 段的既有手法，用 postgres 身分把 `deleted_at` 回填成一個過去的時間（例如 `now() - interval '29 days'`）**再**呼叫重複軟刪、然後斷言它沒被刷新（我的探針就是這樣寫的，在上述 mutation 下會紅）；同時把第 388-390 行那段「pg_sleep 之後的新時間」的註解改成事實。改動很小，但這是本票唯一沒有 gate 的核心不變量。
