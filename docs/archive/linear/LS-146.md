### Findings

**F1｜major｜`scripts/ops/review-demo-seed.sh:133`（配 `:54-61` 的參數迴圈）——文件寫的主要用法必定失敗**

```
exec bash "$lock_sh" -- bash "${BASH_SOURCE[0]}" "$@"
```
`"$@"` 在第 54-61 行的 `while [ $# -gt 0 ] … shift` 迴圈裡已經被吃光，這裡展開成**空**。結果：只要呼叫者不在 lock 內，重新執行的那一份沒有任何參數 → 走到 `:65` 的 `case "$target"` → `exit 2`。

**失敗情境（已實跑重現）**：照腳本檔頭 `:39` 寫的用法執行
`bash scripts/ops/review-demo-seed.sh --target local`
輸出：
```
→ 未在 Supabase lock 內，改經 scripts/ops/supabase-lock.sh 重新執行
✗ review-demo-seed：需要 --target local|prod
EXIT=2
```
使用者明明帶了 `--target local`，卻被告知沒帶——訊息指錯方向。作者 5 次驗證全是從外層 `supabase-lock.sh -- …` 進來（`--held` 為真、這段永遠不執行），所以沒被踩到。次生風險：操作者看到這個矛盾訊息，最順手的「解法」就是繞開 lock 自己跑，把 LS-70 的競態放回來——而這支腳本正是之後要交給人（可能是使用者本人）對正式站執行的。

**修法**：迴圈前先存一份，例如檔頭加 `orig_args=("$@")`，第 133 行改用 `"${orig_args[@]}"`（bash 3.2 下空陣列展開要留意 `set -u`，可用 `${orig_args[@]+"${orig_args[@]}"}`）；或直接由已解析的變數重建 `--target "$target"`（本例 local 分支不會有 `--yes`）。修完請實跑一次「不在 lock 內」的路徑，那正是目前零覆蓋的那條。

**F2｜minor｜`scripts/ops/review-demo-seed.sh:154`／`:157`（`run_sql`）＋ `:430` — 沒有事務邊界，斷言擋不住它自己驗出來的壞資料**

兩個 `run_sql` 都沒帶 `--single-transaction`／`-1`，psql 對 `-f`／stdin 是逐句 autocommit；`ON_ERROR_STOP=1` 只保證「出錯就停」，不保證「出錯就回捲」。

**失敗情境**：SQL 檔中段任一句失敗（例如未來加欄位造成 media INSERT 違反新 CHECK），`auth.users`／`profiles`／`families`／`children`／`invites` 已經各自 commit，media 之後全部沒有 → 留下「登得進去但空空如也的審核家庭」。更關鍵的是檔尾 `:393-426` 的 `do $$ … raise exception 'SEED FAIL…'` 自我檢查：它**在自己的 DO 區塊裡**丟例外，前面所有資料早就落地了——這個斷言只能報警、無法回捲它剛判定為錯的狀態。`:430` 的錯誤訊息說「中止——不繼續上傳 Storage」對 Storage 是準的，但對 DB 半套資料是靜默的。目前靠「重跑冪等」自癒，正式站則多一段人必須看懂 exit code 的空窗。

**修法**：`run_sql` 兩處加 `--single-transaction`（docker 那條同樣支援），讓 SEED FAIL 直接回捲成「什麼都沒發生」。一個字的改動，語意從「報警」升級成「全有或全無」。

**F3｜minor｜`scripts/ops/review-demo-seed.sh:188-192`——Storage 批次刪除的結果完全沒檢查**

`curl -sS -X DELETE … -o /dev/null` 沒有 `-f`、沒有接 exit code、回應丟掉，接著無條件印「✓ 批次刪除請求已送出」。而上傳端 `storage_put`（`:435-439`）用的是 **POST（非 upsert）**，物件已存在會回 409。

**失敗情境**：service key 輪替／bucket 名變更／反向代理擋掉 DELETE → 刪除靜默失敗 → DB 端照樣重建（family 級聯刪乾淨）→ 走到 `:445` 第一次 POST 撞 409 → `exit 1`，訊息是「✗ 上傳原圖失敗：media_id=…」。會 fail loud，但指向錯的一步，正式站現場除錯要多繞一圈；且此時 DB 已經重建完成、Storage 還是舊物件，是 F2 那種半套狀態的另一個入口。

**修法**：DELETE 加 `-f` 並檢查 exit code（失敗即 `exit 1`），或上傳改帶 `-H "x-upsert: true"` 讓上傳本身冪等（兩者擇一即可，後者順帶讓整個 Storage 步驟不依賴刪除成功）。

**F4｜minor（PLAUSIBLE，僅正式站路徑）｜`scripts/ops/review-demo-seed.sh:272`——對 prod `auth.users` 做前綴硬刪**

```
delete from auth.users where email like 'review-demo%';
```
`--target prod --yes` 時這句直接打正式站。`like 'review-demo%'` 沒有網域錨點：任何 email 以 `review-demo` 開頭的**真實使用者**（`review-demo@gmail.com` 之類）會被硬刪，並沿 `profiles.id … on delete cascade`（`20260822120000_init_schema.sql:38`）連帶刪掉他的 profile 與 `family_members`，其家庭的 `created_by` 被 set null。這是邀請制家庭 app，撞名機率極低，所以標 PLAUSIBLE、不是 blocker；但這是**不可逆**的正式站刪除，而修法只有一行。

**修法**：`where email in ('${OWNER_EMAIL}','${MEMBER_EMAIL}')`。註解說前綴是為了收「family_id 對不上但帳號還在」的網——那兩個固定 email 已經完整覆蓋該情境（含 handoff 提到的 `shouldCreateUser` 幽靈帳號，它的 email 與固定值完全相同）。建議在使用者核可的正式站執行**之前**改掉。

**F5｜minor｜`scripts/ops/review-demo-seed.sh:56`——`--target` 漏帶值會無聲無限迴圈**

`--target) target=${2:-}; shift 2 ;;`：`--target` 是最後一個參數時 `$#` 為 1，`shift 2` 失敗（腳本是 `set -uo pipefail`，沒有 `-e`）→ 不 shift、`while [ $# -gt 0 ]` 恆真。

**失敗情境（已實跑重現）**：`bash scripts/ops/review-demo-seed.sh --target`（打字漏了值）→ 無任何輸出、CPU 空轉，5 秒後仍在跑，只能 kill。違反 fail loud。

**修法**：照本 repo 既有寫法（`scripts/ops/supabase-lock.sh` 的 `--timeout` 分支）補一句 `[ -n "${2:-}" ] || { echo "✗ review-demo-seed：--target 缺值" >&2; exit 2; }`。
