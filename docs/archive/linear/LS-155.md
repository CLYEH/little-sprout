## M1（major・race・已實測重現 40P01）新增的 media UPDATE 會對「呼叫者已非成員」的家庭取新的 `families` 鎖，檔頭的鎖序證明在這個情境不成立

**檔案**：`supabase/migrations/20260904070941_delete_account_media.sql:185-188`（新增的 UPDATE）、檔頭鎖序推演 `:48-80`（關鍵是 `:67`「…的每個家庭，跟這裡 media UPDATE 會影響到的家庭集合完全相同」）、`docs/API.md:1346-1362`。

**問題**：那句 UPDATE 只篩 `uploaded_by`／`deleted_at`，不限定家庭。使用者「已退出／被移除、但 media 還留在該家庭」時，`media_storage_sync()` 會對那個家庭的 `families` 列下 `UPDATE storage_used_bytes`——本交易對這個家庭**沒有**任何 `family_members` 列可刪、`enforce_family_has_owner()` 也不會鎖它，所以這是本交易第一次、也是唯一一次對該 `families` 列取鎖，而且發生在已持有其他 `families`／`family_members` 鎖之後。檔頭「家庭集合完全相同」「只是重新確認已持有的鎖」兩句在這條路上都是錯的。

**前提可達性**：`docs/API.md:195`／`20260822120200_rls_policies.sql:166` 的 `family_members_delete` policy 明文允許「owner 移除成員／任何人自行退出」，而成員離開時 media 不會被清掉 → 「非成員家庭仍有我的 media」是既有、有文件的正常狀態。

**實測 1（E2，單連線）**：U1 已退出家庭 X（成員列不存在）、X 內留有 U1 的一張 500,000 bytes 照片；U1 `delete_my_account()` 後 → 該 media `deleted_at` 非 NULL、X 的 `storage_used_bytes` 500000→0。證明 UPDATE 確實會對非成員家庭寫入並取鎖。

**實測 2（E3，三連線，具體失敗時序）**：
- 家庭 X（`family_id` 較小）：UO owner、U3 member、U1 **已退出但留有 media**；家庭 A：UO owner、U3、U1 皆為成員。
- S0（撐開窗口用）持有 A 的一列 `family_members` 列鎖；
- S2＝`finalize_account_deletion(U3)`（LS-151 EF 的第一道防線）：處理完 X（持有 `families(X)` FOR UPDATE），走到 A 時卡在 `family_members(A)`；
- S1＝U1 的 `delete_my_account()`：`DELETE family_members` → owner_guard 取得 `families(A)`；接著新增的 media UPDATE 要 `families(X)` → 被 S2 擋住；
- S0 釋放後 S2 要 `family_members(A)`（含 S1 已刪未提交的那列）→ 互等。
- 結果：`ERROR: deadlock detected … CONTEXT: while locking tuple in relation "family_members" / SQL statement "SELECT 1 from public.family_members fm2 where fm2.family_id = v_family_id for update" / finalize_account_deletion line 33`（S2 被回滾＝EF 的帳號刪除失敗）。
- **對照組**：同一份 setup、同一組時序，只把函式 `create or replace` 回 LS-143 版本（無 media UPDATE）→ **無死鎖**，finalize 7.0s 正常完成、`delete_my_account` 11.8ms 完成。死鎖確實是本 PR 這句 UPDATE 引入的。
- S0 只是把窗口撐大；窗口本身不需要它——finalize 是「先 X 後 A」，`delete_my_account` 只要在這兩步之間插入即可，是自然競態。

**影響**：40P01 可重試、無資料損毀（API §10 有重試契約），但這正是 LS-151 R2→R3 花一輪修掉的同一類問題，而本 PR 的檔頭宣稱它不可能發生——下一個改這支函式的人會照著這段錯誤推演走。

**建議修法（擇一，orchestrator 裁定）**：
- (a) 把 media 軟刪納入同一個全域順序：先算出 distinct family_id（成員家庭＋留有 media 的家庭），依 `family_id` 遞增逐家 `select 1 from public.family_members where family_id = f for update`（比照 finalize R3）再做 media UPDATE；
- (b) 把 UPDATE 限縮成「呼叫者仍是成員的家庭」，讓實作與檔頭／API.md 現有敘述一致，「退出後留下的 media」另票處理（但要注意這會讓票文「照片在我們伺服器上就刪掉」的承諾出現缺口）；
- (c) 若決定接受這個殘餘死鎖：把 `:67` 與 `docs/API.md:1350-1362` 改寫成事實（非成員家庭是唯一未經 `family_members` 的取鎖點、殘餘 40P01 交由重試契約承接），不要留下「已證明不會死鎖」的錯誤敘述。
