## Findings

### m1（minor／race／**PLAUSIBLE**）情況 2 的 `DELETE FROM families` 確實引入了一種新的鎖強度，檔頭與 API.md 的「沒有引入任何新的鎖」「不會死鎖」講得太滿

`supabase/migrations/20260903084231_delete_account.sql:137-145`（宣稱處：同檔 `:62-77`、`docs/API.md:1189`）

情況 3 走的 `delete from family_members`（`:176`）→ 既有 trigger `FOR NO KEY UPDATE`（`20260822120100_triggers.sql:70`）確實零新鎖、零新順序，這段沒問題。但情況 2 是直接 `DELETE FROM public.families`——刪列本身就取 **FOR UPDATE 等級**的列鎖，而 LS-6 檔頭 `20260822120100_triggers.sql:66-68` 白紙黑字記著 reviewer 當初實測：「FOR UPDATE 與子表 FK 檢查取的 FOR KEY SHARE 互斥，先插子表、再動成員的兩個併發交易會互相死鎖」。這正是本票在情況 2 又把那個形狀帶回來了。

**具體失敗情境**（未實測，故標 PLAUSIBLE）：使用者是家庭唯一成員，A 裝置的背景上傳佇列正在 `insert into media`（RI 對 families 取 FOR KEY SHARE）→ B 裝置呼叫 `delete_my_account()`，情況 2 的 DELETE 排在該 families 列上等 FOR UPDATE → A 那句 insert 的 statement trigger `media_storage_sync()` 接著要 `update families set storage_used_bytes`（鎖升級）→ 等 B 手上的 tuple lock → 迴圈成立 → `40P01`。影響僅止於一邊拿到死鎖錯誤（通常是上傳那邊）後重試，**無資料損壞**，且只有「同一個使用者的另一個 session」才進得了這個窗（單成員家庭沒有別人能寫）。

**建議**：不改邏輯，改口徑——把檔頭 `:62-77` 與 API.md `:1189` 的「沒有引入新的鎖／不會死鎖」修成「情況 3 無新鎖；情況 2 的 families 刪除必然取 FOR UPDATE，與同家庭併發子表寫入存在既有已知的 KEY SHARE 升級死鎖窗，最壞是一邊 40P01 重試」。UI 票也可在呼叫前先停掉上傳佇列。

### m2（minor／race／**PLAUSIBLE**）情況 2 的守門在鎖之外，`approve_join` 剛加入的成員可能被連坐刪掉

`supabase/migrations/20260903084231_delete_account.sql:137-145`

`delete … where id in (select … not exists(other member))` 的子查詢在 READ COMMITTED 下用的是**本語句開始時**的快照；若此時 `approve_join`（`20260823010000_join_approval.sql:332` 只取 FOR NO KEY UPDATE、不改列）正持有該 families 列的鎖，DELETE 會排隊等鎖，**而列本身沒有被 UPDATE，解除阻塞後不會觸發 EPQ 重新評估 qual**，於是「已經不是唯一成員」的家庭仍被刪除，剛被核准的成員連同其 family_members 列一起 cascade 消失（trigger 因家庭已不存在而 `continue`，不會報錯）。

**可觸發性**：只有 owner 能核准入家，而情況 2 的家庭裡 owner 就是刪帳號者本人 → 需要同一使用者兩個 session 幾乎同時「核准入家」與「刪帳號」。窄，但不是不可能（多裝置）。

**建議**（可留給後續票）：情況 2 改成兩段——先 `select fm.family_id … order by 1 for no key update`（同時把情況 2 的取鎖順序固定成 family_id 遞增，順手收斂 m1 提到的順序不確定性），拿到鎖後**再重新評估**「唯一成員」謂詞，才 DELETE。這樣 m2 完全關窗；m1 的 FK KEY SHARE 死鎖窗仍在（DELETE 終究要 FOR UPDATE），別把兩者混為一談。

### m3（minor／測試覆蓋）情況 2 的測試只放 diary，沒有 `media`；混合案也沒有測

`supabase/tests/91_delete_account.sql:156-215`

情況 2 是本票唯一的**不可逆硬刪**路徑，而真實家庭一定有照片。目前測試的 fixture 只有一篇 diary，所以「家庭 cascade ↔ `media_storage_sync()` DELETE 分支對正在被刪的 families 列下 UPDATE」這個交互完全沒被釘住；同理「同一次呼叫同時吃到情況 2＋情況 3」也沒有測。我已手動驗過兩者都正確（見上方「已實跑驗證」），所以這是**覆蓋缺口、不是缺陷**——但下次有人動 `media_storage_sync()` 或 cascade 拓撲時，這條線沒有測試會叫。

**建議**：§3 的 fixture 補一列 `media`（含 `byte_size`）＋斷言 `media` 與 `feed_items` 均清空；另加一段「獨居家＋共居家」的混合案。

### m4（minor／測試斷言）§5 的收尾訊息宣稱 `display_name／avatar_url` 不受影響，但只驗了 `display_name`

### m5（minor／口徑／已實測阻塞、死鎖變體 PLAUSIBLE）誠實化之後仍有一處未窮盡：recheck 失敗的候選家庭被 `FOR UPDATE` 鎖住到 commit

`supabase/migrations/20260903084231_delete_account.sql:83-86`、`docs/API.md:1215-1216`

兩處都寫「這只發生在『唯一成員』的家庭，**能觸發它的只有同一個使用者自己的另一個 session**（單成員家庭沒有別人能寫）」。R2 之後這句話不再窮盡：迴圈在 `:188` 取 `FOR UPDATE`，`:190-195` 的 recheck **失敗時並不會釋放那把鎖**（列鎖持有到交易結束），而 recheck 失敗的定義就是「這個家庭現在已經有別人了」。於是被擋住的可以是**另一個使用者**（剛被核准的成員的裝置），不只是呼叫者自己的第二個 session。

**具體失敗情境**：A 是 F 家唯一成員，A 在裝置 1 按「核准 C 加入」、裝置 2 幾乎同時按「刪除帳號」。刪帳號那支在 `:188` 排隊 → C 加入 commit → `:190` recheck 失敗、F 保留，但 `FOR UPDATE` 已在手上。此時 C 的手機開始上傳照片（`INSERT INTO media`，FK 取 `FOR KEY SHARE`）→ **C 被擋住**，直到 A 的 `delete_my_account()` commit。

**實測**（把機制釘死，不是推論）：另開一條連線持有 `families` 某列的 `FOR UPDATE` 3 秒，另一條 1.2 秒後 `INSERT INTO media` 到同一個家庭 → `PROBE_ELAPSED=1.82 秒`，確實被完整擋住。

**嚴重度為什麼只有 minor**：迴圈之後剩下的工作只有 1 句 DELETE＋3 句 UPDATE＋1 句 DELETE＋1 句 UPDATE，毫秒級；而且**鎖強度與取得時點都不是新的**（R1 版本的 `DELETE FROM families` 對同一列同樣取 `FOR UPDATE`），所以**沒有新的死鎖形狀**——這純粹是那段「為了誠實而重寫」的文字本身還差一句。40P01 的對手方可以是別的使用者這個變體我沒有實跑（需要三方精準時序），標 **PLAUSIBLE**。

**建議**：在上述兩處各補一句——「recheck 失敗的候選家庭同樣被 `FOR UPDATE` 鎖住到 commit；此時該家庭已有其他成員，他們的子表寫入會被擋住毫秒級，40P01 的對手方因此不限於呼叫者自己的 session」。可留給 LS-151 或記入 LS-96，不需要在本票改。
